# Use Case 20: Automated macOS real-physics sim setup (prebuilt pybullet, no source build)

## Summary
Make the **PyBullet (real-physics / mastery) simulator** reproducibly installable on **modern macOS (26 / Tahoe, Apple Silicon)**, where the current `scripts/train.sh` path is broken: it builds `pybullet==3.2.6` from source into a uv venv, and pybullet's vendored zlib (`zutil.h` `#define fdopen(fd,mode) NULL`) collides with the macOS 26 SDK's `_stdio.h fdopen` declaration, so **no from-source pybullet (3.2.6 or the 3.2.7 that gym-pybullet-drones pins) can compile** — regardless of Xcode CLT/clang version. This UC adds a **`scripts/setup-sim-macos.sh`** that provisions the sim from **prebuilt binaries only** via miniforge/conda-forge, teaches **`scripts/train.sh`** to use that path on macOS instead of the doomed source build, and updates the README. It changes only tooling/docs — **no `src/` runtime change, no observation-schema change, no checkpoint impact**. The proven recipe (validated on a managed macOS 26 arm64 box, 2026-09-18 — run logged "using PyBullet backend"): miniforge in `~/miniforge3` (user-space, no admin) → `dronefly` conda env (Python 3.12) with conda-forge **prebuilt `pybullet` (3.2.5, newest arm64 on conda-forge)** → install `gym-pybullet-drones@7ebad1e…` (the pinned 2.2.0 SHA) with **`pip install --no-deps`** so pip does not source-build pybullet, plus its other deps explicitly → `pip install -e ".[dev]"` → run via the `drone-fly` console script from the env. The `gym-pybullet-drones` `pybullet>3.2.7` pin is conservative; its `CtrlAviary`/`DroneModel`/`Physics` (used by `pybullet_adapter.py`) run against 3.2.5.

## Acceptance Criteria
1. **`scripts/setup-sim-macos.sh` exists, is executable, and is `shellcheck`-clean** (bash 3.2-compatible — macOS `/bin/bash` — and works under zsh invocation).
2. **Miniforge handling = prompt-before-install:** if `conda`/miniforge is absent, the script explains and asks for explicit confirmation before downloading miniforge into `~/miniforge3` (no silent install; no `sudo`). If the user declines, it exits non-zero with guidance and installs nothing.
3. **Prebuilt-only provisioning:** the script creates/reuses a `dronefly` conda env (Python 3.12), installs **conda-forge `pybullet`** (prebuilt — the compiler is never invoked for pybullet), installs `gym-pybullet-drones@<pinned SHA from train.sh>` via **`pip install --no-deps`** plus its remaining runtime deps explicitly, then `pip install -e ".[dev]"`. The pinned SHA is read from / kept consistent with `scripts/train.sh` (single source of truth), not duplicated by hand.
4. **Verification step:** after provisioning, the script imports `pybullet`, `gym_pybullet_drones` (`CtrlAviary`, `DroneModel`, `Physics`), and `drone_fly`, and prints the resolved pybullet API version + the active backend; it exits non-zero if any import fails.
5. **Fail-fast + steer-to-container:** if the native path cannot be satisfied (e.g. conda-forge has no usable arm64 `pybullet`, or a required import fails on this SDK), the script does **not** attempt a source build — it exits with a clear message and emits the ready-to-run **Linux-container** command (Apple `container` / Docker) that installs the prebuilt manylinux pybullet wheel.
6. **`scripts/train.sh` macOS branch:** on `Darwin`, `train.sh` no longer attempts the `pybullet==3.2.6` source build; it uses the `dronefly` conda env if present (running training through it), or otherwise instructs the user to run `setup-sim-macos.sh`. Non-macOS (Linux/CI) behavior is unchanged. The change is guarded so CI (Linux) exercises the existing path exactly as before.
7. **README updated:** the "Simulator bootstrap" section documents the macOS prebuilt path (miniforge → conda-forge pybullet → `gym-pybullet-drones --no-deps` → `drone-fly` console script), states that **from-source pybullet is unsupported on modern macOS SDKs** and why, documents the **3.2.5 / `--no-deps`** rationale, and keeps the existing test-required doc-contract sections intact (so `tests/test_bootstrap_docs.py` / `test_viz_contract.py` still pass).
8. **No runtime/behavior change:** nothing under `src/` changes; the numpy `simple` adapter and all existing tests remain byte-for-byte unaffected; the full existing suite stays green on Linux CI (all three gates: `ruff check`, `ruff format --check`, `pytest`).

## Potential Pitfalls & Open Questions
- **Boundary — the macOS/conda path is NOT exercisable in Linux CI** (no macOS runner, no conda). Like the existing pybullet sim boundary, the conda/macOS execution is a documented **untested boundary**; QA verifies what IS hermetic on Linux — the script is shellcheck-clean and structurally correct, `train.sh`'s macOS branch is guarded/dry-runnable without a Mac, the README doc-contract tests pass, and any pure-logic helpers are unit-tested — and the README records the boundary.
- **Assumption** — conda-forge's arm64 `pybullet` (currently 3.2.5) remains runtime-compatible with the pinned gym-pybullet-drones (`>3.2.7` is conservative; validated working). If a future gym-pybullet-drones bump uses a 3.2.7-only API, the fail-fast/container path (AC5) is the escape hatch.
- **Bash portability** — must run under macOS `/bin/bash` (3.2): no associative arrays, `${x^^}`, or `mapfile`. Prefer `$(...)`, plain loops.
- **Consent/policy** — managed machines: never `sudo`, never auto-install; the miniforge prompt (AC2) is mandatory.
- **Single-source SHA** — the gym-pybullet-drones commit pin must not drift between `train.sh` and `setup-sim-macos.sh`.

## Clarifications / Decisions
- Q: If miniforge is absent, install it automatically?
  A: **Prompt before installing** — explain and ask first; never silent, never `sudo` (managed machine).
- Q: When the native path can't work, what should the script do?
  A: **Detect and steer to the Linux container** — fail fast with the ready-to-run container command; never attempt a doomed source build.
- Q: Does this touch runtime/observation/schema?
  A: No — tooling + docs only; no `src/` change, no checkpoint impact.
