# Use Case 41: Give the now-committing actor a real learning gradient toward success (reward stall)

## Summary
UC-40 (PR #44) successfully unfroze the training actor: on a fresh post-fix run `entropy` (5.36) and `std` (0.923) now trend **down** off their frozen initialization, and the K0 "undersized slice" verdict no longer fires. But the same run exposes the next bottleneck — a **reward stall**: `health_callback` now reports "Reward stalled: ep_rew_mean is not improving," with `ep_rew_mean` glued to −5 (the pure time-penalty floor ≈ 0.05/step × ~101 steps), `ep_len` pinned at 101 (the no-progress "stuck" cut at step 100), and `success_rate` still 0% at 16% of training. The actor is now *active and committing* — but toward a do-little/0-success local optimum, because nothing in the reward pulls it toward **sustained** flight and waypoint progress: the climb shaping is potential-based/telescoping (UC-39), so a drone that lifts briefly but doesn't sustain altitude nets ~0 and returns exactly −5. There is a real risk that with `ent_coef` lowered to 0.001 (UC-40) `std` collapses onto this bad policy before it explores into success — the UC-38 premature-entropy-collapse failure mode. This use case diagnoses (with evidence, via the dev-team) why the committing actor converges to 0 success with reward stalled, and delivers a fix so a genuine gradient toward success exists — touching `src/drone_fly/env/config.py` (RewardConfig, stuck_window), `src/drone_fly/train/config.py` (ent_coef), `src/drone_fly/env/racing_env.py` (reward assembly + stuck cut), and the reward-stall / premature-collapse rules in `src/drone_fly/train/health.py`.

## Acceptance Criteria
1. The reward stall is diagnosed **with evidence** (specific code/config lines, metric traces, or a minimal reproduction): it is shown concretely why a now-committing actor returns exactly the time-penalty floor and reaches 0% success, and each candidate lever below is explicitly confirmed or ruled out.
2. Candidate levers are each evaluated with evidence, not blindly applied: (a) **reward gradient** — whether sustained-flight / airborne-survival / progress reward is too weak relative to the time penalty; (b) **`ent_coef`=0.001** — whether `std` collapses too early (premature-collapse), needing a floor or slower decay; (c) **`stuck_window`** — whether the 100-step no-progress cut ends episodes before takeoff→progress can be chained (training-time only).
3. A concrete fix is implemented such that, in a short CPU smoke-train, the episode return / airborne-or-progress signal **measurably responds** (rises above the flat −5 time-penalty floor, or a progress/airborne metric leaves its stalled baseline) — with rationale tied to the evidence from criterion 1.
4. The fix demonstrably does **not** cause premature entropy collapse: in the smoke-train `std` does not collapse to ~0 while success is still 0 (verified against `health.py`'s premature-collapse rule and/or a direct std-floor assertion).
5. All UC-37/38/39 reward invariants are preserved: potential-based/telescoping (F = γΦ′ − Φ), non-farmable, ≈0 on the floor, capped at target (no ceiling-seeking), per-episode shaping total < `completion_bonus`, `climb_gamma == training gamma`, penalty-free stuck-cut, and the anti-suicide guarantees. Any change extends these, never violates them.
6. If any `RewardConfig` value changes, the README reward table is updated in the same change and the doc-contract tests stay green (`tests/test_reward_docs.py`, `tests/test_bootstrap_docs.py`, `tests/test_viz_contract.py`); the `stuck_window ≥ ~65` golden-fixture floor is respected (change a training value, not the fixture default).
7. The full suite stays green: `uv run --extra dev pytest`.
8. Lab-validation is in-sandbox only (no GPU): unit tests + a short CPU smoke-train. The full ~12h GPU retrain remains the user's to run on Windows and is NOT a gate.

## Potential Pitfalls & Open Questions
- **Risk** — reward shaping is heavily protected work (UC-37/38/39). The temptation to "just add a bigger climb reward" can break non-farmability or the per-episode < completion_bonus bound. Any change must be shown to preserve every invariant, with tests.
- **Risk** — the three levers interact: strengthening reward, raising `ent_coef`, and relaxing `stuck_window` could individually or jointly over-correct (e.g. reward hacking, or episodes that never terminate). The fix should be the minimal set the evidence supports, not all three at once unless justified.
- **Assumption** — a short CPU smoke-train can show the return/airborne signal *responding* and std *not collapsing*, even though it cannot reach task mastery. Treated as sufficient per AC8 (matches the UC-40 smoke-train precedent).
- **Edge case** — a stronger sustained-flight reward must not let the drone farm reward by hovering in place without progressing toward waypoints; progress toward the objective must still dominate.
- **Ambiguity** — whether the real blocker is reward *magnitude*, exploration (`ent_coef`), or episode *length* (`stuck_window`) is exactly what the diagnosis must settle before choosing the lever(s).
