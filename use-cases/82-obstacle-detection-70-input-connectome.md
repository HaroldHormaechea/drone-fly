# Use Case 82: Obstacle detection for the 70-input connectome — ray noise model + obstacle-avoidance retrain (sim-only)

## Summary
This is the next slice of the UC-73 draft and the project's pivot target after UC-79/80/81 showed the MLP-student distillation cannot be made to complete courses by tuning observation or distillation (even `teacher_full` and a combined on-policy + β-floor + reward-shaped PPO stayed at 0% held-out). UC-78 already shipped the vision **"eyes"** module (`src/drone_fly/eyes/`: fov-report / label / dataset / train / eval / bench) that turns Liftoff camera frames + telemetry ego-motion into the **40 obstacle-ray values** the user's **70-input connectome** (lineage 10/11/12, `sim/course.py ray_cone`) consumes. UC-82 closes the loop that UC-78 explicitly deferred (UC-73 AC7–AC8), **entirely in the GPU simulator with no Liftoff**: (1) produce a **measured obstacle-ray noise model** — the per-ray error distribution of the perceived rays vs ground-truth — following the UC-70 gate-detector-noise pattern; (2) **retrain the 70-input connectome student under that ray noise** on obstacle-bearing courses; and (3) **demonstrate obstacle avoidance** — a lower collision share on unseen validation tracks than the same model with its obstacle-ray inputs blanked (the AC8 control). The deliverable is the first evidence that the connectome actually *uses* vision-derived obstacle rays to avoid obstacles. Live Liftoff validation (UC-73 AC9–10) remains a later slice. The run uses the 23 GB of existing UC-71 captures already on disk and the existing `uc70-diag-run1` 70-input student; it runs in-sandbox on the RTX A3000.

## Acceptance Criteria
1. **Obstacle-ray noise model.** A command (following the UC-70 detector-noise pattern, e.g. `drone-fly eyes noise-model` or equivalent) produces a **measured per-ray noise model** of the obstacle-ray estimator's error — per-ray bias, spread, and miss / false-alarm behaviour vs the exact ground-truth rays, split at least by in-view / out-of-view and by distance — and writes it as a YAML the simulator can inject (same shape/role as the gate-detector `noise_model.yaml`). The error source is the UC-78 eyes estimator evaluated on held-out maps **if a trained estimator is available**; otherwise the analyst may derive the noise model from the eyes `eval` error statistics or a documented measured fallback — the chosen source is recorded in the model and the doc. A test asserts the noise model loads and injects into the ray inputs.
2. **Noise injection into the 70-input observation.** The simulator can apply the AC1 noise model to the 40 obstacle-ray inputs of the 70-input connectome observation at training and eval time (opt-in, parameterised), exactly as the gate-detector noise is applied today. With injection off / weight unset, the 70-input observation path is **byte-identical** to today (existing tests pass; a test asserts the no-injection path is unchanged).
3. **Obstacle-avoidance retrain.** The 70-input connectome student is retrained (the UC-70 pattern — distill/fine-tune from the existing teacher / `uc70-diag-run1` lineage) under the AC1 ray noise on **obstacle-bearing** courses, with a documented, resumable config and budget sized for an overnight single-GPU run. A resumable driver runs it unattended.
4. **Blanked-ray control.** The same retrain/eval is run with the obstacle-ray inputs **blanked** (zeroed / set to max-range "clear"), as the AC8 control, so the collision comparison is like-for-like (same budget, seed, tracks).
5. **Collision-reduction report.** On unseen validation tracks (held-out maps, obstacles present), report **collision share** and completion for (a) the ray-noise-trained model and (b) the blanked-ray control, with the outcome breakdown (collision / floor / out-of-bounds / gate_lost / timeout), fixed episode count and seed. The headline metric is **collision share with rays < collision share blanked**.
6. **Driver + doc.** A resumable back-to-back driver (e.g. `scripts/uc82_obstacle_avoidance.sh`) runs the noise-model build (if applicable), the two retrains, and the two evals; it is reboot-safe and documents the artifacts to copy (captures or the derived noise model, the 70-input teacher/student). `docs/experiments/uc82-obstacle-detection-70-input.md` contains one comparison table (rays-on vs blanked, plus the teacher / UC-70 references) and a recommendation.
7. **Success criterion.** The ray-noise-trained 70-input model shows a **materially lower collision share than the blanked-ray control** on the held-out obstacle tracks (a concrete threshold — e.g. a relative collision-share reduction ≥ 20% — is set in the plan and justified). If it does not, the doc records the negative result and the likely cause (ray accuracy, range/warning-time per UC-73 AC10, or the connectome lineage's own flying quality).
8. **CI-hermetic tests.** CPU-only, no Liftoff, no real captures: noise-model load + injection into the ray inputs; the no-injection byte-identity guard (AC2); the blanked-ray control path; the collision-metric math; a tiny CPU smoke retrain of the 70-input student under injected ray noise.

## Potential Pitfalls & Open Questions
- **Dependency / Assumption** — AC1's ideal error source is a *trained* UC-78 eyes estimator; none is on disk yet. The analyst must decide: train the eyes estimator first on the existing captures (adds significant time and data-quality unknowns), or derive the noise model from the eyes `eval` statistics / a documented measured fallback. Record the choice; prefer whatever yields a defensible per-ray noise model within the overnight budget.
- **Risk** — the 70-input lineage's own flying quality in the sim is unestablished (UC-73 flags this); if the blanked-ray control itself can't fly at all, the collision comparison is uninformative. The plan should sanity-check the base model flies before attributing differences to the rays.
- **Risk** — at `RAY_RANGE` 4 m there is only ~0.2–0.3 s of warning at racing speed (UC-73 AC10); too little warning can mask a real avoidance benefit. Note it; a longer range would require retraining at the new range (out of scope here unless the evidence forces it).
- **Edge case** — out-of-view rays (below the camera / 20° uptilt) must be handled consistently between the noise model and the blanked control so the comparison is fair.
- **Risk** — GPU budget: the retrains + evals must fit the overnight single-GPU window; size the budget conservatively and keep everything resumable.
- **Assumption** — obstacle-bearing courses are available in the existing track/catalogue data (UC-24 randomization / the captured maps); if the obstacle-free `student-liftoff-open` scope used in UC-77/79/80/81 has no obstacles, the retrain must use an obstacle-bearing track set, documented.
