# Use Case 24: Full-course randomization by default + first-class feature toggles

## Summary
Make `drone-fly train` course randomization place the **full** set of course features and expose **first-class YAML toggles** for each, and fix the fact that pad randomization is currently unreachable. Today `randomize: true` randomizes gates/dynamics only: `_env_config` (`src/drone_fly/cli/__init__.py:63`) sets just `enable_course`/`enable_dynamics`; **obstacle** placement is an accidental side-effect of `_reconcile_obstacle_vision` (`src/drone_fly/train/loop.py:74`) flipping `enable_obstacles` when the obs schema carries an `obstacle_vision` block *and* randomize is on; **recharge-pad** placement needs `enable_recharge` (`src/drone_fly/env/randomization.py:325`) which nothing in the train path ever sets — so it is unreachable via the CLI; and **repair pads are never randomized at all** (`_place_recharge_pads` only appends `rechargeable=True` pads). This UC adds independent, end-to-end-wired toggles for obstacle / recharge-pad / repair-pad placement (`TrainRunConfig` → `_env_config` → `RandomizationConfig` → the randomizer's placement gates), makes recharge placement reachable (coherently coupling it to battery being enabled), and adds a **new repair-pad placement axis** (`PadSpec(..., repairable=True)`) respecting the existing solvability / descend-column-clearance guards. Per the user's decision, randomization places **exactly one recharge pad and exactly one repair pad** per course (one pad for each purpose — not a variable cover). It also changes the default so a bare `randomize: true` run uses the **full `damage_proprioception_v4` schema** with all three placement axes on — gates + obstacles + one recharge pad + one repair pad — with a matching observation schema that can sense them, all explicitly overridable. `configs/train/example.yaml` documents the new keys and default. The non-randomized path (`randomize: false`/unset) stays byte-identical to today (no schema, no placement), and the hermetic smoke-train path must stay green with the full schema + all axes on (placement must satisfy solvability on tiny fixture courses, and the width-coupling assertion `obs_schema.total_width == env.obs_width` at `loop.py:363` must hold).

## Acceptance Criteria
1. **Independent placement toggles, wired end-to-end:** new config keys control per-episode placement of (a) obstacles, (b) recharge pad, (c) repair pad during randomization, each threaded `TrainRunConfig` → `_env_config` → `RandomizationConfig` → randomizer. Each is independently unit-testable: on → the feature is placed; off → it is not.
2. **Recharge placement reachable (exactly one pad):** with the recharge toggle on (and battery active), `drone-fly train` produces randomized courses that contain **exactly one** `rechargeable=True` pad (today impossible — zero). A test drives the train-config path (not just `RandomizationConfig` directly) and asserts the pad appears.
3. **Repair placement added (exactly one pad):** with the repair toggle on (and the damage block active), randomized courses contain **exactly one** `repairable=True` pad, placed at an eligible gate anchor reusing the recharge descend-column-clear + solvability geometry. Independently unit-tested; off → none placed.
4. **Battery↔recharge / damage↔repair coherence:** enabling recharge placement without battery active — and repair placement without the damage block active — is resolved by a single documented rule (auto-enable the dependency / error / warn+skip, per clarification), never a silent no-op that yields zero pads.
5. **Full-schema default for randomized runs:** when `randomize: true` and neither `schema` nor the placement toggles are explicitly set, the run defaults to `schema: damage_proprioception_v4` with obstacle + recharge + repair placement all ON (one pad each); an explicit `schema:` or any explicit toggle overrides the corresponding default. Verified by a config-resolution test.
6. **Non-randomized parity (byte-identical):** `randomize: false` or unset yields no schema and no placement exactly as today — existing checkpoints and all current tests on the base path are unaffected.
7. **Hermetic CI green with everything on:** the smoke-train path (simple numpy adapter, fixture connectome) completes a finite update with the full schema + all placement axes on; placement satisfies the solvability guard on tiny fixture courses (or degrades safely without deadlocking the sampler within a bounded resample budget), and the width-coupling assertion holds.
8. **Docs updated:** `configs/train/example.yaml` documents every new key with its default and the full-by-default behavior; the retrain / checkpoint-invalidation implication is stated. Existing doc-contract tests stay green.

## Potential Pitfalls & Open Questions
- **Risk (checkpoint invalidation)** — defaulting randomized runs to `damage_proprioception_v4` (26-d) changes the default observation width, invalidating existing randomized-run checkpoints (fresh retrain), exactly like the UC-13/15/17/19 schema extensions. Deliberate; must be documented.
- **Risk (behavior change)** — a bare `randomize: true` now trains against a much harder course (obstacles + energy/damage constraints). Intended per the user; documented.
- **Edge case (one-recharge-pad vs energy-cover solvability)** — the existing recharge model (`_place_recharge_pads` + `is_course_solvable`) can require a *multi-pad* cover to make an energy-constrained course completable. With placement capped at **one** recharge pad, the randomizer must sample courses solvable with a single recharge pad (e.g. bound gate count / energy so one pad suffices), or relax the energy constraint accordingly. The analyst pins how "one pad" and the energy-cover guarantee are reconciled so the sampler neither deadlocks nor emits an unsolvable course.
- **Edge case (sampler termination)** — recharge/repair placement must not deadlock the sampler; reject-resample must stay bounded and satisfiable on tiny fixture courses in CI, with a safe degrade if no valid placement is found.
- **Assumption** — "one pad for each purpose" means a single recharge pad and a single repair pad; a pad is not made dual-purpose unless the analyst finds co-location is required for solvability (in which case it is documented).

## Original Description
The user wants course randomization to, by default, use the FULL observation schema and actually place ALL course features (obstacles + recharge pad + repair pad), plus first-class YAML toggles to control each — and to make pad randomization reachable at all, because today it isn't. Direct request: "Create a new UC so by default we do have the full-schema for the course randomization in the YAML with the toggles, and make it reachable, yes."

Verified current behavior (traced in the root session, cited above): `randomize: true` randomizes gates/dynamics only; obstacle placement is only an accidental side-effect of picking a vision schema + randomize (`_reconcile_obstacle_vision`, loop.py:74/100); recharge-pad placement is unreachable because nothing sets `enable_recharge` (randomization.py:325; `_env_config` cli/__init__.py:63; `_reconcile_battery` loop.py:105 only enables battery physics/obs, not pad placement); repair pads are never randomized in any path (`_place_recharge_pads` only builds `rechargeable=True` pads). YAML exposes only `randomize`, `randomize_dynamics`, `schema`. Schemas: migrated_v1, obstacle_vision_v2, battery_hunger_v3, damage_proprioception_v4 (full, 26-d). A user recording with `randomize: true` and no `schema:` produced a gates-only course (`pads: None, obstacles: None`), confirming the diagnosis.

## Clarifications
- Q: For a bare `randomize: true` run with no explicit schema/toggles, what should the default be?
  A: **Full schema + all placement ON** — default to `damage_proprioception_v4` with obstacle + recharge + repair placement all on, accepting the observation-width change and the invalidation of existing randomized-run checkpoints (fresh retrain). All overridable.
- Q: How should repair pads be placed during randomization (recharge has an energy-cover model; repair has no existing analog)?
  A: **Only one pad for each purpose** — place exactly one recharge pad and exactly one repair pad per randomized course (not a variable cover). Repair pad placed at an eligible gate anchor reusing the recharge descend-column-clear + solvability geometry.
- Q: What if recharge placement is requested without battery (or repair without damage)?
  A: Resolve with one documented coherence rule rather than a silent zero-pad no-op (auto-enable the dependency / error / warn+skip) — the analyst pins the exact rule.
