# Use Case 83: Eyes v2 — cut the obstacle-ray miss rate (classification head + focal loss + denser mining)

## Summary
UC-82 showed that feeding the UC-78 vision "eyes" obstacle rays to the 70-input connectome makes obstacle avoidance **worse** than blanking them (collision 57% vs 35%), because eyes v1 misses ~96% of obstacles (≈99% of the nearest-quarter, 0–4 m, the ones that matter) and mostly just predicts "clear." UC-82's recommendation, and UC-78's own "likely levers" list, both point at **the estimator, not more avoidance training**. This UC builds **eyes v2** to materially cut the obstacle-ray miss rate — especially near obstacles — using the two levers that are fully doable in the GPU sandbox with the existing 23 GB of UC-71 captures (no Liftoff, no new capture flights): **(1) a hit/no-hit classification head trained with focal loss (and hit-weighted class rebalancing)** instead of v1's mostly-regression objective that collapses to "clear" under ~5% hit-ray imbalance; and **(2) denser mining of the existing captures** — lower frame stride and hit-weighted sampling to extract many more hit-bearing frames than v1's ~17.5k thin sample. A deeper/pretrained or depth-model backbone (UC-78 lever 3) is an optional stretch, not required. Eyes v2 is trained and evaluated with the existing `src/drone_fly/eyes/` CLI (`dataset` / `train` / `eval`), measured on the same held-out maps as v1 so the numbers are directly comparable. If v2 clears a usefulness threshold, this UC **re-derives the obstacle-ray noise model** from v2's measured error and **re-runs the UC-82 rays-vs-blank comparison** to see whether better eyes now help the connectome; if v2 does not clear the threshold, that is a documented result and the follow-up (new close-to-obstacle captures, which need Liftoff) is named. Sim-only; runs in-sandbox on the RTX A3000.

## Acceptance Criteria
1. **Classification head + focal loss (opt-in, default-off byte-identical).** The eyes model gains an opt-in hit/no-hit classification head trained with focal loss and hit-weighted class rebalancing, selectable by config/flag. With the new options unset, `eyes train` / the model are behaviourally unchanged from v1 (existing UC-78 eyes tests pass; a test asserts the default path is unchanged). The new loss/head is covered by unit tests (shape, class-imbalance behaviour, that focal loss down-weights easy "clear" rays).
2. **Denser dataset mining.** `eyes dataset` can build a denser, hit-weighted training set from the existing captures (e.g. lower `--stride-s`, a hit-oversampling / hit-frame-biased option), disk-aware (honour `--disk-margin-gb`, downscaled frames, cache) given the ~18 GB free / 87%-full disk. The manifest records the sampling settings and the resulting hit-ray fraction (which must be higher than v1's ~5%). A test covers the sampling/manifest logic on a tiny synthetic capture set.
3. **Eyes v2 trained + measured, comparable to v1.** `eyes train` produces a v2 checkpoint on the existing captures; `eyes eval` reports on the **same held-out maps** as UC-78 (HangarC03, MinusTwo, ThePit; range, tol identical) the per-ray **miss rate (all hits), miss-in-view, miss nearest-quarter (0–4 m), and false-alarm on clear rays**, split as in UC-78, so v2 vs v1 is a like-for-like table.
4. **Success criterion.** Eyes v2 shows a **materially lower nearest-quarter (0–4 m) miss rate than v1's ~0.99** — concrete bar set in the plan and justified (e.g. a relative reduction ≥30%, i.e. ≤~0.69, as a first milestone), without blowing up the false-alarm rate on clear rays (bounded, bar set in the plan). If v2 clears it, proceed to AC5; if not, record the negative result and name the next lever (new close-to-obstacle captures — needs Liftoff — or a depth-model backbone).
5. **Conditional: re-derive noise model + re-run the UC-82 comparison (only if AC4 passes).** Re-derive the obstacle-ray noise model from eyes v2's measured held-out error (the UC-82 `eyes noise-model --from-eval` path) and re-run the UC-82 rays-vs-blank obstacle-avoidance comparison (`scripts/uc82_obstacle_avoidance.sh` recipe with the v2 noise model) on the same held-out proc courses / seed, reporting collision share rays-v2 vs blanked. The headline is whether better eyes now reduce collisions vs blanked (reversing UC-82's −62%).
6. **Driver + doc.** A resumable driver runs the v2 dataset build → train → eval (→ conditional noise-model + UC-82 re-run). `docs/experiments/uc83-eyes-v2.md` has one comparison table (v1 vs v2 ray-accuracy metrics; and, if AC5 ran, rays-v2 vs blanked collision share) + a recommendation.
7. **CI-hermetic tests.** CPU-only, no Liftoff, no real captures: classification-head + focal-loss math; default-off byte-identity; denser-sampling / manifest logic; model IO contract; a tiny CPU train smoke on the v2 path; the v1-vs-v2 eval-metric comparison math.

## Potential Pitfalls & Open Questions
- **Risk (data ceiling)** — UC-78 diagnosed the root cause partly as *thin data* (7 train maps, ~5% hit rays). Classification head + focal loss + denser mining attack the imbalance and sample count, but the *information* ceiling of monocular ranging from the existing captures may still cap v2 below usefulness. A plausible honest outcome is "v2 better than v1 but still not enough to help the connectome"; AC4/AC5 branches cover it.
- **Blocked lever** — UC-78's top lever is "much more and denser hit data, including captures flown *close to obstacles*," which requires new Liftoff capture flights — not available in-sandbox. UC-83 deliberately pursues the two in-sandbox levers; the capture lever is named as the follow-up.
- **Risk (disk)** — denser mining lowers stride → more frames → larger dataset/cache; disk is ~18 GB free / 87% full. The dataset build must be disk-aware (downscale, margin guard, prune intermediate) and the plan must estimate the footprint before the full build.
- **Risk (false alarms)** — pushing miss rate down can trade into more false alarms on clear rays, which UC-82 showed also mislead the connectome. AC4 bounds the false-alarm rate, not just the miss rate.
- **Assumption (overfit)** — v1 overfit after ~epoch 4 on thin data; v2's denser set + rebalancing + regularisation should help, but early-stopping / val-split discipline (no map leakage, honour the catalogue split) must be kept.
- **Scope** — the depth-model backbone (UC-78 lever 3) is a stretch; if it doesn't fit the overnight/session budget it is a follow-up, not a blocker for AC1–AC4.
