# Use Case 37: Floor start + airborne survival reward (learn to take off and stay up)

## Summary
Training does not learn to fly: across ~1900 episodes on the k1 slice the drone "falls like a rock" every episode, `ep_rew` is flat (~−101), `success` is 0%, and `entropy`/`std` rise (the signature of *no learning signal*). Root cause is a bootstrap trap, **not** a physics limit — the sim's thrust-to-weight ratio is 2 (hover = 50% throttle; the code's own `_WARMUP_ACTION=[0.5,…]` hovers perfectly), so the task is easily solvable. The two compounding problems: (1) the episode starts the drone **mid-air** (`start_z_range=(0.7,1.5)`), which is artificial — with the policy's near-zero initial throttle the drone simply drops from height; and (2) the reward has **no dense survival term**, so every episode ends in the −100 crash cliff and all rollouts score ≈−101 → flat advantages → no gradient toward staying up. This UC fixes it by making the start realistic and adding a small survival incentive: **start on the floor** (a real drone begins grounded), and **reward being airborne** by a modest per-step amount so the only way to earn reward is to throttle up and stay up — while keeping the bonus small enough that completing gates/finish always dominates loitering. Deliberately **no** hover-bias on the action: the policy must learn takeoff from a zero-throttle neutral. This intentionally changes default training dynamics (unlike recent byte-identity-preserving UCs); airborne-start code paths and their existing tests stay unchanged.

## Acceptance Criteria
1. **Floor start (default).** On reset, the drone spawns resting on the floor — z at the adapter's ground rest height (within the floor band, not the old 0.7–1.5 m mid-air) with ~zero initial velocity. A test asserts the reset state's altitude is at/near the floor and initial vertical velocity ≈ 0. The old mid-air start is no longer the default (may remain available via config if trivial, but the default is floor).
2. **No hover-bias / must learn takeoff.** The neutral (zero) action still maps to ~zero throttle; nothing is added to make the drone rise on its own. A floor-start drone under the zero/neutral action stays on the floor (does not spontaneously lift). The policy must learn to command throttle to take off.
3. **Grounded early-termination arms only after first takeoff.** The UC-25/UC-36 grounded detector does **not** fire while the drone has never risen above the floor band this episode; it **arms** only after the drone first leaves the floor band (takeoff). After it has taken off, returning to the floor and resting fires the grounded cut exactly as today. A test: a floor-start drone that never lifts off is **not** cut by the grounded detector (it is instead bounded by the no-progress/stuck detector and/or the episode timeout); a drone that takes off and then floors **is** cut.
4. **Airborne-start behavior unchanged (backward compatible).** Any episode that starts with the drone already above the floor band (as the existing UC-25/UC-36 tests and fixtures do) is considered "taken off" at step 0, so grounded-termination arms immediately and behaves byte-for-byte as before this UC. All pre-existing UC-25/UC-36 grounded/no-progress tests pass unchanged.
5. **Airborne-only survival reward.** A new documented, configurable per-step survival reward (e.g. `RewardConfig.airborne_bonus`) is added to `compute_reward`. It accrues **only while the drone is airborne** (above the floor band) and is exactly **zero while the drone is on/at the floor**, so sitting on the ground earns nothing. A test asserts an airborne step yields the bonus and a grounded step does not.
6. **Balanced so completion dominates loitering.** The survival bonus is sized so that: (a) the net per-airborne-step reward (`airborne_bonus − time_penalty`) is **strictly positive**, so staying airborne beats sinking/crashing and there is a gradient toward takeoff; AND (b) the **maximum total survival reward accruable over a full episode is strictly less than the reward for completing the course** (and ideally below a single normalized `gate_bonus`), so a policy that merely hovers/loiters without progressing scores strictly worse than one that reaches gates and finishes. A test asserts both bounds with the shipped constants (net-per-step > 0; max-episode survival reward < `completion_bonus`). The exact value is the dev-team/challenger's call, documented.
7. **Non-flyers and loiterers remain bounded.** A drone that never takes off, or that takes off and hovers without progressing, is still terminated by the existing no-progress (stuck) detector and/or the episode timeout — episodes never run unbounded.
8. **Determinism preserved.** Same seed → identical reset state, placement, and trajectory. The change alters defaults but stays fully deterministic (RNG contract intact).
9. **Intended-change hygiene.** This UC deliberately changes default training dynamics (floor start + survival reward). Any golden fixtures / byte-identity tests that legitimately change are regenerated/updated with the change explained (they are not silently deleted), while airborne-start reward/termination paths remain unchanged. User-facing docs/README are updated to describe the floor start and the new reward term. All three CI gates stay green (`uv run ruff check .`, `uv run ruff format --check .`, `uv run --extra dev pytest`).

## Potential Pitfalls & Open Questions
- **Risk (core interaction)** — floor start collides with UC-36's grounded early-termination: a grounded drone would be cut at ~step 10 before takeoff. Resolved by AC-3 (arm-after-takeoff). The "armed" flag must reset each episode.
- **Edge case** — "takeoff" threshold: what altitude counts as having left the floor. Use the floor band (`floor_epsilon`) or a slightly higher liftoff threshold to avoid arming on a sub-epsilon bounce; the dev-team picks and documents it.
- **Risk (local optimum)** — a drone that learns to hover airborne without progressing. Mitigated by AC-6 (survival reward capped well under completion) and AC-7 (the no-progress detector cuts a non-progressing hover after `stuck_window`), so completing always scores strictly higher than loitering.
- **Tension** — the existing `time_penalty` (−0.05/step) opposes a survival bonus. `airborne_bonus` must exceed `time_penalty` for staying up to be net-positive (AC-6a), yet the episode total must stay below completion (AC-6b). The challenger pins the value against these two bounds.
- **Assumption** — floor rest height comes from the adapter's ground contact model (the crash recording showed z≈0.013 at rest); use that, don't hardcode a magic number if the adapter exposes it.
- **Intended dynamics change** — unlike UC-33/34/35/36, this changes default trajectories on purpose; byte-identity across the change is NOT a goal (AC-9), but airborne-start paths and determinism are preserved.

## Original Description
User, 2026-09-20, after ~1900 episodes of k1 training still failing ("falls like a fucking rock", `ep_rew` flat −101, 0% success, rising entropy): asked whether the task is even solvable / whether the drone has enough thrust. Investigation confirmed thrust is ample (TWR=2, hover=0.5 throttle) and the failure is a bootstrap trap (mid-air start + near-zero initial throttle + no survival reward → flat crash reward → no gradient). User's chosen fix: "the reward for survival should be the only improvement. Normally a drone would start from the floor anyway — one of our issues may be we are starting from an in-flight position, which is artificial. So, start from the floor → 0 throttle → reward for staying alive that is not too much as to favor not going through the end or gates as preferable."

## Clarifications
- Q: With a floor start, the drone begins "grounded", so UC-36's grounded early-termination would end the episode before takeoff. How should grounded-termination behave?
  A: **Arm only after first takeoff** — the grounded detector stays disarmed until the drone first leaves the floor band; after that, dropping back down and resting ends the episode. A drone that never lifts off is caught by the no-progress/timeout instead.
- Q: Should the per-step survival reward accrue while the drone is sitting on the floor, or only while airborne?
  A: **Airborne only** — reward is earned only while off the ground, so the only path to reward is to take off and stay up (prevents a "sit still" local optimum).
