# Use Case 63: Repoint the desktop app at the reservoir pipeline (launch / monitor / audit / view `gpu_prototype` runs)

## Summary
The UC-61 desktop app (FastAPI + Uvicorn backend in a pywebview native window, vanilla HTML/CSS/JS front-end, embedded `viz/viewer.{html,js}` recording player) was **deleted in commit `cc817f4`** (the "2026-10 cleanup") because its entire training backend — the Stable-Baselines3 `drone-fly train` subcommand, the `TrainRunConfig`/`PruneRunConfig` YAML surface, and `drone_fly.config` — was removed along with the old SB3 + gymnasium racing lineage. The project's **active** training lineage is now the frozen-K1 reservoir pipeline in `gpu_prototype/`, which has **no UI at all**: runs are launched by invoking launcher scripts directly from the CLI inside the `dronefly` micromamba env, monitored by eyeballing `[aug] …` stdout lines, and audited by running `verify_proc.py` / `diagnose_proc.py` by hand. This use case **restores the desktop app from git and swaps its dead SB3 backend for a reservoir one**, so the whole reservoir loop — launch, live-monitor, honesty-gated audit, and recording playback — is drivable from the UI again, mirroring the old RunRegistry subprocess pattern but targeting `gpu_prototype/` launchers instead of `drone-fly train`.

The app is restored at `app/` from `cc817f4~1` (recover via `git show cc817f4~1:app/<file>` / `git ls-tree -r cc817f4~1 -- app`) and then **surgically repointed**: the front-end shell (left-nav → main-view, hash routing, Settings pane, explicit-save forms, no auto-save, no version history — UC-61 AC2/AC9), the server static mounts, `app/logs.py`, `app/recordings.py` (server-side gunzip for the embedded viewer), and the pywebview launcher (`app/__main__.py`) are kept; the **training backend is rewritten** so launching a run spawns a `micromamba run -n dronefly python <launcher> …` subprocess for a `gpu_prototype/` recipe rather than `drone-fly train --config <yaml> --no-tui`. The dead SB3 imports and config machinery (`drone_fly.config`, `drone_fly.config.ConfigError`, `app/configs_io.py`'s `TrainRunConfig`/`PruneRunConfig` YAML (de)serialisation, the `drone-fly train` / `drone-fly prune` argv builders, and the SB3 `.zip`/`vecnormalize.pkl` checkpoint-and-resume state machine) are **removed or replaced**, because none of those symbols exist anymore after `cc817f4`. The reservoir has no YAML config schema — a run is parameterized by **env flags + `train_aug(...)` keyword knobs + a `.pt` save path** — so the UC-61 form-serialization-to-YAML surface (UC-61 AC3/AC4) is replaced by a reservoir-run form that emits those env vars and launcher arguments. The app stays a thin front-end over the existing `gpu_prototype/` scripts (it shells out to them under the hood, UC-61 AC10); the only reservoir-side code it may add is observability/coordination glue (a run registry + progress parsing), not training/env/reward logic.

Concretely the UI must let a user:
1. **Launch a reservoir run** — pick a recipe/launcher (`exp11_count-curriculum.py`, `exp12_gap-steering.py`, `exp13_count-gap.py`, `train_shaping.py`, or a generic `train_aug(...)` form), set the env flags (`PROC_TRACTABLE`, `PROC_RAYCAST`, `PROC_SHAPING`, `PROC_OBS_TERMINAL`, `PROC_GAP`) and the `train_aug` knobs (`N`, `budget`, `roll`, `epochs`, `logstd_init`/`logstd_final`, `anneal_start`, `count_curr_frac`, `pos_curr_frac`, `warm_from` warm-start checkpoint, `warm_src_extra_dim`), and a `save_path` (`.pt`); the app spawns `micromamba run -n dronefly python <launcher> <save_path> [budget]` (with the env vars set on the child) as a tracked subprocess.
2. **Monitor progress live** — parse the periodic `[aug] it <N> steps <M> fps <F> ep_rew/step <r> tilt <t>deg compl <c>%` stdout lines (emitted every 20 iterations by `train_aug`, plus the final `[aug] saved <path>`) into a dashboard (steps, fps, ep_rew/step, tilt, completion EMA), tail the raw captured log, and surface GPU/throughput.
3. **Run honesty-gated audits** — invoke `verify_proc.py <ckpt> <eps>` (with `AUDIT_SEED` for the canonical seeded head-to-head) and `diagnose_proc.py <ckpt> <eps>` from the UI, and surface completion **plus** the cheat checks (obstacle BARGING %, mean speed, mean tilt, min surface clearance, HOVERING indicator) and the failure breakdown — a high completion % that *cheats* (barges / hovers) must be **visibly flagged, not celebrated**, consistent with `EXPERIMENTS.md`'s "`Honest?`" rule.
4. **View recordings** — keep/restore the embedded brain + actions + 3D-course viewer for `training/<name>/recordings/*.json[.gz]` produced by `record_aug.py`, served via `app/recordings.py`'s server-side gunzip and the unchanged `viz/viewer.{html,js,css}` (the standalone `viz/viewer.html` is the reference).
5. *(Optional)* **Register + promote finished runs** — append a numbered row to `training/EXPERIMENTS.md` and offer promotion of a winning checkpoint into a committed `training/NN-<slug>/` model via `save_readout.py` (strips the deterministic `body.layer.*` sparse connectome, keeping `body.input_projection` + readout).

All new backend logic (run registry, `[aug]` line parser, audit runner + output parser, recipe/knob schema) is covered by **hermetic tests** that run in CI without a GPU, CUDA, pybullet, torch, or a display — subprocess spawning, env-var assembly, signal handling, log parsing, and audit-output parsing are driven through injected fakes exactly as the UC-61 `RunRegistry` did (its spawner/signaler/probe were all injected). Front-end / native-window rendering that cannot run headless is documented for owner eyeball, per the UC-59/60/61 convention. This UC **restores and repoints the app only** — it does not change any `gpu_prototype/` training, env, reward, or audit logic, nor any committed model under `training/`.

## Acceptance Criteria
1. **App restored & repointed, SB3 lineage removed:** `app/` is restored from `cc817f4~1` and builds/imports with **no reference to the deleted SB3 world** — `drone_fly.config`, `drone_fly.config.ConfigError`, `TrainRunConfig`, `PruneRunConfig`, the `drone-fly train`/`drone-fly prune` argv, and the SB3 `.zip` + `vecnormalize.pkl` resume machinery are gone or replaced. Importing `app.server` / `app.runs` / `app.configs_io` succeeds without importing torch, pybullet, or SB3.
2. **Recipe + knob schema (replaces the YAML form):** the Train surface exposes the reservoir run parameters — a recipe/launcher choice (`exp11_count-curriculum` / `exp12_gap-steering` / `exp13_count-gap` / `train_shaping` / generic `train_aug`), the five env flags (`PROC_TRACTABLE`, `PROC_RAYCAST`, `PROC_SHAPING`, `PROC_OBS_TERMINAL`, `PROC_GAP`), the `train_aug` knobs (`N`, `budget`, `roll`, `epochs`, `logstd_init`, `logstd_final`, `anneal_start`, `count_curr_frac`, `pos_curr_frac`, `warm_from`, `warm_src_extra_dim`), and a `save_path` — each via a typed control, with sensible defaults matching the launchers' defaults. Explicit **Save**, no auto-save on blur/navigation, no config version history (UC-61 AC9 preserved).
3. **Launch spawns the reservoir launcher:** starting a run spawns `micromamba run -n dronefly python <launcher> <save_path> [budget]` (CWD = `gpu_prototype/`, or project root as the scripts assume) with the selected `PROC_*` env vars set on the **child's** environment; for the generic `train_aug` recipe the knobs are forwarded as the launcher's arguments. Spawn, argv, and env assembly are verified through an **injected fake spawner** (no real subprocess, no micromamba, no GPU).
4. **Run registry (mirrors old RunRegistry):** concurrent named runs are tracked in a `name → {pid,state}` map backed by the `training/<name>/` (or `save_path`-derived) filesystem; on backend restart, state reconciles from disk (a finished `.pt` present → `finished`; a periodic checkpoint `.pt` present → resumable/`idle`; neither → `ready`). Stop terminates the run's process group cleanly; the spawner, signaler, and any capability probe are injected so the whole state machine is unit-testable with fakes.
5. **Live `[aug]` parsing → dashboard:** the backend parses the `[aug] it … steps … fps … ep_rew/step … tilt …deg … compl …%` stdout lines (every-20-iter cadence) and the terminal `[aug] saved <path>` line into structured status (iteration, Msteps, fps, ep_rew/step, tilt°, completion EMA), streamed to the UI (SSE/WebSocket or poll) to drive progress + curves. A malformed or partial line is skipped without crashing the stream. The raw captured log is tailable in the UI, and GPU/throughput (fps) is shown.
6. **Audit from the UI with honesty surfaced:** the user runs `verify_proc.py <ckpt> <eps>` and `diagnose_proc.py <ckpt> <eps>` from a run's view (with an `AUDIT_SEED` field defaulting to `1234` for the canonical seeded comparison); the app parses and displays **completion %** alongside the **cheat checks** — obstacle BARGING % (episodes with any inside-obstacle step), avg inside-steps, min surface clearance (m), HOVERING (mean speed m/s, mean tilt °), mean steps alive, and the completed-only barging line — plus the `diagnose_proc` failure breakdown (by obstacle count / aperture / cause of death).
7. **Honesty flag, not celebration:** when an audit reports a non-trivial barging % or a hovering signature (≈0 speed / ≈0 tilt), the UI **visibly flags the run as dishonest/suspect** and does not present the raw completion % as a success; the "`Honest?`" verdict (`EXPERIMENTS.md` rule — "a higher % that cheats does NOT count") is shown next to completion. Verified hermetically against captured sample audit stdout (honest vs. barging vs. hovering fixtures).
8. **Embedded recording viewer restored:** from a run, the user opens `training/<name>/recordings/episode_<n>.json[.gz]` (as written by `record_aug.py`) in the embedded brain + actions + 3D-course viewer; `app/recordings.py`'s server-side gunzip and the unchanged `viz/viewer.{html,js,css}` static mount are used (UC-61 AC8 preserved); the reference standalone is `viz/viewer.html`.
9. **(Optional) register + promote:** if implemented, the app can append a numbered row to `training/EXPERIMENTS.md` for a finished run and offer promotion of a winning checkpoint to a committed `training/NN-<slug>/` model dir via `save_readout.py <full_ckpt.pt> <out_readout.pt>` (which strips `body.layer.*` and keeps `body.input_projection` + readout). This is additive and clearly separated from launch/monitor; if deferred, it is documented as out of scope, not half-built.
10. **Thin-front-end invariant:** every operation reduces to spawning an existing `gpu_prototype/` script (launcher, `verify_proc.py`, `diagnose_proc.py`, `record_aug.py`, `save_readout.py`) or reusing an existing asset (`viz/viewer.*`); the only reservoir-side additions are observability/coordination glue (run registry, log/audit parsing) with **no changes to training/env/reward/audit logic** and **no edits to any committed `training/NN-*/` model**.
11. **Hermetic tests + docs:** backend logic — recipe/knob → argv+env assembly, run enumeration & state reconciliation, subprocess/stop state machine, `[aug]` line parser, `verify_proc`/`diagnose_proc` output parser incl. the honesty verdict, server-side gunzip, recording enumeration — is covered by tests that run in CI with **no GPU/CUDA/torch/pybullet/micromamba/display** (all externals injected as fakes, as UC-61 did). Front-end/native-window behavior that cannot run headless is documented for owner eyeball. `app/README.md` is updated to describe launching the app and the reservoir workflow (removing the SB3 instructions).

## Potential Pitfalls & Open Questions
- **Missing input** — the reservoir has **no YAML config schema** like the old `TrainRunConfig`; a run is "env flags + `train_aug` kwargs + save path." The UC-61 form-serialization-to-YAML machinery (`app/configs_io.py`) therefore cannot be reused as-is — it must be replaced by a recipe/knob form that emits env vars + launcher args. Decide whether runs persist as a small per-run metadata file (recipe + flags + knobs) so the registry can reconstruct/re-launch them after a backend restart, since there is no committed `configs/train/*.yaml` to enumerate anymore.
- **Edge case** — `micromamba run -n dronefly python <launcher>` is a different interpreter-resolution problem than UC-61's venv/pybullet probe: the old auto-detect walked `.venv*` dirs and probed `import pybullet`. Decide the new resolution (assume `micromamba` on PATH + a `dronefly` env, make the env name a Settings field, probe `import torch`?) and fail with an actionable message when micromamba/the env is absent — mirror the old "no capable interpreter → `RunError`" behavior, do not silently fall through.
- **Risk** — several launchers hardcode a warm-start base path (e.g. `exp11` uses `BASE = "/workspace/drone-fly/gpu_prototype/proc_shapeA_term.pt"`); a UI `warm_from` field only takes effect for the generic `train_aug` recipe unless the launchers are parameterized. Clarify whether the UI edits those per-recipe bases or only exposes `warm_from` on the generic form — do not silently imply a knob is wired when the chosen launcher ignores it.
- **Risk — honesty gate is the whole point:** the dangerous failure mode is a polished dashboard that shows a big completion % for a run that barges through obstacles or hovers. AC6/AC7 must land: completion is **never** shown as success without the barging %, clearance, and speed/tilt alongside it, and a cheating run is flagged. Fixtures for honest / barging / hovering audit outputs are needed to test the verdict hermetically.
- **Edge case** — the `compl …%` field in the `[aug]` line comes from `env.metric()` and may be absent/empty for some envs; the parser must treat the trailing metric as optional and not assume a completion EMA is always present.
- **Edge case** — `save_path` collisions and the periodic-vs-final save: `train_aug` writes the checkpoint to `save_path` every 200 iterations **and** again at the end (same path), and recordings live under `training/<name>/recordings/`. Reconcile the registry's notion of "run name" (UC-61 used `training/<name>/`) with the reservoir's free-form `.pt` save path — decide whether the UI imposes a `training/<name>/`-style layout or tracks arbitrary save paths.
- **Edge case** — restoring `app/` must not reintroduce the deleted SB3 symbols transitively: `app/server.py`, `app/runs.py`, and `app/configs_io.py` all `import` from `drone_fly.config` in the `cc817f4~1` revision. Every such import has to be removed/replaced during restore or the app will fail to import (AC1). A grep for `drone_fly.config`, `ConfigError`, `TrainRunConfig`, `PruneRunConfig`, `drone-fly train`, `drone-fly prune`, `vecnormalize` after restore should come back empty.
- **Assumption** — single-user local developer tool; app and training run on the same machine (UC-61's local-only topology). Remote-GPU control is out of scope. `training/` checkpoints and logs are gitignored and regenerable; the app must not assume they are present.
- **Open question** — scope of the optional promote/register surface (AC9): is `training/EXPERIMENTS.md` registration + `save_readout.py` promotion in scope for this build, or deferred? The ledger is currently hand-maintained prose with a specific numbering convention; automated row-append must match that format exactly or be left out.
