# Use Case 51: Expose the training curriculum schedule + restagger defaults so floor-takeoff is the last isolated stage

## Summary
The three training curricula — airborne spawn (UC-44), attitude authority (UC-46), and collision penalty (UC-41) — all anneal on the same `anneal_fraction ≈ 0.5` schedule, so at the 50% mark of training the spawn drops to the floor, attitude authority jumps to full, and the collision penalty ramps to 100 **simultaneously**. Diagnosis of the 1M-step `k1-training` run (UC-50 reward on, randomized maps) showed this synchronized difficulty cliff is the current wall: 0% success with *rising* entropy/std and `ep_rew` worsening to ≈ −102, i.e. the airborne-phase flight skill does not survive the handoff to floor-start and the policy diffuses. Independently, none of these schedule knobs (the anneal fractions, start/end values, per-curriculum enable flags, and `ent_coef`) are reachable from `drone-fly train --config` — they exist only as `TrainConfig` dataclass defaults and the YAML resolver (`TrainRunConfig.from_mapping` in `src/drone_fly/config.py`) validates against a fixed whitelist that omits them, so every schedule experiment costs a code change plus a ~12h retrain. This use case (1) surfaces the curriculum knobs + `ent_coef` in the validated train YAML and wires them through the CLI to `TrainConfig`, and (2) restaggers the **default** schedule so difficulty steps are isolated and floor-takeoff is the last, longest stage: attitude authority anneals to full earliest, the collision penalty reaches its end value next (≈ mid-training), and the airborne spawn stays **fully airborne through the early stages** and descends to the floor only in the final stretch (a start-delay/warmup on the airborne curriculum, mirroring the collision curriculum's `warmup_fraction`). Default `total_timesteps` is bumped 1M → 2M so the isolated floor-takeoff tail is not starved. Scope is training-orchestration and config surface only — reward, env, adapters, PPO assembly, and termination are untouched. The behavioral verdict (does the drone now take off and fly gates) is the user's fresh GPU retrain and is explicitly out of scope; all tests here are hermetic and assert schedule *shape*, YAML round-trip, and default-parity.

## Acceptance Criteria
1. The train YAML accepts optional keys for every curriculum knob — `airborne_curriculum_enabled`, `airborne_curriculum_warmup_fraction` (new start-delay param), `airborne_curriculum_anneal_fraction`, `attitude_authority_curriculum_enabled`, `attitude_authority_start`, `attitude_authority_anneal_fraction`, `collision_curriculum_enabled`, `collision_penalty_start`, `collision_penalty_end`, `collision_penalty_warmup_fraction`, `collision_curriculum_hold_fraction` — plus `ent_coef` and `timesteps` — validated (type + range) by `TrainRunConfig.from_mapping`, with unknown or out-of-range values rejected with a clear `ConfigError`.
2. Each new key is optional; a config that sets a knob to its default value produces a run **byte-identical** to omitting it (the exposure plumbing is lossless). This guarantee is about set-to-default == omit, not about old-vs-new defaults.
3. Each new key is wired end-to-end: a value set in the YAML reaches the corresponding `TrainConfig` field consumed by the curriculum callbacks (verified without a GPU/sim).
4. The **default** schedule is restaggered so the anneals are ordered and isolated: `attitude_authority_full_fraction < collision_penalty_full_fraction < spawn_reaches_floor_fraction`, with the airborne spawn held fully airborne through the early stages (a non-zero warmup) and reaching the floor only at the very end of training (fraction 1.0).
5. A hermetic test asserts the schedule *shape* of the new defaults: attitude authority == 1.0 by its (earliest) target fraction; collision penalty == its end value by ≈ mid-training; spawn stays at its airborne start value throughout the warmup window, then anneals and reaches floor by fraction 1.0. The test asserts the **ordering/isolation and monotonicity**, not exact fraction values.
6. A bare config (no curriculum keys) reproduces the **new** staggered defaults exactly (default-parity test) — the restagger deliberately changes what "default" means; there is no hidden dependence on the old schedule.
7. Default `total_timesteps` is `2_000_000` (up from `1_000_000`) so the isolated floor-takeoff tail gets real budget.
8. `configs/train/example.yaml` documents every new key with its default in the "Optional keys" block; the README training section reflects the new default schedule and the new tunable knobs.
9. The change set touches only: `src/drone_fly/train/config.py`, `src/drone_fly/train/airborne_curriculum.py` (add the `warmup_fraction` start-delay), `src/drone_fly/config.py`, `src/drone_fly/cli/__init__.py`, `configs/train/example.yaml`, the README, and tests. Reward, env/`racing_env.py`, adapters, PPO policy assembly, and termination are not modified. The attitude and collision curriculum modules change only if their existing machinery cannot express the target schedule (collision already has warmup+hold precedent).

## Potential Pitfalls & Open Questions
- **Assumption** — the exact endpoint numbers from the selected preview (authority full @ ~25%, collision full @ ~50%, airborne warmup ~0.6 then descent to 1.0, `ent_coef` 0.005) are advisory targets the analyst/challenger may tune and justify; the ACs assert the *ordering/isolation and shape*, not the precise fractions.
- **Edge case** — the airborne `warmup_fraction` + `anneal_fraction` must compose coherently (warmup end ≤ anneal end == 1.0); validation must reject a warmup that runs past the anneal window, and the smoke/`timesteps: 256` example run must still terminate the schedule sanely.
- **Risk** — restaggering defaults changes default-run behavior; the "byte-identical" guarantee (AC-2) applies to the exposure plumbing (set-to-default == omit), not to old-vs-new defaults. Any caller relying on the old implicit schedule must opt back in explicitly.

## Original Description
Use case: Expose the training curriculum schedule in the run config, and restagger the default schedule so floor-takeoff is the last isolated stage.

Background/motivation (from this session's diagnosis of the k1-training run): a fresh 1M-step retrain with UC-50 enabled + default curricula + randomized maps ended at 0% success with RISING entropy/std and ep_rew worsening to ~-102 (≈ one full collision penalty/episode). Physics (UC-48, T/W 2.25) and reward (UC-50) are fine. The wall is a SYNCHRONIZED CURRICULUM CLIFF: all three training curricula anneal on the same schedule (anneal_fraction 0.5), so at the 50% mark spawn drops to floor (UC-44 airborne curriculum), attitude authority jumps to full (UC-46), and the collision penalty ramps to 100 (UC-41) all at once — three difficulty spikes landing simultaneously, on top of per-episode randomized courses. The airborne-phase flight skill does not survive the handoff to floor-start; the policy diffuses (entropy rises) because the UC-50 gate correctly withholds cheap progress reward once it can no longer reach the altitude band from the floor.

Second, independent finding: these curriculum knobs (airborne_curriculum_anneal_fraction, attitude_authority_start/anneal_fraction, collision_penalty_start/end/warmup_fraction/hold_fraction, the three *_curriculum_enabled flags, and ent_coef) exist only as TrainConfig dataclass defaults in src/drone_fly/train/config.py and are NOT reachable from `drone-fly train --config` — the YAML resolver in src/drone_fly/config.py (TrainRunConfig.from_mapping) validates against a fixed whitelist of _Spec entries that omits all of them. So today every schedule experiment costs a code change + a 12h GPU retrain. This is the same trap UC-50's reward weights hit.

Scope of this UC (two parts):
1. EXPOSE: surface the curriculum schedule knobs + ent_coef in the train YAML — add validated _Spec entries in TrainRunConfig.from_mapping and wire them through to TrainConfig in the CLI (src/drone_fly/cli/__init__.py). Update configs/train/example.yaml to document them (with their defaults, in the "Optional keys" block). Keep them optional; omitting them must be byte-identical to today's behavior for the DEFAULT values.
2. RESTAGGER DEFAULTS: change the default schedule so difficulty steps are isolated and floor-takeoff is the last, longest stage. Target shape (analyst/challenger to refine exact numbers): attitude authority anneals first & fastest (full by ~25%); collision penalty ramps next (full by ~50%); airborne spawn anneals LAST and slowest with a hold (start descending ~60%, reach floor at 100%), i.e. airborne_curriculum_anneal_fraction ~0.8 + a hold fraction. Bump default total_timesteps (1M -> 2M) so the isolated floor-takeoff tail isn't starved. Preview the user selected suggested: attitude_authority_anneal_fraction 0.25, collision_penalty_warmup_fraction 0.4, airborne_curriculum_anneal_fraction 0.8, airborne_curriculum_hold_fraction 0.2, ent_coef 0.005, timesteps 2_000_000.

Invariants / guardrails:
- Confined to training-orchestration + config surface: src/drone_fly/train/config.py, src/drone_fly/train/{airborne,attitude,collision}_curriculum.py (only if a hold phase needs adding), src/drone_fly/config.py, src/drone_fly/cli/__init__.py, configs/train/example.yaml. Do NOT touch reward.py, racing_env.py, adapters, PPO policy assembly, or termination.

Hermetic tests only (no pybullet/GPU): assert the schedule shape (e.g. authority reaches 1.0 by fraction X; spawn stays airborne until fraction Y then reaches floor by 1.0; collision reaches 100 by ~0.5), YAML round-trip of the new knobs, and default-parity where a bare config reproduces the new staggered defaults.
- README/training-section docs must reflect the new default schedule + the new tunable knobs.

## Clarifications
- Q: Default total_timesteps for a restaggered run?
  A: Bump the default to 2_000_000 (isolated floor-takeoff tail ~800k steps; default run ~24h).
- Q: How should the airborne spawn descend to floor?
  A: Late-descent tail — spawn stays fully airborne through the early stages and descends only in the final stretch; add an `airborne_curriculum_warmup_fraction` start-delay param (mirrors collision's warmup_fraction).
- Q: Are the specific endpoint fractions firm or advisory?
  A: Advisory — ACs assert the ordering/isolation and shape only (authority-full < collision-full < spawn-floor); the analyst/challenger pick and justify exact fractions.
