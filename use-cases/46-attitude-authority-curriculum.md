# Use Case 46: Attitude-authority curriculum (stop the drone tumbling so it can learn to take off)

## Summary
The drone won't fly because it **tumbles**, not because of reward, spawn curriculum, or throttle. On the real pybullet backend, throttle=1.0 + level attitude climbs 0.9→9.36 m and throttle=0.5 + level hovers at 0.900 m exactly — lift and the CTBR→RPM mixer are fine. But the PPO policy (action std ~1.0 early in training) commands wild roll/pitch/yaw **rate** commands into the open-loop mixer (`ctbr_to_rpm`, `rate_gain=0.15`, in `adapter/pybullet_adapter.py`; `BASE_MAX_BODY_RATE=4.0` in `adapter/simple.py`), which has **no attitude stabilization**, so the drone flips (roll reached 171° in a reproduction), vectors thrust sideways/down, loses net lift, and falls. UC-45 proved the recordings are byte-faithful, so this tumbling is real behavior and is the same root that defeated seven reward/curriculum use cases (37→45). This use case adds a **training-time attitude-authority curriculum** (the direct analogue of UC-44's airborne-start reverse curriculum, applied to attitude): scale the roll/pitch/yaw command channels by an "authority" factor that starts low (so a noisy policy cannot flip the drone → it stays roughly level → net thrust stays up → it can climb and collect the existing airborne/climb reward) and anneals up to full authority as training progresses (so the policy regains full maneuvering control, bootstrapped from an upright-and-climbing policy). Throttle is never scaled. Eval and recording run at full authority (1.0 = the annealed endpoint) so true flight is still measured. No reward-function change and no inner-loop controller — those levers are deliberately deferred so this result is attributable to authority-limiting alone. It touches a new `train/attitude_curriculum.py`, `env/racing_env.py`, `train/config.py`, `train/loop.py`, and the README.

## Acceptance Criteria
1. A pure schedule `attitude_authority_at(num_timesteps, cfg)` exists and is unit-tested: returns the configured `attitude_authority_start` at training-progress fraction 0; returns exactly `1.0` at and after the configured anneal-end fraction; is monotone non-decreasing; is clamped to `[attitude_authority_start, 1.0]`; and handles degenerate/off cases (anneal fraction 0 or curriculum disabled → constant 1.0, i.e. full authority = no-op). Stateless in `num_timesteps` (resume-correct).
2. `RaceEnv` gains a per-instance attitude-authority override (default **1.0**) settable via `set_attitude_authority(factor)`, applied in `RaceEnv.step` by multiplying **only** the roll/pitch/yaw action channels (indices 1,2,3) before they reach `adapter.step`. A unit test asserts the throttle channel (index 0) is never scaled and the three attitude channels are scaled by the factor.
3. The curriculum is applied **only** during training rollouts (a `BaseCallback` pushing the scheduled factor via `training_env.env_method("set_attitude_authority", …)`). Eval and recording environments run at full authority (1.0) — verified by a test constructing an eval/recording env and asserting its effective attitude authority is 1.0 regardless of the schedule.
4. The curriculum is wired into training on both the fresh and resume paths, guarded on an enable flag; a disable path restores pre-UC-46 behavior (authority constant 1.0). Config fields added: `attitude_authority_curriculum_enabled` and `attitude_authority_start` (and any anneal-fraction field), placed beside the airborne-curriculum fields.
5. No reward-function change; UC-44 (airborne-start curriculum, climb-bias init), exploration/entropy, and UC-45 recording fidelity/provenance are all untouched. The CTBR→RPM mixer is unchanged (no inner-loop controller). Existing reward-math, doc-contract, and recording tests stay green.
6. The full CI gate is green: `uv run ruff check .`, `uv run ruff format --check .`, `uv run --extra dev pytest`. Committed tests are hermetic (no pybullet).
7. The README documents the attitude-authority curriculum (what it scales, training-only scope, anneal schedule) and re-states the standing **fresh-run requirement** (a valid evaluation needs a brand-new model with old checkpoints cleared, since the climb-bias init is fresh-build only).
8. Lab validation (not a CI gate): a short pybullet/CPU smoke (via the main-checkout venv with `PYTHONPATH=<WORKDIR>/src`) demonstrates that under reduced early authority the drone stays markedly more upright (lower max |roll|/|pitch|) and gains altitude (z rises) versus full authority with the same policy/noise. Reported in the PR.

## Potential Pitfalls & Open Questions
- **Assumption** — `attitude_authority_start = 0.25`, linear anneal 0.25→1.0 over the first 50% of `total_timesteps` then full, `attitude_authority_curriculum_enabled = True`. Tunable; the dev-team may adjust the start value or anneal shape/duration with justification.
- **Assumption** — Multiplicative scaling of the command channels (cleaner) rather than hard clamping. The analyst should confirm scale-vs-clamp and confirm the application point (multiply in `RaceEnv.step` — adapter-agnostic — vs scaling `rate_gain`/`max_body_rate` inside each adapter).
- **Edge case** — Scaling must land before `sanitize_action`'s clip semantics don't change the intent; verify the scaled command still lies in the valid box and that yaw is treated like roll/pitch (all three attitude channels scaled equally).
- **Risk** — Too-low a start could make the drone unable to correct at all (sluggish), too-high could still let it flip; the start value is the key tunable and the smoke test should sanity-check it.
- **Risk** — If reducing authority still doesn't produce learned takeoff on a fresh GPU retrain, the remaining lever is a proper inner-loop attitude stabilizer (a separate future UC) — out of scope here by design.

## Original Description
(Full seed handed to the dev-team; summarized above.) The drone tumbles under the open-loop CTBR→RPM mixer (no attitude damping) because PPO commands wild roll/pitch/yaw rates with std~1.0 early; level control is proven fine (throttle 1.0 → climb to 9.36 m; 0.5 → hover 0.900 m). Add a training-time attitude-authority curriculum: scale the roll/pitch/yaw command channels by a factor annealing from a low start (≈0.25) up to 1.0 over the first ~50% of training, throttle never scaled, eval/recording at full authority. Mirror UC-44's curriculum pattern: pure `attitude_authority_at` schedule + `BaseCallback` pushing `set_attitude_authority` on `RaceEnv`, applied in `RaceEnv.step`. No reward change, no inner-loop controller (both deferred for clean attribution), mixer unchanged, UC-44/UC-45 untouched. Hermetic unit tests for the schedule, throttle-not-scaled, training-only; a non-gating pybullet/CPU smoke showing more-upright + climbing under reduced authority. Files: new `train/attitude_curriculum.py`, `env/racing_env.py`, `train/config.py`, `train/loop.py`, README.

## Clarifications
- Q: Which lever should UC-46 use for the attitude tumbling?
  A: Attitude-authority curriculum (reduce roll/pitch/yaw authority early, anneal to full). The inner-loop attitude stabilizer and the attitude-stability reward penalty were explicitly deferred/rejected for this UC so the result is attributable to authority-limiting alone.
