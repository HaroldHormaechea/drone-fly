## Summary
Liftoff renders an on-screen **next-gate pointer** — a small circle/arrow HUD icon that points toward the gate the pilot should fly through next. UC70 run-2 already taught the student to consume a **next-gate pointer observation**: a body-frame unit bearing (3) plus an availability bit (1), appended at the tail of the student observation (`student-obs` schema `VERSION = 3`, `DIM = 61 → 65`; block `("pointer", 4)` in `src/drone_fly/sim/student_obs.py:63`). In the simulator that signal is produced from the truth target centre and corrupted with a HUD-like noise model; **live, it is always `None` → zeros / availability bit 0**, because no live reader exists yet — the learned `TrackingGateEstimator` never populates `info["pointer"]` (`src/drone_fly/harness/student.py:127-130`). Run-2 flown live is therefore degraded to "run-1 + gate-memory + FP-suppression (temporal + memory sub-gates only)" — the pointer OBS gain and the pointer FP-suppression sub-gate are unrealized (`.dev-team/plans/uc-70-run-2.md:60`).

This use case builds that missing live reader using **classic OpenCV image processing only — no AI/ML model**. It detects the fixed HUD pointer icon in the live game frame (template match / colour threshold / contour-shape), reads its screen position/angle relative to the image centre, and converts that into the **same body-frame unit bearing (3) + availability bit (1)** that `est.info["pointer"]` expects. The reader plugs into the existing live assembler path (`build_student_obs(..., pointer=(gate.info or {}).get("pointer"))`, `src/drone_fly/harness/student.py:130`), so the already-trained run-2 student consumes it **unchanged** — no retrain, no obs-schema bump.

It deliberately **mirrors how gates become model inputs today**: the gate detector thresholds/contours the frame, solves a camera-frame pose, rotates it into the body frame via the live attitude and the `CameraModel` (uptilt), and emits it through `est.info` (`src/drone_fly/harness/liftoff/gate_cv.py`). The pointer reader is the lightweight equivalent — a fixed 2-D HUD icon rather than a 3-D gate — so it reuses the project's established camera conventions (horizontal FOV, principal point at image centre, `body_to_camera` uptilt rotation, FLU body frame).

**Calibration deliverable.** The sim pointer-noise parameters are currently *provisional* — `bias_sigma_rad: 0.05`, `jitter_sigma_rad: 0.03`, and `pointer_bearing_tol_deg: 20.0` are flagged "provisional; UC72" in `src/drone_fly/training/configs/student-liftoff-run2.yaml:25-26` and `.dev-team/plans/uc-70-run-2.md:61`. This use case produces the **first real measurements** of the HUD reader's bearing error so those provisional sigmas / tolerance can later be replaced with characterized values (an input to a future run-2 noise re-tune — not part of this use case's happy path, which is detection + conversion + live wiring).

### How gates become model inputs today (the pattern to mirror)
1. **Detect in image.** `OpenCvGateEstimator.detect_quads` (`gate_cv.py`) does HSV threshold over configured ranges → morphology (`MORPH_CLOSE`/`MORPH_OPEN`) → external contours → convex 4-corner quads (area / convexity filters). The learned detector is the alternative `detect()` implementation.
2. **Camera-frame pose.** `solve_pose` runs `solvePnP` (IPPE) of each quad against the nominal gate rectangle, giving `(t_cam, n_cam)` in the camera frame, using intrinsics from the configured horizontal FOV (`camera_from_config`, `gate_cv.py`; `CameraModel.intrinsics` in `src/drone_fly/harness/geometry.py:163` — `fx = (width/2)/tan(hfov/2)`, principal point at image centre `cx,cy`).
3. **Camera → body → world.** `detection_from_pose` (`gate_cv.py`) rotates the camera-frame vector by `CameraModel.body_to_camera()` (the uptilt rotation `R_cb`, `geometry.py:166-171`) and the live attitude `quat_to_matrix(state.quat)`. Body-frame bearing is `R^T (centre − pos)` (see the pointer math below).
4. **Masks.** Before `detect()`, the frame is masked (`FrameMasks.apply`, `src/drone_fly/harness/liftoff/masks.py:89`); detections whose centre pixel falls inside a mask are dropped (`TrackingGateEstimator.detect_frame`). **The HUD region the pointer lives in is exactly a masked region** — see the pitfalls.
5. **Emit via `info`.** The estimate carries extra fields on `GateEstimate.info` (`extra_info()` / the `info` dict assembled in `TrackingGateEstimator.update`); the assembler reads `gate.info` downstream.

### The exact pointer contract the model expects
Single-sourced body-frame unit bearing (3) + availability bit (1), surfaced on `est.info["pointer"]`:
- **Sim truth path** computes it in `GatePerception._pointer` (`src/drone_fly/sim/perception.py:632-650`) and its numpy twin `ReferencePerception._pointer` (`src/drone_fly/student/perception_ref.py:242-256`): `rel_b = R^T (centre − pos)`, normalise to a unit vector, then `az = atan2(rel_b.y, rel_b.x)`, `el = asin(rel_b.z)`, reassemble `[cos(el)cos(az), cos(el)sin(az), sin(el)]`; availability `avail = target_valid AND NOT dropped`; when unavailable the vector is zeroed and the bit is 0.
- **Emitted** as `"pointer": concat(ptr_body(3), [1.0 if avail else 0.0])` — see `perception_ref.py:485-486` and the torch `outputs()` at `src/drone_fly/sim/perception.py:927`.
- **Through `estimate_from_raw`** it lands on `est.info["pointer"]` as `None` or `float32[4]` (`perception_ref.py:527-530`).
- **Obs builder** reads it: torch via `perc["pointer"]` (`student_obs.py:330`), numpy via `est.info["pointer"]` with `pointer`-arg fallback (`src/drone_fly/student/obs_ref.py:78-109`), appended as the `("pointer", 4)` tail block (`student_obs.py:63`; `input_scale` tail `[1.0]*4`, `student_obs.py:104`).
- **Live assembler** passes `pointer=(gate.info or {}).get("pointer")` (`src/drone_fly/harness/student.py:130`) — **this is the single integration seam**: the only thing the new reader must do is make a `TrackingGateEstimator`-shaped live estimate carry a correctly-computed `info["pointer"]` (a `float32[4]`) instead of leaving it `None`.
- **Schema record** (`student_obs.py:164-172`): `pointer.layout = "body-frame unit bearing (3) + availability bit (1)"`, with `source` documented as "sim: noisy truth bearing; live (pre-UC72): learned tracker leaves it unavailable (bit = 0)" — this use case flips the live half of that statement.

## Acceptance Criteria

1. **Classic-OpenCV detector, zero ML dependency.**
   - The pointer reader detects the fixed HUD pointer icon from a single live frame using only classic image processing — template matching, colour thresholding (HSV in-range, as the gate detector does), and/or contour-shape analysis. OpenCV is imported lazily, matching the gate estimator's `_cv2()` pattern (`gate_cv.py`).
   - A test proves **no ML model / neural network / learned weights** are reachable from the pointer reader's code path (no torch, no model file load, no `gate_net`/`gate_learned` import). This is a hard constraint.

2. **Detection precision / recall on captured HUD frames.**
   - On a labelled set of captured Liftoff frames (pointer present vs absent), the detector reports **precision ≥ P and recall ≥ R** for "pointer present and localized to within K px of ground truth" (P, R, K to be fixed during refinement; suggested starting targets: precision ≥ 0.98, recall ≥ 0.95, K ≤ 5 px at the capture reference resolution).
   - The labelled frame set and the evaluation script are checked in (frames themselves may live under the existing capture artifact convention, not the repo, if large).

3. **Bearing accuracy vs known ground truth.**
   - On frames where the true next-gate bearing is reconstructable (telemetry pose + track XML, the UC64/UC70 auto-label machinery), the reader's body-frame unit bearing agrees with ground truth within **N degrees** (N to be fixed during refinement; suggested starting target: median ≤ 3°, p95 ≤ 8°). Report both azimuth and elevation error separately and as a combined angular error.
   - The conversion uses the project's existing camera conventions: screen offset from principal point (`cx,cy`, image centre) → camera-frame ray via the configured horizontal FOV (`CameraModel.fx`), → body frame via `CameraModel.body_to_camera()` (uptilt) and the live attitude, producing the exact `[cos(el)cos(az), cos(el)sin(az), sin(el)]` unit vector the sim contract emits (`perception.py:632-650`). A unit test checks a hand-computed frame (known icon pixel, known attitude) reproduces the expected bearing.

4. **Availability bit degrades gracefully.**
   - When the pointer is **absent, occluded, or being passed through a gate** (Liftoff hides/repositions the pointer at/near a gate), the reader emits availability bit = 0 and a zero bearing — never a stale or hallucinated bearing. This matches the sim contract (`avail = target_valid AND NOT dropped`, zeroed vector when unavailable).
   - A test feeds pointer-absent frames and asserts `info["pointer"] == [0,0,0,0]` (bit 0), and that the student still flies (the run-2 student was trained with per-episode pointer dropout for exactly this regime — `.dev-team/plans/uc-70-run-2.md:19`).

5. **Per-frame latency within the live budget.**
   - The pointer reader's p95 per-frame latency fits inside the live control budget **alongside** the existing gate detector and obs assembly on the target live GPU/host (budget value to be stated during refinement, consistent with the UC70/UC73 live-latency framing). Because it is pure OpenCV on a small fixed HUD region, it should be cheap; this is a guardrail, not a research target.

6. **Parity with the sim pointer contract (student consumes it unchanged).**
   - The live reader populates `est.info["pointer"]` as a `float32[4]` = body unit bearing (3) + bit (1), identical in shape, dtype, frame convention (body FLU), and availability semantics to the sim/`ReferencePerception` output. No change to `student-obs` schema (`VERSION` stays 3, `DIM` stays 65), no change to `build_student_obs`, no retrain of the run-2 student.
   - An integration test runs the live assembler path (`harness/student.py`) with a reader-produced estimate and asserts the `("pointer", 4)` obs tail block is populated (non-zero when the pointer is present) and that an identical frame with no pointer yields the degraded zeros/bit-0 block.

7. **HUD-mask interaction handled explicitly.**
   - The pointer lives inside the HUD/OSD region that the gate detector **masks out** (`FrameMasks`, `masks.py`; gate detections centred in a mask are dropped — `gate_cv.detect_frame`). The pointer reader must read the **unmasked** frame for the pointer's region (or a dedicated pointer ROI) while the gate detector continues to mask it. A test/doc shows the two consumers do not fight: the pointer region feeds the pointer reader, and is still excluded from gate detection.

8. **Live validation in Liftoff.**
   - The reader is exercised live on at least one track, and a short report shows the pointer bearing is populated and plausible across a lap (e.g. overlaid on the UC65 live debug overlay), with the availability bit dropping to 0 at gate passes as expected.

9. **Calibration output for a future noise re-tune.**
   - The measured bearing-error statistics from AC3 are written to a small report (bias, per-tick jitter std, availability/false-positive rates), framed so they can **replace the provisional** `bias_sigma_rad` / `jitter_sigma_rad` / `pointer_bearing_tol_deg` defaults (`student-liftoff-run2.yaml:25-26`, `.dev-team/plans/uc-70-run-2.md:61`). Re-running run-2 training with the real values is explicitly **out of scope** here (it is a downstream experiment), but the numbers are produced.

## Potential Pitfalls & Open Questions
- **HUD-mask interaction (primary).** The pointer sits in the masked HUD region. The reader must deliberately read the pointer's ROI from the *unmasked* frame while gate detection keeps masking it. Decide whether the pointer ROI is a new config field (like `camera.masks` rects) or derived from the HUD mask geometry. Resolution/layout-specific, exactly like masks (`masks.py:3-5`, "one set per resolution + HUD configuration").
- **Icon variants / scale / colour.** The pointer icon may differ across Liftoff versions, map themes, colour schemes, or HUD scale settings. Template matching is brittle to scale/colour; colour-threshold + shape may generalize better but risks false matches. Open question: multi-scale template bank vs shape/contour descriptor vs a hybrid. Must be validated across the maps/themes in the capture set (mirrors UC71's multi-map generalization concern).
- **Pointer absent / repositioned near or at a gate.** Liftoff typically hides or snaps the pointer when you are at/through the current gate; this must map cleanly to availability bit 0 (AC4) rather than a spurious detection. The exact Liftoff behaviour at gate passes needs to be characterized from captures.
- **False matches vs other HUD elements.** Lap timer, speed/altitude readouts, stick widgets, ghost/lap lists, battery and other OSD glyphs share the HUD region and may trigger template/colour false positives. Needs an explicit reject strategy (ROI restriction, shape constraints, uniqueness of best match).
- **Resolution / DPI dependence.** All screen geometry is resolution-specific (gate masks reference `camera.resolution`, scaled per frame — `masks.py:68-80`; UC72 notes positions measured on a 2560×1080 reference). The pointer ROI, template scale, and pixel→angle conversion must scale with capture resolution the same way (`CameraModel.scaled_to`, `geometry.py:200`).
- **Screen-position/angle → bearing model.** The HUD pointer encodes a *direction*, but is it a simple 2-D screen-space arrow (angle on screen) or a 3-D-projected marker? If it is a screen-edge/clamped indicator when the gate is off-frame, the pixel→camera-ray model (principal point + FOV) may not hold at the clamp. Need to characterize whether the icon's position is a faithful projection of the gate direction or a clamped/eased indicator — this bounds achievable bearing accuracy (AC3).
- **Sim ↔ live calibration gap.** The run-2 sim noise (`bias_sigma_rad=0.05`, `jitter_sigma_rad=0.03`, `bearing_tol_deg=20`) is provisional (`student-liftoff-run2.yaml:25-26`). Until replaced by this reader's measured characteristics (AC9), there may be a sim-to-live mismatch in how the student weighs the pointer. Replacing them is a downstream run-2 re-tune, not this use case.
- **Capture latency vs budget.** Screen capture (`frames.py`: dxcam on Windows else mss) and the extra OpenCV pass add latency on top of the gate detector; must stay within the live budget together (AC5). Reusing the already-captured frame (not a second grab) is important.
- **This unblocks the degraded run-2 live.** Today a run-2 student live is "run-1 + gate-memory + FP-suppression (temporal + memory sub-gates only)" — the pointer OBS gain and the pointer FP-suppression sub-gate are dead (`.dev-team/plans/uc-70-run-2.md:60`). This reader turns both on live. Open question: does enabling `fp_suppress_pointer` live (which consumes the same `ptr_body`) need any guard when the live bearing is noisier than the sim noise model assumed?
- **Windows-only live path.** The live harness / screen capture is Windows-oriented (`frames.py`, the `liftoff-episodes` skill). Capturing the labelled frame set and live validation run on Windows; the pure-OpenCV conversion logic itself is platform-neutral and unit-testable anywhere.
- **Stale "UC72" references in code.** On completion, update the "UC72 adds the live HUD reader" comments (`harness/student.py:129`, `student_obs.py:171`, `obs_ref.py:88`, `student-liftoff-run2.yaml:8,19`) to this use case's assigned number.

## Original Description
> Liftoff (the drone sim) renders an on-screen "point guide" / next-gate pointer — a small circle/arrow HUD icon pointing toward the next gate. We want to DETECT that pointer from the live game frame and convert it into a pointer-to-target bearing for the model — the SAME signal the UC70 run-2 student already consumes (currently None/unavailable in live flight because no live reader exists yet). Crucially this should NOT need an AI/ML model — just classic OpenCV image processing (template/shape/colour detection of the fixed HUD icon) + coordinate conversion (screen position/angle → body-frame unit bearing), mirroring how GATES are turned into model inputs today.

## Clarifications
- Q: Should the reader use any ML/learned model?
  A: No. Classic OpenCV only (template match / colour threshold / contour shape) + coordinate conversion. A learned HUD reader is explicitly out of scope.
- Q: Does the student need retraining to use the live pointer?
  A: No. The run-2 student already consumes the `("pointer", 4)` obs block; this reader only fills the live `info["pointer"]` the assembler already reads. Schema `VERSION`/`DIM` are unchanged.
- Q: What exactly must the reader output?
  A: A body-frame unit bearing (3) + availability bit (1) as `float32[4]` on `est.info["pointer"]`, byte-compatible with the sim/`ReferencePerception` contract (`perception.py:632-650`, `perception_ref.py:242-256`, `student_obs.py:63`).
- Q: Is re-tuning the run-2 noise sigmas part of this?
  A: No — this use case *measures* the real HUD-reader error (AC9) so a later run-2 re-tune can replace the provisional sigmas/tolerance, but running that experiment is downstream.
