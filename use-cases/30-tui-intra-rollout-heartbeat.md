# Use Case 30: Live training TUI must tick during a rollout (intra-rollout heartbeat)

## Summary
The UC-22 live training TUI shows nothing during training — all metrics 0/flat and even the elapsed clock stuck at 0 — whenever a rollout is slow (the user hit this on a 122,816-neuron slice, but it reproduces any time the first rollout takes a while). Training is actually running (with `--no-tui` the logs flow and recordings are written; `progress.csv` is empty only because no PPO iteration has completed yet). Verified root cause (read + an empirical render test in the root session): `TuiCallback` (`src/drone_fly/train/tui/callback.py`) pushes a dashboard update and calls `dashboard.redraw()` **only** in `_on_rollout_end` — once per completed rollout; `_on_step` just `return True`, and `elapsed_seconds` is computed only inside `_on_rollout_end`. Rich `Live` (`dashboard.py`, `refresh_per_second=4`) only re-renders the renderable that `redraw()` last built, so it stays pinned to the initial all-zero `DashboardModel` for the entire first rollout. The empirical test confirmed the metrics/render layer *does* update correctly when `model.update(...)` + a rebuild are called (elapsed→42, success→50% appeared) — the only gap is that the callback never feeds it until a rollout ends. This is **not** a deadlock (the `FdLogCapture` drains on a daemon thread), not the subproc backend, not the capture. This UC adds an **intra-rollout heartbeat**: on a throttled `_on_step` (time-gated, ~4×/sec), tick the live elapsed clock, a within-rollout step-progress indicator (steps collected this rollout vs `n_steps × n_envs`), and refresh the log pane — so the dashboard is visibly alive during collection, not only at rollout boundaries. The existing `_on_rollout_end` full snapshot is preserved unchanged; rollout-only metrics stay placeholders until the first rollout completes. Scope is the TUI callback/model/render only; no change to training dynamics, observation schema, connectome, reward, or checkpoints.

## Acceptance Criteria
1. **Live during collection:** before any `_on_rollout_end` fires, driving `TuiCallback._on_step` on a stub model makes the `DashboardModel` (and rendered output) show a **non-zero elapsed time** and a **within-rollout step-progress** value, with zero completed rollouts. (A slow first rollout is no longer a blank/zero screen.)
2. **Throttled:** many rapid `_on_step` calls trigger at most ~N redraws/second (time-gated, e.g. asserted via an injectable/fake clock), so per-step overhead is negligible and fast slices are unaffected.
3. **Rollout step-progress correct:** progress = steps collected in the current rollout vs the rollout target `n_steps × n_envs`; it resets at each `_on_rollout_start` and reads the resolved `n_envs`/`n_steps` correctly.
4. **Rollout-end snapshot unchanged (regression):** `_on_rollout_end` still pushes the full metric snapshot (ep_rew_mean / ep_len_mean / success_rate / entropy / std / value_loss / approx_kl / explained_variance + n_updates + elapsed) exactly as before; rollout-only metrics remain placeholders (not fabricated 0s) until the first rollout completes.
5. **Defensive:** an exception in the heartbeat disables it and logs, never crashing training (mirrors the existing `_enabled` guard); the `--no-tui` path is unchanged.
6. **Log pane live:** captured log lines appear in the dashboard during collection (before the first rollout end), via the heartbeat's redraw refreshing `_log_lines()`.
7. **Scope + CI:** no change to training dynamics, observation schema/width, connectome graph, reward, or checkpoints; UC-22 (7 trend rows, iterations-vs-scheduled progress), UC-23 (health status bar), and UC-26 (AC-11 n_envs/backend display) behavior preserved; full suite (`ruff check .`, `ruff format --check .`, `uv run pytest`) green + offline; viewer untouched (no `node --check` impact).

## Potential Pitfalls & Open Questions
- **Edge case (throttle clock in tests):** the time gate must be testable deterministically — inject the clock (or a monotonic source) so tests assert the redraw-count bound without real sleeps.
- **Edge case (rollout step count source):** derive current-rollout steps from `self.num_timesteps - rollout_start_timesteps` (captured at `_on_rollout_start`) or an equivalent per-rollout counter; ensure it reads the true `n_steps`/`n_envs` (resolved values) for the target.
- **Assumption (Live auto-refresh):** Rich `Live` re-renders the last-built renderable; the heartbeat must call the dashboard's `redraw()` (rebuild) — not rely on Live auto-refresh — for new values to appear. Tests target the pure model/render + a synthetic callback harness, not a live Rich `Live`.
- **Risk (overhead):** without the time gate, per-step redraws would slow fast rollouts; the throttle is mandatory and covered by AC-2.
