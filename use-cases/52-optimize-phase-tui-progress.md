# Use Case 52: Optimize-phase progress + collect/optimize timing in the training TUI

## Summary
The live training TUI shows an `iterations` bar and a `collecting X/Y` rollout bar, both driven by SB3 callback hooks that fire **only during rollout collection**. PPO's optimize phase — `PPO.train()`'s `n_epochs × minibatch` gradient loop — has no SB3 callback hook, and the redraw runs on the same thread that is blocked inside that loop, so during optimize the screen is frozen at `collecting 100%`. On the ~25,627-neuron connectome actor with `n_epochs=10`, the optimize phase is the **majority of each iteration's wall-clock**, so most of every iteration is currently invisible. This use case adds an `optimizing epoch e/N · minibatch m/M (X%)` progress bar plus a per-iteration collect-vs-optimize wall-clock split, using a minimal `ProgressReportingPPO(PPO)` subclass that instruments the optimize loop via a **counting-proxy over `rollout_buffer.get()`** (no duplication of the gradient/loss math). The instrumentation is inert when no dashboard sink is attached (headless / `--no-tui` / smoke / resume-before-attach), so those paths stay byte-identical to plain PPO. The optimize redraw is throttled to **~1 update/second** (a dedicated interval separate from the 4 Hz collection heartbeat) to keep overhead negligible. Scope is train-orchestration + TUI only; no reward/env/adapter/policy/connectome math is touched. This is an observability feature — no training-behavior change on any existing path.

## Acceptance Criteria
1. During the PPO optimize phase the TUI renders an `optimizing epoch e/N · minibatch m/M (X%)` progress bar (immediately below the existing `collecting` bar), updating while `train()` runs — the region that is currently frozen. Cumulative fraction = `(epoch*M + minibatch) / (N*M)`.
2. A per-iteration **collect-vs-optimize wall-clock split** is shown in the TIME column (e.g. `split c 12s · o 46s (79%)`), where collect duration is measured between `_on_rollout_start` and `_on_rollout_end`, and optimize duration across `train()`.
3. The optimize-phase redraw is throttled to **~1 update per second** via a dedicated module constant (e.g. `_OPTIMIZE_MIN_INTERVAL = 1.0`), **distinct** from the collection heartbeat's `_HEARTBEAT_MIN_INTERVAL` (which is unchanged). `begin_optimize`/`end_optimize` redraw immediately so phase transitions and the first tick are not delayed.
4. When no dashboard sink is attached (TUI off / `--no-tui` / `smoke_train` / resume-before-attach), `ProgressReportingPPO.train()` is **byte-identical** to plain `PPO.train()` — no wrapping, no behavior change, zero overhead. The AC-9 "byte-identical on unix" invariant is preserved.
5. Progress is derived by temporarily wrapping `rollout_buffer.get(batch_size)` with a counting-proxy generator for the duration of `super().train()`; the gradient/loss/optimizer loop is **not** copied or modified. Training math is never altered.
6. Robustness: any anomaly (observed epoch count ≠ `n_epochs` beyond a tolerated `target_kl` early-stop, or an unexpected buffer/get shape) disables the instrumentation and falls through to `super().train()` — it must never crash or perturb training. The `rollout_buffer.get` wrap is always restored in a `finally`.
7. The minibatch denominator is `M = ceil(n_steps * n_envs / batch_size)` (handles the partial final minibatch); the rendered `m/M` text is clamped with `min(cur, total)` so a divergent buffer shape can never render e.g. `33/32`.
8. `ProgressReportingPPO` is used on both the fresh (`PPO(...)`) and resume (`PPO.load(...)`) construction paths in `loop.py`; the dashboard sink is attached only when the TUI is active, after construction/load.
9. All redraw paths go through the dashboard's existing single `RLock` — no new thread is introduced. (On Windows, the existing ~1 Hz timer and the train-thread optimize ticks are both serialized by that lock.)
10. Tests are hermetic (no GPU/pybullet): (a) model→text render assertions for the optimizing bar and the split line across synthetic begin/tick/end sequences (0%, mid, 100%, pre-first-tick placeholder); (b) the counting-proxy as a pure helper tested with fake iterables + a recording sink (asserts N×M ticks with correct indices, one begin/one end); (c) a `smoke_train` (numpy backend, CPU, 256 steps — already CI-hermetic) with a recording sink proving `train()` emits `begin_optimize → tick_optimize(≥1) → end_optimize` with correct counts; (d) the 1 Hz throttle tested via the dashboard's injectable clock; (e) an unattached-sink byte-identity check.
11. Scope is confined to: NEW `src/drone_fly/train/progress_ppo.py`, `src/drone_fly/train/loop.py`, `src/drone_fly/train/tui/metrics.py`, `src/drone_fly/train/tui/dashboard.py`, `src/drone_fly/train/tui/render.py`, `src/drone_fly/train/tui/callback.py`, and tests. No changes to `reward.py`, `racing_env.py`, adapters, env, or policy/connectome math. README/docs updated only if user-visible TUI behavior needs describing.

## Potential Pitfalls & Open Questions
- **Throttle discipline (from prior design review):** the ~1 s redraw gate must live in `dashboard.tick_optimize` as new state (`_last_optimize_redraw`), reusing the dashboard's injectable `self._now` for hermetic tests; the counter mutation is unconditional/cheap, only the Rich rebuild is gated. `begin_optimize`/`end_optimize` reset the gate.
- **Non-clobber contract:** `begin/tick/end_optimize` must leave `raw`/`history` untouched (mirroring `tick()`), so the last rollout-end snapshot persists in the values panel during optimize.
- **Redraw overhead:** at 1 Hz on the train thread the added cost is ~0.25–0.75% of optimize wall-clock; `backward()`/`optimizer.step()` release the GIL. Overhead is zero on the unattached/headless path (AC-4).
- **SB3 drift:** bounded by the hard `stable_baselines3==2.9.0` pin; the counting-proxy reads only the stable "one `get()` per epoch" contract, never the loss math, plus disable-on-anomaly (AC-6).
- **Layout:** the TIME/values panel gains one line (split), so its Layout region size likely bumps by one (as a prior UC did for the steps line); the trends panel is flexible and needs no size change.

## Original Description
Add optimize-phase progress reporting to the training TUI. Today the TUI shows a `collecting X/Y` rollout bar and an `iterations` bar, but nothing during PPO's optimize phase (`PPO.train()` — the n_epochs × minibatch gradient loop), which has no SB3 callback hook and runs on the same thread as the redraw. The user confirmed the optimize phase takes the MAJORITY of each iteration's wall-clock (25.6k-neuron connectome actor × n_epochs backprop), so most of every iteration is invisible/frozen at `collecting 100%`. Add an `optimizing epoch/minibatch (%)` bar plus a per-iteration collect-vs-optimize wall-clock timing split. This was analyzed design-first by the dev-team (analysis-only run, challenger-approved against the installed SB3 2.9.0 source): the recommended approach is a minimal `ProgressReportingPPO(PPO)` subclass that instruments the optimize loop via a counting-proxy over `rollout_buffer.get()` (zero duplication of the gradient math), with an optional inert sink so headless/smoke/resume stay byte-identical, all redraws through the existing dashboard RLock (no new thread), and hermetic tests. Scope: train-orchestration + TUI only.

## Clarifications
- Q: What redraw cadence during optimize (given the ~1–3% overhead at 4 Hz)?
  A: Aim for **1 update per second** (1 Hz) — dedicated throttle constant, separate from the collection heartbeat, keeping overhead ~0.25–0.75%.
- Q: Which approach for instrumenting the hook-less `train()`?
  A: The challenger-approved **counting-proxy PPO subclass** (wrap `rollout_buffer.get()`), NOT copying SB3's `train()` body and NOT a cross-platform render thread.
