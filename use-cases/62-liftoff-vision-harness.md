# Use Case 62: Pluggable live-harness framework + vision-driven Liftoff harness

## Summary
Add a new `harness` package that runs an already-trained K1 flight model against an external, real-time flight system instead of the training simulator, built strictly against the frozen inference contract (`docs/INFERENCE_CONTRACT.md` + `gpu_prototype/inference.py`) and treating `gpu_prototype/`, `training/` and all training code/config as read-only. A harness is composed of separately-owned parts: a **state source** (telemetry → proprioception), a **frame source** (screen capture), a **perception stack** of pluggable estimators that turn frames (+ current state) into the contract's gate/obstacle senses, an **observation assembler** that builds the 12-dim core obs plus the `extra` vector at the checkpoint's `extra_dim` (12/30/70), and an **action sink** that converts the contract's raw `[collective, wx, wy, wz]` into the target's native input. A runner loads the model, runs a fixed 50 Hz perceive → assemble → act → actuate loop on wall-clock time, records everything, and fails safe. Harnesses are name-registered and YAML-configured so new targets only add implementations. First concrete harnesses: **Liftoff (5-inch FPV, configurable per game/airframe)** — UDP telemetry (~100 Hz), screen capture → an **OpenCV gate detector** (PnP against a configured nominal gate size → `rel`, `curr_gate`, `next_lookahead`) and a **monocular depth network** (first implementation of a pluggable free-space estimator → `obstacle_vision` and the 40-ray `raycast`, sampling metric depth along the contract's velocity-aligned 90° cone projected into the camera), output via a **ViGEm virtual Xbox 360 pad (`vgamepad`)**; and a **sim-loopback** harness driving the contract's reference `plant_step` through the same interfaces to prove the harness reproduces the reference inference path. The acceptance target model is the **70-dim obstacle-avoid model** (`training/10-proc-obstacle-avoid`), so vision-derived raycast is on the critical path. Liftoff track/race XMLs are **never** used at runtime — only offline, as ground truth to score and calibrate the vision estimators against recorded flights.

## Acceptance Criteria
1. `src/drone_fly/harness/` defines abstract `StateSource`, `FrameSource`, `GateEstimator`, `FreeSpaceEstimator` (→ `obstacle_vision` + `raycast`), `ObservationAssembler`, `ActionSink`, `PolicyRunner`, and `Harness` interfaces plus a name-based registry. Backend deps (OpenCV, screen capture, depth model, `vgamepad`, torch/K1) are lazily imported with actionable errors; the hermetic CI path still imports without them.
2. The harness loads K1 checkpoints exactly per the inference contract (`load_policy(path, extra_dim)`, `strict=False`, only `body.layer.*` missing) **without modifying** `gpu_prototype/`, `training/`, `docs/INFERENCE_CONTRACT.md`, or any training code/config. A test asserts the harness's action mapping matches the contract (linear-clamp collective, `tanh·MAX_BODY_RATE`).
3. The assembler produces the contract layout bit-exactly given the same inputs: `obs(12) = [rel, g_body, vel, omega]`; `extra = obs ‖ curr_gate(3) ‖ next_lookahead(7) ‖ obstacle_vision(8) ‖ raycast(40)` truncated to the model's `extra_dim`. The runner refuses to start (naming the missing blocks) if the configured perception cannot fill the blocks the model needs.
4. **Sim-loopback parity:** with ground-truth estimators (gate/obstacle geometry from a test course; rays from the contract's `raycast()`), the harness's per-step obs/extra/actions match `inference.py`'s reference loop within float tolerance for a fixed model and seed.
5. **Liftoff state source:** a UDP listener parses the Liftoff telemetry fields (`t`, position, xyzw quaternion, velocity, gyro pitch/roll/yaw, stick inputs, battery, RPMs) into a typed record; a frame converter maps Unity left-handed Y-up into the contract's Z-up world frame and yields `g_body`, `vel`, body-frame `omega`. Unit-tested against fixtures cut from the existing recorded Liftoff telemetry CSVs — no live game in CI.
6. **Gate estimator (OpenCV, first implementation):** detects the current and next gate in a frame and estimates their camera-relative pose using configurable camera FOV, uptilt and nominal gate dimensions; converts to world-frame `rel`, `curr_gate` (cos/sin yaw, aperture) and `next_lookahead` (bearing, orientation, distance, `vis` flag when the next gate is not seen). Advances the gate on a detected pass; holds the last estimate for a configurable timeout when the gate is lost, then triggers the fail-safe.
7. **Free-space estimator (monocular depth net, first implementation behind the pluggable interface):** runs a configurable depth model with metric-scale calibration on its own thread (latest-frame-wins); projects the contract's 40-ray velocity-aligned cone (target-direction fallback below 0.3 m/s, as in the contract) into the camera image and returns normalized free-space distance (≤ `RAY_RANGE`, scaled by config) plus the nearest-2 `obstacle_vision`. Rays outside the camera FOV use a documented, configured fill policy.
8. **Offline evaluation tool:** given a recorded session (frames + telemetry) and the matching Liftoff track/race XML, reports gate-estimator error (position, yaw) and free-space-estimator error against XML-derived ground truth (ground-truth raycast via the contract's `raycast()`). XMLs are accessed **only** by this tool and its tests, never by the runtime.
9. **Action sink (ViGEm via `vgamepad`):** maps collective and body rates to virtual-pad axes through a configurable inverse of the Liftoff rate profile (rc rate / super rate / expo) and a configurable throttle mapping, so a commanded body rate yields the intended deg/s. Unit-tested with a mocked pad.
10. **Runner:** 50 Hz loop by default (configurable); logs per-tick latency (state, perception, inference, actuation), perception estimate age, and missed deadlines. **Fail-safe:** on stale telemetry, gate lost past timeout, a perception/sink exception, or a user abort hotkey → neutral rates + throttle cut. Tested with fakes.
11. **Recording:** each run writes raw telemetry, sampled frames (or frame metadata), estimator outputs, obs/extra vectors and actions under a per-run folder in `artifacts/` (never under `training/`).
12. **CLI (new):** `src/drone_fly/cli/` and the `[project.scripts]` entries were removed in cc817f4, so the harness adds its own fresh entry point (new console script) — do not assume prior CLI scaffolding or the deleted `configs/` dir. Commands: `drone-fly harness list` and `drone-fly harness run --harness liftoff --checkpoint … --extra-dim 70 --config <yaml>`. Per-game/airframe settings (telemetry port, FOV, uptilt, nominal gate size, rate profile, world-scale factor) live in YAML; a Liftoff 5-inch config ships as the default, and the game/airframe is switchable by config.
13. Adding a new harness or estimator = implement the interface + register it, with no runner edits. An ADR/doc records the layering with Liftoff as the worked example.
14. Existing tests (the 22 test modules kept after cc817f4) stay green; ruff passes. New harness deps (OpenCV, screen capture, depth model, `vgamepad`) are added as an optional extra in `pyproject.toml`, not to the core dependencies.
15. **Delivery order (staged, each stage green before the next):** (a) sim-loopback parity (AC4) against the reference `plant_step`; (b) Liftoff obstacle-free waypoint flight path wired end-to-end (state source, gate estimator, action sink, runner) usable with the 30-dim model; (c) the depth-net free-space estimator + raycast reconstruction (AC7) enabling the 70-dim model. The 70-dim model remains the acceptance target.

## Potential Pitfalls & Open Questions
- **Risk** — Scale/plant mismatch (dominant risk, bigger than "warm start"; confirmed by the training agent). Models were trained on a 32 g whoop plant (T/W 2.5, 4 rad/s max rate, 4 m ray range, small courses); a 5-inch Liftoff quad has T/W > 8, much higher rates and larger gates. The world-scale factor and rate/throttle scaling are configurable, but this is a warm-start, not a guaranteed zero-shot flight. Flight success in Liftoff is not an acceptance criterion; correct, contract-exact I/O and measured perception accuracy are.
- **Risk** — Latency. Depth net + OpenCV per tick on an RTX 3050 while Liftoff renders may not sustain 50 Hz; perception runs async and the runner tolerates estimate age, but real performance needs live calibration.
- **Risk** — Ray coverage. The contract's cone is velocity-aligned, not camera-aligned; with high camera uptilt / fast forward flight part of the 90° cone may fall outside the image (hence the configured fill policy).
- **Edge case** — Crashes / respawns / menus / pause: detect via telemetry discontinuities (position jump, `t` reset) and optionally by tailing Unity `Player.log` ("Enabling controller mapping: Flight/Menu"); re-sync gate tracking.
- **Missing input** — Exact Liftoff telemetry configuration (port, enabled fields) and the owner's rate profile for the chosen airframe; defaults will be documented and assumed.
- **Risk** — Raycast reconstruction from monocular depth (AC7) is the single biggest perception task.
- **Assumption** — The harness imports `gpu_prototype/inference.py` and the K1 classes in place (read-only) via a configured path; if the other agent changes the contract, the parity test is what detects drift.
- **Risk** — Concurrent work: another agent is actively changing the training regime on `main`. Implementation must happen on a separate branch / isolated worktree and must not touch training code, configs, `gpu_prototype/`, `training/`, or training artifacts.

## Clarifications
- Q: Constraints on concurrent work?
  A: Another agent is working on the project doing and uploading trainings and tweaking the training regime — this work MUST NOT touch that. Work happens in a branch.
- Q: Where does gate information come from at runtime — the exported Liftoff track/race files?
  A: No. The model must NOT base itself on the map files; it must visually process the screen in real time. Track files are not acceptable at runtime for now.
- Q: Can the track/race XMLs be used offline only, as ground truth to measure/calibrate the vision estimator against recorded flights?
  A: Yes, offline eval only.
- Q: How should the harness drive Liftoff's controls on Windows?
  A: ViGEm via `vgamepad` (emulated Xbox 360 controller).
- Q: Include a sim-loopback harness with a parity test?
  A: Yes.
- Q: How should vision feed the policy / is there a raycast input?
  A: There is a raycast input (set up by the other agent): the 70-dim obstacle models consume a 40-ray forward-cone free-space scan (reference `raycast()` in `gpu_prototype/inference.py`, commit d5947e1); full extra layout `[obs(12) ‖ curr_gate(3) ‖ next_lookahead(7) ‖ obstacle_vision(8) ‖ raycast(40)]`. Zeroing raycast blinds an obstacle model.
- Q: Which model(s) must the Liftoff harness fly in this use case?
  A: The 70-dim obstacle model.
- Q: How should the 40-ray free-space scan be derived from the screen?
  A: Pluggable, but the first implementation is a monocular depth network.
- Q: How should gates be detected on screen?
  A: OpenCV first, behind a pluggable interface.
- Q: Which game is the target?
  A: Configurable, starting with Liftoff (5-inch FPV), which has much easier tracks.
- Q: Sync notes from the training agent (cc817f4)?
  A: Branch from latest main (cc817f4, includes d5947e1 `raycast()`); never reimplement the raycast — reuse the validated reference. `src/drone_fly/cli/`, `[project.scripts]` and `configs/` were deleted (build a fresh CLI); stable-baselines3/gymnasium/pybullet dropped from deps (sim-loopback uses the reference `plant_step`, not pybullet); "existing tests" = the 22 kept tests. 12/30/70 extra layouts are clean prefixes. Sequence: loopback parity first, then obstacle-free waypoint flight, then the depth/raycast estimator.
