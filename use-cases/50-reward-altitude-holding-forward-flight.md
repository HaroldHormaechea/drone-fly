# Use Case 50: Reward altitude-holding forward flight — stop trading height for gate-progress

## Summary
The post-UC-48 policy (physics confirmed healthy — T/W 2.25 via UC-49 telemetry) shows emerging gate-directed motion but never sustains altitude: it rushes the target horizontally and sinks to the ground, doing *either* climb *or* advance, never both together, and crashes. The cause is a reward-gradient conflict grounded in the real weights: the dense progress term (`progress_weight = 1.0` per metre) is driven by **3D** Euclidean distance to the current target, so the drone earns the dominant dense reward by closing on the gate in *any* direction — including while descending — whereas holding altitude pays almost nothing (`airborne_bonus = 0.2`/step graded only up to `climb_target_height = 1.0`; the UC-39/42/43 climb and ground-break terms are potential-based and telescoping, rewarding altitude *change* and netting ≈0 for level flight). The cheapest dense reward is therefore "rush the gate horizontally and sink" → floor `collision_penalty = 100` (vs `completion_bonus = 200`), whose per-episode variance destabilized the PPO critic (health-callback CRITICAL value_loss divergence, later self-recovered). This use case makes **level, altitude-holding forward flight** the rewarded path: forward progress must not be net-positive while sacrificing altitude below a safe band, and holding a safe altitude must be actively rewarded (sinking penalized before it becomes a crash). The safe-altitude reference **tracks the current target gate's z** (each gate carries its own centre z; gates vary in altitude). The change is confined to the reward function and its config, preserving the existing non-farmable, potential-based, default-off-byte-compatible design. The concrete mechanism — altitude-gating the progress term, an additive altitude-error/sink-rate term, or a combination — is left to the analyst/challenger to choose against the real code (diagnose-first, per the UC-40/UC-47 precedent).

## Acceptance Criteria
1. **Progress is not earnable while sinking below the safe band.** In a `compute_reward` unit test, a step that closes horizontal distance to the current target but descends so the drone is below the safe band (referenced to the target gate's z) nets **≤ 0** from the combined progress + altitude terms.
2. **Level beats descending for equal horizontal progress.** For two steps with identical horizontal closing distance, the trajectory that holds altitude within the safe band nets **strictly higher** reward than the one that loses altitude.
3. **Safe altitude tracks the target gate's z.** The safe band / altitude-hold reference is derived from the current target gate's centre altitude (not a hardcoded global constant); a test with two gates at different z shows the reference shifting with the active target.
4. **Non-farmability preserved.** Any new altitude/vertical shaping keeps the telescoping, non-farmable property: a climb-then-descend or bob round trip nets ≈0, no loiter/hover-forever optimum is introduced, and the per-episode altitude-term total remains ≪ `completion_bonus`.
5. **Takeoff still bootstraps.** The change interoperates with the UC-43 sub-threshold ground-break term so a fresh policy can still leave the floor — it must not create a new chicken-and-egg where progress is ungated but unreachable until airborne and altitude reward is unreachable until moving.
6. **Additive & byte-compatible defaults.** New reward weights are additive and config-gated; with the new terms at their default (off / zero) values, `compute_reward` is byte-identical to the pre-change function for every existing caller (a regression test pins this).
7. **Scope containment.** Only `src/drone_fly/env/reward.py` and `src/drone_fly/env/config.py` (`RewardConfig`) change. The simple and pybullet adapters, the UC-48 T/W fix, the UC-44 spawn/airborne curriculum, the UC-46 attitude-authority curriculum, PPO hyperparameters, and episode-termination logic are unchanged.
8. **Hermetic validation.** All new tests exercise `compute_reward` directly — no pybullet, no GPU. Because reward feeds VecNormalize, assertions are **relative/structural** (orderings, signs, round-trip nets), never absolute-margin (the UC-42 lesson).
9. **CI green + docs.** `ruff check` + `ruff format --check` + `pytest` pass; the README reward-section table is updated for every new/changed reward term (standing project rule).

## Potential Pitfalls & Open Questions
- **Assumption** — "safe band" is centred on the target gate's z with a symmetric margin; the exact margin and whether the band is one-sided (penalize only *below*) vs two-sided (also discourage overshoot above) is an implementation choice for the dev-team, bounded by AC-1/AC-2.
- **Risk** — over-penalizing sink could make the drone too conservative (hover, never advance). The altitude and progress weights must be balanced so forward flight *within* the band is still net-positive; AC-2 guards the ordering but not the absolute pull.
- **Risk** — gating the progress term on altitude can re-introduce a takeoff chicken-and-egg; AC-5 makes interoperation with the UC-43 ground-break bootstrap mandatory.
- **Edge case** — the final gate → finish leg: the "target" becomes the finish plane after all gates pass; the safe-altitude reference must resolve sensibly for the finish target too (e.g. reuse the last gate's z or the finish z).
- **Edge case** — gates near the floor or ceiling: a gate whose z sits inside the floor band or near the ceiling could make the safe band degenerate; clamp to the flyable range.
- **Assumption** — vertical velocity / sink rate, if used, is available to `compute_reward` from the height-prev/height-curr already passed in (Δh per step); no new adapter plumbing is assumed.
- **Risk (out of scope, noted)** — the PPO critic instability is being addressed indirectly (fewer crashes → lower return variance). If the critic still diverges after this change, a separate stability use case (curriculum pacing / value-clipping / collision-penalty scale) is the follow-up — deliberately **not** in this use case for clean attribution.
- **Deferred** — the behavioral verdict (does it now hold altitude and fly the course) requires a fresh GPU retrain; hermetic tests can only encode the reward *property*. Checkpoints from the current run are invalidated by any reward change.
