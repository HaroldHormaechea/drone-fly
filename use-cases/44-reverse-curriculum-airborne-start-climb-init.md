# Use Case 44: Airborne-start reverse curriculum + climb-biased throttle init (learn to fly by removing the takeoff-discovery problem)

## Summary
Seven consecutive reward-shaping use cases (UC-37 through UC-43) produced **zero** altitude movement: on a 565k-step run the drone sits at z ≈ 0.0135 m from episode 50 through episode 900, with `ep_rew_mean` glued to exactly −5 (the pure time-penalty floor) and `success_rate` 0%. The bottleneck is therefore **not** the reward shape — our reward-math unit tests correctly verify the gradient is well-formed — but that PPO's policy never outputs sustained above-hover throttle, so the drone never enters the airborne region every one of our shaping terms targets. A correctly-shaped gradient the policy never experiences cannot teach anything. This use case stops tweaking reward magnitude and attacks the *discovery* problem directly with two composed levers. **Lever 1 — airborne-start reverse curriculum (training-time only):** instead of always spawning on the floor (UC-37 forces spawn z → `floor_z` at `racing_env.py:277`), spawn the drone at an initial altitude that begins at/near `climb_target_height` early in training and anneals toward `floor_z` as training progresses (keyed on training-progress fraction). Early on the policy experiences the rewarded airborne region from step 0 and only has to learn to **maintain** altitude — a far easier problem than discovering takeoff — and as the spawn anneals to the floor the policy must learn takeoff itself, now bootstrapped from a hover-competent policy. **Lever 2 — climb-biased throttle init (fresh-build only):** extend UC-40's hover-bias so `action_net.bias[THROTTLE_INDEX]` is initialized to a new `CLIMB_BIAS_THROTTLE` slightly above `HOVER_THROTTLE` (candidate 0.6), so a fresh policy's default action produces gentle net-positive lift and collects airborne/climb reward immediately, compounding with the reverse curriculum. Crucially, eval and recording continue to spawn on the floor (consistent with UC-36 eval/recording semantics) so we still measure **true** takeoff, and the curriculum changes only the spawn state — not the reward function — so all UC-37/38/39/42/43 reward invariants and doc-contract tests remain green. Temporally-correlated (OU/pink-noise) exploration is deliberately **out of scope** here and deferred to a later use case so the effect of these two levers can be attributed cleanly. The work touches `env/config.py`, `env/racing_env.py` (reset/spawn + early-termination), `train/loop.py` (climb-bias + schedule wiring), `train/config.py`, `controller/encoding.py`, and the README.

## Acceptance Criteria
1. A training-time spawn-height schedule exists and is unit-tested: it returns `climb_target_height` (or the configured high endpoint) at training-progress fraction 0, `floor_z` at/after the configured anneal-end fraction, is monotone non-increasing in between, and never returns a value below `floor_z` or above the high endpoint.
2. The schedule is applied **only** during training rollouts. Eval and recording environments spawn on the floor (z ≈ `floor_z`) exactly as before this use case — verified by a test that constructs an eval/recording env and asserts the reset spawn z is at the floor regardless of the schedule.
3. A fresh model build initializes `action_net.bias[THROTTLE_INDEX]` to `CLIMB_BIAS_THROTTLE` (a new constant in `controller/encoding.py`, value > `HOVER_THROTTLE`), verified by a unit test reading the bias after build. The UC-40 hover-bias code path is superseded by (not duplicated alongside) the climb-bias path — there is exactly one throttle-bias initializer.
4. The climb-bias init fires **only on a fresh build** and is skipped when resuming from a checkpoint, and is skipped (with a warning, as UC-40 does) when `model.policy.squash_output` is True. Both branches are unit-tested.
5. A drone spawned airborne (spawn z > `floor_z + floor_epsilon`) is **not** flagged grounded / no-progress / stuck and terminated at or near step 0. A unit test spawns airborne and asserts the episode is not cut by the grounded or no-progress detector within its warm-up window; a drone that then falls to the floor and stays there is still cut (grounded semantics preserved).
6. All pre-existing reward invariants remain intact — potential-based/telescoping/non-farmable shaping, ≈0 on the floor, capped at `climb_target_height`, per-episode shaping total < `completion_bonus`, `climb_gamma == gamma`, penalty-free stuck-cut, anti-suicide, and UC-43's `ground_break_height == EarlyTerminationConfig.floor_epsilon` coupling. The existing reward-math and doc-contract tests (`test_reward_docs.py`, `test_bootstrap_docs.py`, `test_viz_contract.py`, and the UC-37→43 reward tests) all pass unchanged, or are updated only where a documented value legitimately changed.
7. The README documents (a) the reverse-curriculum spawn schedule and its training-only scope, (b) the climb-biased init and its value, and — prominently — (c) the **fresh-run requirement**: a valid evaluation of this change requires starting a brand-new model with old checkpoints cleared, because both levers are defeated by resuming from a checkpoint (climb-bias applies only to fresh builds; a resumed pre-fix checkpoint carries an already-collapsed policy). If any reward/config value in the README reward table changed, the table is updated in the same PR.
8. Lab validation (not the ~12h GPU retrain, which stays the user's and is not a CI gate): a short CPU smoke-train or the sandbox real-pybullet probe demonstrates that with an airborne spawn the drone collects airborne/climb reward, `ep_rew` rises above the −5 time-penalty floor, and the policy's action std does not collapse to 0 over the smoke window. The smoke result is reported in the PR; it is not required to be a committed hermetic test if it depends on pybullet.

## Potential Pitfalls & Open Questions
- **Edge case** — Early termination vs airborne spawns: the existing `_took_off` latch (`racing_env.py:314`) arms the grounded detector from the spawn state, so an airborne spawn already gets sane grounded semantics (cut only if it falls and stays down). The dev-team must confirm the **no-progress / stuck** detector does not spuriously fire for a drone that spawns high and descends slowly, and that the grounded warm-up windows behave correctly for a non-floor spawn.
- **Risk** — Curriculum leak into eval/recording would invalidate the takeoff measurement. The schedule must be plumbed so only training rollouts see a raised spawn; any shared reset path must branch on a training flag.
- **Risk** — Distribution shift as the spawn anneals to the floor: if the anneal is too fast the policy never consolidates hover before takeoff is required; too slow and most of the budget is spent not learning takeoff. Anneal shape/duration are tunable (assumption below).
- **Assumption** — Anneal linearly from `climb_target_height` → `floor_z` over the first 50% of `total_timesteps`, floored for the remaining 50%. Tunable; the analyst/challenger may pick a staged schedule or a different fraction with justification.
- **Assumption** — `CLIMB_BIAS_THROTTLE = 0.6` (gentle net-positive lift; the sandbox pybullet probe showed hover ≈ 0.48 and throttle 0.9 rockets upward, so 0.6 is a mild climb). Tunable.
- **Assumption** — The reverse curriculum re-parameterizes the UC-37 floored-start line rather than reverting it; the floored start remains the terminal state of the anneal and the eval/recording spawn.
- **Assumption** — Reuse/generalize the latent `start_z_range` config already present rather than inventing a parallel mechanism, if it fits.

GOAL: make the drone actually EXPERIENCE sustained airborne flight during training so PPO can reinforce it, by removing the takeoff-discovery problem — not by more reward shaping.

LEVER 1 — Airborne-start reverse curriculum (TRAINING-TIME ONLY). Instead of always spawning on the floor (UC-37), spawn the drone at an initial altitude that starts high (at/near climb_target_height) early in training and anneals down toward the floor as training progresses (keyed on training-progress fraction; e.g. staged or linear anneal from climb_target_height → floor over the first portion of steps, then floor for the remainder). CRITICAL: recording and eval spawn on the floor as normal (consistent with UC-36 eval/recording semantics) so we still measure TRUE takeoff — the curriculum must not leak into eval/recording.

LEVER 2 — Climb-biased throttle init (fresh-build only). Extend UC-40's hover-bias: instead of initializing action_net.bias[THROTTLE_INDEX] to HOVER_THROTTLE=0.5 (net-zero thrust → the drone sits), initialize slightly above hover via a new CLIMB_BIAS_THROTTLE constant (candidate 0.6–0.7) so a fresh policy's default action produces gentle net-positive lift and collects airborne/climb reward immediately, compounding with the reverse curriculum. Fresh-build only, same guards as UC-40 (never perturb a resumed checkpoint; require squash_output False).

PROVENANCE GUARD (must be an explicit acceptance criterion and documented loudly in the README run guidance): a VALID test of this UC requires a FRESH run — a brand-new model with old checkpoints cleared — so the climb-bias init fires and no pre-fix collapsed policy is inherited. The last 565k-step run was almost certainly invalidated by resuming from a checkpoint (hover-bias only applies on fresh builds); resuming silently defeats both levers.

INVARIANTS TO PRESERVE (do not regress): all UC-37/38/39/42/43 reward invariants — potential-based/telescoping/non-farmable shaping, ≈0 on the floor, capped at target, per-episode total < completion_bonus, climb_gamma==gamma, penalty-free stuck-cut, anti-suicide, and UC-43's ground_break coupling (ground_break_height == EarlyTerminationConfig.floor_epsilon). The reverse curriculum changes the SPAWN STATE, not the reward function, so reward-math tests stay green.

KEY PITFALL — early-termination vs airborne spawns: a drone spawned at altitude must NOT be instantly flagged "grounded/stuck/no-progress" and cut. Ground-stuck / no-progress early termination (UC-25/36/38) must either be measured relative to actual motion rather than absolute floor contact, or be suppressed while spawn_height > floor. The analyst/challenger must resolve this explicitly.

VALIDATION (lab only; the ~12h GPU retrain stays the user's, NOT a gate): unit tests for (a) the spawn-height schedule — monotone anneal, correct high/low endpoints, training-only (eval/recording spawn on floor), (b) the climb-bias init — fresh-only, correct value, squash guard, (c) early-termination compatibility with airborne spawns (no instant cut). Plus a short CPU smoke-train (or the sandbox real-pybullet probe) demonstrating that with an airborne spawn the drone COLLECTS airborne/climb reward, ep_rew rises above the -5 floor, and std does NOT collapse to 0. Real takeoff verdict = the user's fresh GPU retrain.
