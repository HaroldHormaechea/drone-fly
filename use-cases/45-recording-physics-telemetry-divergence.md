# Use Case 45: Diagnose & fix the recording-vs-physics telemetry divergence

## Summary
Flight recordings do not faithfully represent what the drone actually does in the pybullet physics, which means the project has been debugging takeoff off untrustworthy telemetry. The discrepancy was found by replaying a recording's own action sequence through the physics and comparing trajectories. For `episode_500.json` from the UC-44 training run (backend=pybullet, dt=0.05, 20 frames): replaying the recorded actions through the bare `PybulletDroneAdapter` produces a drone that **tumbles** (roll swings past 90°/155°, fully flips), **rises to z≈1.03 then inverts and falls**, and travels **~1.77 m horizontally**; the recording of that same episode shows x/y **frozen** (~0.002 m total) and a **monotonic z-fall** from 0.889 to the floor by step 9. Same actions, materially different trajectory in both the horizontal axes and the vertical profile — the recording is inconsistent with the physics of its own actions. Sanity checks confirm the physics/mixer are fine when level: bare-adapter throttle=1.0+level climbs 0.9→9.36 m; throttle=0.5+level holds 0.900 m exactly. The task is to reproduce the discrepancy through the **real training path** (`RaceEnv`+pybullet, including the in-training `RecordingCallback`), localize the divergence to either the recorder or the env with evidence, fix the root cause so recorded trajectories match the true drone state, and add a hermetic regression test. This gates further GPU training — nothing else should be tuned until telemetry is trustworthy. It touches `record/recorder.py`, `train/record_callback.py`, `env/racing_env.py`, `adapter/pybullet_adapter.py`, `train/loop.py`, and `tests/`.

## Acceptance Criteria
1. The discrepancy is reproduced through the real training path: a `RaceEnv` on the pybullet backend, constructed as training constructs it (and, where feasible, exercised through the `RecordingCallback`), is driven with episode_500's recorded action sequence, and its emitted per-step `drone_position` is compared against (i) the recording and (ii) the bare-`PybulletDroneAdapter` replay. The comparison is captured as evidence in the PR.
2. The divergence is **localized with evidence** to a specific cause — recorder (logs a position that doesn't reflect the true adapter/env state, e.g. a frozen or dropped axis) vs env (the training path applies actions differently or constrains lateral motion) — before any fix is written. The root cause is stated explicitly in the PR.
3. The root cause is fixed so that, for a given action sequence, the recorded trajectory faithfully matches the drone's true per-step state on **all three position axes** (and the vertical profile matches the physics, not a monotone artifact).
4. A **hermetic** regression test (no pybullet) is added that would catch a recorder/env that freezes or drops a position axis — e.g. via the simple adapter or a fake adapter whose position advances on all three axes, asserting the recorder writes the adapter's exact per-step position componentwise.
5. If the cause is env-side (lateral motion constrained in the training path), the fix restores full 3-DOF translation in training and a test asserts a laterally-commanded drone actually translates.
6. The full CI gate is green: `uv run ruff check .`, `uv run ruff format --check .`, `uv run --extra dev pytest`. The manual pybullet reproduction (run via the main-checkout venv) is reported in the PR but is **not** a CI gate.
7. Reward function, curriculum, and exploration/entropy settings are unchanged (out of scope). The attitude-tumbling-under-exploration observation is noted as a separate follow-up, not addressed here.
8. **Recording provenance (scope addition, user-approved 2026-09-22).** Every recording's `meta` block additionally pins enough to reproduce/analyze it after the fact, even across code drift: (a) the exact code version — a `git_sha` resolved at record time, with a safe fallback (e.g. `"unknown"`) when not in a git work tree; (b) a real `checkpoint` reference — the path/identifier of the model that produced the rollout — replacing the current `"(training)"` placeholder when a checkpoint exists (the placeholder remains only when genuinely training-from-scratch with no saved weights yet); (c) the per-episode sampled `dynamics` (mass/thrust/drag/etc.) when domain randomization is active, so the physics is pinned independent of the seed→sample mapping.
9. Hermetic tests assert the enriched `meta`: `git_sha` present and non-empty (with the resolver mocked/monkeypatched so the test does not depend on the runner's real git state), the `checkpoint` field carries a provided reference (not the placeholder) when one is supplied, and sampled `dynamics` are recorded when randomization is enabled. No behavioral change to physics, reward, or the action channel beyond UC-45's fidelity fix.

## Potential Pitfalls & Open Questions
- **Risk** — Misattribution: fixing the recorder when the env is at fault (or vice versa) would leave the real bug in place. AC2 forces evidence-based localization before any change.
- **Edge case** — The in-training `RecordingCallback` records env-0 of the vec stack (VecNormalize→VecMonitor→SubprocVecEnv). The divergence may live in how position is read through that wrapper stack, or in a subproc boundary — reproduce as close to that path as feasible, not just a bare env.
- **Assumption** — CI is hermetic with no pybullet; the committed regression test must be hermetic (simple/fake adapter), and the pybullet reproduction is a local/manual probe run via `/workspace/drone-fly/.venv/bin/python` with `PYTHONPATH=<WORKDIR>/src`. The worktree does not share the main venv.
- **Assumption** — episode_500's recorded actions are a valid, representative repro input; if the recorder also mis-logs actions (not just positions), the repro must account for that (compare logged-action replay vs a freshly-driven known sequence).
- **Risk** — A recorder that logged wrong positions means prior per-UC "sits on the floor" conclusions were partly artifacts; the fix should make future recordings trustworthy but the team should flag which past observations are now suspect.
