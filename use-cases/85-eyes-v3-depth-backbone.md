# Use Case 85: Eyes v3 — pretrained monocular-depth backbone for the obstacle-ray estimator

## Summary
UC-83 proved the vision "eyes" estimator cannot learn to range obstacles from the current captures even with a classification head + focal loss + hit-weighted mining (near-obstacle miss stuck ~0.99, hit head recall 0.027 — both detection and ranging fail). UC-84 attacks that ceiling with *more data* (richer Liftoff captures). UC-85 attacks it with *architecture*: replace the eyes estimator's from-scratch CNN trunk with a **pretrained monocular-depth backbone** (a small DepthAnything-/MiDaS-class model) as the feature extractor, so the ray head predicts distances from depth-aware features carrying a strong prior learned from millions of general images — the ranging intuition a few thousand drone frames can't teach. It is **opt-in / default-off** (the UC-78/83 `EyesNet` stays the default, byte-identical when unset), is built and evaluated **in-sandbox on the current 5-map data now** (an independent read on whether a depth prior helps even with thin data — parallel to the user's UC-84 capture flights, no Liftoff needed), and is designed to re-run on UC-84's richer captures when they land. Because the eyes must run within the live control budget, UC-85 treats **latency as a first-class gate**: a depth backbone that improves ray accuracy but blows the ~25 ms / 40 Hz tick (alongside the gate detector) is recorded as "accuracy-win but not deployable," mirroring UC-79's diagnostic-not-deployable framing. Depth-model weights are small (≤ ~150 MB) given disk pressure (~17 GB free). Success is measured like UC-83: v3-depth vs the v1-baseline on the same held-out maps, ≥30 % relative nearest-quarter in-view miss reduction with false-alarm ≤0.10, AND within the latency budget to count as shippable.

## Acceptance Criteria
1. **Opt-in depth backbone (default-off byte-identical).** The eyes model gains an opt-in mode that swaps the CNN trunk for a pretrained monocular-depth backbone feeding the existing ray/confidence head (and the UC-83 hit head when enabled), selectable by config/flag. With the option unset, the model and `eyes train` are behaviourally unchanged from UC-78/83 (existing eyes tests pass; a test asserts the default path is byte-identical). The chosen backbone is a **small** model (≤ ~150 MB weights) named in the plan, with its license/source recorded.
2. **Backbone provisioning.** The pretrained weights are fetched to a per-user cache (reuse the project's cache convention) once and reused; the dependency is added to the project deps. A documented offline/already-cached fallback exists so a no-internet run reuses the cache. A test covers the "weights already cached → no download" path with a stub.
3. **Depth features feed the ray head.** The backbone's features (or predicted depth map) are adapted to the ray-head input; the K-frame / ego-motion contract of the estimator is preserved. A test asserts the forward IO contract (frames+ego-motion in → 40 distances + confidences [+ hit logit] out) with the backbone on.
4. **Trained + measured vs v1-baseline on current data.** `eyes train` produces a v3-depth checkpoint on the current 5-map dense dataset; `eyes eval` reports on the **same held-out maps** as UC-78/83 (HangarC03, MinusTwo, ThePit; identical range/tol) so v3-depth vs v1-baseline is like-for-like via `eyes compare`.
5. **Latency gate.** `eyes bench` reports the v3-depth estimator's p50/p95/p99 latency on the target budget; the result doc states whether it fits the ~25 ms / 40 Hz live tick alongside the gate detector. A backbone that clears the accuracy bar but not latency is flagged "accuracy-win, not deployable," and the doc names the mitigation (smaller/distilled backbone, lower input res, features-only).
6. **Success criterion.** v3-depth shows a **≥30 % relative reduction in nearest-quarter (0–4 m) in-view miss vs the v1-baseline on the same data**, false-alarm-on-clear ≤0.10, AND fits the latency budget → adopt. If it improves accuracy but fails latency, record it as a non-deployable accuracy result + the mitigation. If it does not improve accuracy, record the negative result (depth prior insufficient on this data) and defer to the UC-84 richer-data re-run.
7. **Driver + doc + re-run hook.** A resumable driver runs provision → dataset → train v1-baseline → train v3-depth → eval both → `eyes compare` + `eyes bench`, reusing the UC-83 recipe structure where possible. `docs/experiments/uc85-eyes-v3-depth.md` has the v1-vs-v3 ray-accuracy table, the latency line, and a recommendation; it documents how to re-run on UC-84's richer captures once available (and, if a winner clears both bars, the gated path to re-run the UC-82 obstacle-avoidance comparison).
8. **CI-hermetic tests** (CPU-only, no GPU, no network, no real captures): default-off byte-identity; cached-weights/no-download path (stub); backbone-on forward IO contract; the ray-head adapter shape; a tiny CPU train smoke on the depth path (with a stub/tiny backbone so it stays hermetic); the v1-vs-v3 compare + latency-report math.

## Potential Pitfalls & Open Questions
- **Risk (latency, the main one)** — a depth backbone can easily exceed the 25 ms live budget on the RTX 3050; AC5 gates on it, but even the smallest models may be marginal. The plan must pick the smallest viable backbone and consider features-only / reduced-resolution inference.
- **Risk (data ceiling persists)** — a depth prior may still not clear the near-miss bar on the thin 5-map data; that is an acceptable, informative outcome (AC6 negative branch) and routes to the UC-84 richer-data re-run rather than a failure.
- **Risk (disk)** — ~17 GB free / 88 % full; the backbone weights + cache must stay small (≤ ~150 MB) and the dataset/cache reuse UC-83's disk-margin guard.
- **Assumption (internet)** — HuggingFace is reachable in-sandbox (verified), so the backbone can be fetched; the offline-cache fallback (AC2) covers the no-internet case.
- **Edge case (hermetic tests)** — CI must not download the real backbone; tests use a stub/tiny module and the cached-path branch, so AC8 stays network-free.
- **Dependency** — adds a model dependency (timm or transformers + the depth model) to the venv; the analyst confirms the lightest option that provides a small depth model.
- **Assumption** — the K-frame + ego-motion input contract is preserved; if the depth backbone wants single-frame input, the adapter reconciles that without changing the deployable estimator interface.
