# Use Case 42: Strengthen the climb/airborne reward so the drone leaves the floor (takeoff gradient)

## Summary
UC-41 (PR #45) removed the crash-cliff *punishment* (hold-then-ramp collision curriculum), and a fresh run confirms that half worked: the actor no longer crashes or freezes, no K0 verdict fires, and it holds a calm hover against the floor. **But it still never takes off.** Across three real training recordings (`episode_100/150/200`, iters ~8–11, `backend: pybullet`) the drone is pinned at z ≈ 0.0135 m (resting height), x/y frozen, `total_reward` ≈ −5.49 (the pure time-penalty floor), and the effective (clipped-to-[0,1]) throttle sits at ~0.49 — right at hover — with ~47% of steps above 0.6 yet **zero net altitude gain**. The "Reward stalled" health warning has fired (as in the pre-UC-41 run). The policy has settled into a *penalty-free hover-rest local optimum*: removing the takeoff punishment did not create enough pull toward sustained lift, and momentary above-hover excursions are not being reinforced into the sustained above-hover throttle needed to break ground contact and climb. This use case diagnoses (with evidence) why sustained takeoff isn't reinforced and delivers a fix that makes leaving the floor and gaining altitude decisively out-reward hovering — most likely by strengthening the low-altitude climb / airborne-survival reward, while evaluating exploration (`ent_coef`) and thrust-authority/takeoff-bootstrap as secondary levers. It touches `src/drone_fly/env/config.py` (RewardConfig), `src/drone_fly/env/reward.py` / `racing_env.py` (reward assembly), possibly `src/drone_fly/train/config.py` (ent_coef), and `README.md` (reward-table sync if any RewardConfig value changes).

## CRITICAL VALIDATION CONSTRAINT (read first)
**pybullet is NOT available in this sandbox** — the dev-team can only run the numpy `simple` adapter. UC-40's `simple`-adapter smoke-train reported "gets airborne / ~4× altitude," yet the real `pybullet` run shows zero lift: **the simple adapter is over-optimistic about takeoff and must NOT be treated as behavioral proof.** Therefore:
- In-sandbox validation proves the **reward *structure*** only: deterministic reward-function tests showing sustained climb now out-rewards hover-rest, altitude gain is monotonically reinforced, and all invariants hold.
- A green `simple`-adapter smoke-train is a wires/finite/no-collapse check ONLY — it is explicitly NOT evidence that the drone takes off. Do not claim takeoff from it.
- Behavioral confirmation (the drone actually leaving the floor and climbing) is the **user's pybullet GPU retrain** and is NOT a gate for this UC.

## Acceptance Criteria
1. The reason sustained takeoff isn't reinforced is diagnosed **with evidence** (file:line + reward math): why ~hover-throttle exploration nets zero altitude, why brief above-hover excursions don't accumulate into lift, and why the current climb/airborne reward is too weak relative to the hover-rest floor. Each candidate lever (climb/airborne reward magnitude; `ent_coef`/exploration; thrust-authority / takeoff bootstrap) is explicitly confirmed or ruled out.
2. A fix is implemented that makes **sustained climb decisively out-reward hover-rest** at the operating point, demonstrated by a **deterministic reward-function test**: e.g. a trajectory that gains and holds altitude accrues strictly greater return than the hover-at-floor trajectory, by a margin large enough to survive PPO advantage normalization. This — not any smoke-train — is the primary evidence.
3. The fix preserves ALL UC-37/38/39 invariants: potential-based/telescoping (F = γΦ′ − Φ), non-farmable (no reward for hovering-in-place without progress/altitude; no ceiling-seeking — capped at target), ≈0 on the floor, per-episode shaping total < `completion_bonus`, `climb_gamma == training gamma`, penalty-free stuck-cut, and anti-suicide. If reward values change, the README reward table is updated in the same change and `tests/test_reward_docs.py` / `test_bootstrap_docs.py` / `test_viz_contract.py` stay green.
4. The fix does not re-introduce prior failure modes: it must not restore a crash-cliff (UC-41), must not collapse `std` to ~0 while success is 0 (UC-38/40 — keep `ent_coef` > 0 and exploration alive), and must not let the actor freeze (UC-40). Covered by the existing health-rule tests staying green + any needed additions.
5. The full suite stays green: `uv run --extra dev pytest`.
6. Because pybullet is unavailable in-sandbox, the smoke-train (numpy `simple` adapter) is used ONLY as a wires/finite/no-collapse check and is explicitly documented as non-behavioral; the acceptance evidence for "takeoff is now rewarded" is the deterministic reward-math test (AC2), and behavioral confirmation is deferred to the user's pybullet retrain (not a gate).

## Potential Pitfalls & Open Questions
- **Risk (repeat-of-UC-41):** trusting a green `simple`-adapter smoke-train as proof of takeoff. The whole reason we're here is that adapter over-promised. Guard hard against it (AC6).
- **Risk (invariants):** naively increasing a climb reward can break non-farmability (drone farms altitude reward by bobbing) or push per-episode shaping ≥ `completion_bonus`. Any magnitude change must preserve the bounds and the telescoping/non-farmable proofs (UC-37/38/39 tests).
- **Ambiguity:** whether the true blocker is reward *magnitude* (climb too weak), *exploration* (std narrowing off hover before a sustained-climb streak is found), or *thrust authority / ground-contact* (momentary above-hover can't break contact; needs sustained, which the reward must incentivize). The diagnosis must settle which — the fix should be the minimal evidence-supported set, not all three.
- **Edge case:** a stronger climb reward must still respect the airborne flag / floor-band definition (`racing_env.py`) so it doesn't pay out while grounded.
- **Assumption:** the hover-bias (UC-40) and hold-then-ramp curriculum (UC-41) stay in place; UC-42 adds the missing *pull*, it does not revert them.
