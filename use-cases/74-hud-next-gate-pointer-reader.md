# Use Case 74: Live HUD next-gate pointer reader (classic OpenCV, no ML)

> **Naming note on "UC72".** The run-2 code and plan refer to the live HUD reader as "UC72" in comments (e.g. `src/drone_fly/harness/student.py:129` "UC72 adds the live HUD reader", `src/drone_fly/sim/student_obs.py:171`, `src/drone_fly/student/obs_ref.py:88`, `src/drone_fly/training/configs/student-liftoff-run2.yaml:8,19`, `.dev-team/plans/uc-70-run-2.md:18`). That label is stale: UC72 is *Liftoff evaluation + fine-tuning* (`use-cases/72-liftoff-eval-and-fine-tuning.md`). **This use case (74) is the real "live pointer reader".** On completion, those stale "UC72" comments should be updated to reference UC74.

## Summary
Liftoff renders an on-screen **next-gate pointer** — a small circle/arrow HUD icon that points toward the gate the pilot should fly through next. UC70 run-2 already taught the student to consume a **next-gate pointer observation**: a body-frame unit bearing (3) plus an availability bit (1), appended at the tail of the student observation (`student-obs` schema `VERSION = 3`, `DIM = 61 → 65`; block `("pointer", 4)` in `src/drone_fly/sim/student_obs.py:63`). In the simulator that signal is produced from the truth target centre and corrupted with a HUD-like noise model; **live, it is always `None` → zeros / availability bit 0**, because no live reader exists yet — the learned `TrackingGateEstimator` never populates `info["pointer"]` (`src/drone_fly/harness/student.py:127-130`). Run-2 flown live is therefore degraded to "run-1 + gate-memory + FP-suppression (temporal + memory sub-gates only)" — the pointer OBS gain and the pointer FP-suppression sub-gate are unrealized (`.dev-team/plans/uc-70-run-2.md:60`).

This use case builds that missing live reader using **classic OpenCV image processing only — no AI/ML model**. It detects the fixed HUD pointer icon in the live game frame (template match / colour threshold / contour-shape), reads its screen position/angle relative to the image centre, and converts that into the **same body-frame unit bearing (3) + availability bit (1)** that `est.info["pointer"]` expects. The reader plugs into the existing live assembler path (`build_student_obs(..., pointer=(gate.info or {}).get("pointer"))`, `src/drone_fly/harness/student.py:130`), so the already-trained run-2 student consumes it **unchanged** — no retrain, no obs-schema bump.

It deliberately **mirrors how gates become model inputs today**: the gate detector thresholds/contours the frame, solves a camera-frame pose, rotates it into the body frame via the live attitude and the `CameraModel` (uptilt), and emits it through `est.info` (`src/drone_fly/harness/liftoff/gate_cv.py`). The pointer reader is the lightweight equivalent — a fixed 2-D HUD icon rather than a 3-D gate — so it reuses the project's established camera conventions (horizontal FOV, principal point at image centre, `body_to_camera` uptilt rotation, FLU body frame).

**Calibration deliverable.** The sim pointer-noise parameters are currently *provisional* — `bias_sigma_rad: 0.05`, `jitter_sigma_rad: 0.03`, and `pointer_bearing_tol_deg: 20.0` are flagged "provisional; UC72" in `src/drone_fly/training/configs/student-liftoff-run2.yaml:25-26` and `.dev-team/plans/uc-70-run-2.md:61`. This use case produces the **first real measurements** of the HUD reader's bearing error so those provisional sigmas / tolerance can later be replaced with characterized values (an input to a future run-2 noise re-tune — not part of this use case's happy path, which is detection + conversion + live wiring).

**Dataset & environment split (see Clarifications).** The detection/bearing logic and its wiring are built and proven **in-sandbox on synthetic fixtures and hand-computed frames** — no real footage is required to implement and unit/integration-test the reader. The *empirical* criteria that need real pixels — AC2 (precision/recall on labelled frames), AC3 (bearing error vs reconstructed ground truth), AC8 (live validation), and AC9 (measured calibration) — are evaluated **on the user's machine** (the project's `captures/` artifact convention; these frames are not checked into the repo and are not present in the Linux dev sandbox). The live-latency half of AC5 is likewise a Windows/live measurement; an offline per-frame cost guardrail is enforced in-sandbox.

**Recording provenance (critical for the empirical ACs).** The frames used for AC2/AC3/AC9 must be **live-pilot screen captures with the game HUD visible** — stored raw by `recording.py` (`frame.image` via `cv2.imwrite`/`np.save` at `recording.py:395-406`, *before* any masking; masking is only a detection-time filter, never a storage crop). Liftoff's own in-game `.xml` **race replays** (what the `liftoff-episodes` skill saves to `Recordings\Race\<name>.xml`) store trajectory data only and re-render without the pilot's next-gate pointer HUD — **they are unusable for this reader.** If the existing corpus is predominantly `.xml` replays (or otherwise lacks the on-screen pointer), a fresh screen-capture pass on Windows with the HUD on is required. Internet-sourced Liftoff FPV gameplay (showing the pilot HUD pointer) is a valid fallback for hardening **detection** (AC2) across themes/scales/versions, but **cannot supply bearing ground truth** (AC3/AC9), which requires synchronized telemetry pose + track XML.

### How gates become model inputs today (the pattern to mirror)
1. **Detect in image.** `OpenCvGateEstimator.detect_quads` (`gate_cv.py`) does HSV threshold over configured ranges → morphology (`MORPH_CLOSE`/`MORPH_OPEN`) → external contours → convex 4-corner quads (area / convexity filters). The learned detector is the alternative `detect()` implementation.
2. **Camera-frame pose.** `solve_pose` runs `solvePnP` (IPPE) of each quad against the nominal gate rectangle, giving `(t_cam, n_cam)` in the camera frame, using intrinsics from the configured horizontal FOV (`camera_from_config`, `gate_cv.py`; `CameraModel.intrinsics` in `src/drone_fly/harness/geometry.py:163` — `fx = (width/2)/tan(hfov/2)`, principal point at image centre `cx,cy`).
3. **Camera → body → world.** `detection_from_pose` (`gate_cv.py`) rotates the camera-frame vector by `CameraModel.body_to_camera()` (the uptilt rotation `R_cb`, `geometry.py:166-171`) and the live attitude `quat_to_matrix(state.quat)`. Body-frame bearing is `R^T (centre − pos)` (see the pointer math below).
4. **Masks.** Before `detect()`, the frame is masked (`FrameMasks.apply`, `src/drone_fly/harness/liftoff/masks.py:89`); detections whose centre pixel falls inside a mask are dropped (`TrackingGateEstimator.detect_frame`). **The HUD region the pointer lives in is exactly a masked region** — see AC7.
5. **Emit via `info`.** The estimate carries extra fields on `GateEstimate.info` (`extra_info()` / the `info` dict assembled in `TrackingGateEstimator.update`); the assembler reads `gate.info` downstream.

### The exact pointer contract the model expects
Single-sourced body-frame unit bearing (3) + availability bit (1), surfaced on `est.info["pointer"]`:
- **Sim truth path** computes it in `GatePerception._pointer` (`src/drone_fly/sim/perception.py:632-650`) and its numpy twin `ReferencePerception._pointer` (`src/drone_fly/student/perception_ref.py:242-256`): `rel_b = R^T (centre − pos)`, normalise to a unit vector, then `az = atan2(rel_b.y, rel_b.x)`, `el = asin(rel_b.z)`, reassemble `[cos(el)cos(az), cos(el)sin(az), sin(el)]`; availability `avail = target_valid AND NOT dropped`; when unavailable the vector is zeroed and the bit is 0.
- **Emitted** as `"pointer": concat(ptr_body(3), [1.0 if avail else 0.0])` — see `perception_ref.py:485-486` and the torch `outputs()` at `src/drone_fly/sim/perception.py:927`.
- **Through `estimate_from_raw`** it lands on `est.info["pointer"]` as `None` or `float32[4]` (`perception_ref.py:527-530`).
- **Obs builder** reads it: torch via `perc["pointer"]` (`student_obs.py:330`), numpy via `est.info["pointer"]` with `pointer`-arg fallback (`src/drone_fly/student/obs_ref.py:78-109`), appended as the `("pointer", 4)` tail block (`student_obs.py:63`; `input_scale` tail `[1.0]*4`, `student_obs.py:104`).
- **Live assembler** passes `pointer=(gate.info or {}).get("pointer")` (`src/drone_fly/harness/student.py:130`) — **this is the single integration seam**: the only thing the new reader must do is make a `TrackingGateEstimator`-shaped live estimate carry a correctly-computed `info["pointer"]` (a `float32[4]`) instead of leaving it `None`.
- **Schema record** (`student_obs.py:164-172`): `pointer.layout = "body-frame unit bearing (3) + availability bit (1)"`, with `source` documented as "sim: noisy truth bearing; live (pre-UC72): learned tracker leaves it unavailable (bit = 0)" — this use case flips the live half of that statement (and updates the stale "UC72" label to "UC74").

## Acceptance Criteria

1. **Classic-OpenCV detector, zero ML dependency.**
   - The pointer reader detects the fixed HUD pointer icon from a single live frame using only classic image processing — template matching, colour thresholding (HSV in-range, as the gate detector does), and/or contour-shape analysis. OpenCV is imported lazily, matching the gate estimator's `_cv2()` pattern (`gate_cv.py`).
   - A test proves **no ML model / neural network / learned weights** are reachable from the pointer reader's code path (no torch, no model file load, no `gate_net`/`gate_learned` import). This is a hard constraint.

2. **Detection precision / recall on labelled frames.** *(empirical — runs on the user's machine against the race-recording corpus)*
   - On a labelled set of captured Liftoff frames (pointer present vs absent), the detector reports **precision ≥ 0.98 and recall ≥ 0.95** for "pointer present and localized to within **≤ 5 px** of ground truth" at the capture reference resolution.
   - The evaluation script and the label manifest are checked in; the frames themselves may live under the existing capture artifact convention (not the repo) if large. The labelled set is drawn from the existing race recordings/screenshots; more is recorded if the corpus is insufficient.
   - In-sandbox, this AC is exercised with synthetic fixture frames (rendered/known-position pointer icons) to prove the evaluation harness and detector plumbing; the gating precision/recall numbers are produced against real frames on the user's machine.

3. **Bearing accuracy vs known ground truth.** *(empirical — real frames on the user's machine; hand-computed unit test in-sandbox)*
   - On frames where the true next-gate bearing is reconstructable (telemetry pose + track XML, the UC64/UC70 auto-label machinery), the reader's body-frame unit bearing agrees with ground truth within **median ≤ 3° and p95 ≤ 8°** combined angular error. Report azimuth and elevation error separately and as a combined angular error.
   - The conversion uses the project's existing camera conventions: screen offset from principal point (`cx,cy`, image centre) → camera-frame ray via the configured horizontal FOV (`CameraModel.fx`), → body frame via `CameraModel.body_to_camera()` (uptilt) and the live attitude, producing the exact `[cos(el)cos(az), cos(el)sin(az), sin(el)]` unit vector the sim contract emits (`perception.py:632-650`).
   - A **hand-computed unit test** (known icon pixel, known attitude → expected bearing) runs in-sandbox and must pass independently of any real footage.

4. **Availability bit degrades gracefully.**
   - When the pointer is **absent, occluded, or being passed through a gate** (Liftoff hides/repositions the pointer at/near a gate), the reader emits availability bit = 0 and a zero bearing — never a stale or hallucinated bearing. This matches the sim contract (`avail = target_valid AND NOT dropped`, zeroed vector when unavailable).
   - A test feeds pointer-absent frames (synthetic in-sandbox) and asserts `info["pointer"] == [0,0,0,0]` (bit 0), and that the student still flies (the run-2 student was trained with per-episode pointer dropout for exactly this regime — `.dev-team/plans/uc-70-run-2.md:19`).

5. **Per-frame latency within the live budget.**
   - **In-sandbox guardrail:** a benchmark test asserts the pointer reader's per-frame cost over its ROI is cheap in absolute terms and does not regress the combined gate-detector + obs-assembly cost (pure OpenCV over a small fixed HUD region).
   - **On the user's machine:** the reader's p95 per-frame latency fits inside the live control budget **alongside** the existing gate detector and obs assembly on the target live GPU/host, consistent with the UC70/UC73 live-latency framing. It reuses the already-captured frame (no second grab).

6. **Parity with the sim pointer contract (student consumes it unchanged).**
   - The live reader populates `est.info["pointer"]` as a `float32[4]` = body unit bearing (3) + bit (1), identical in shape, dtype, frame convention (body FLU), and availability semantics to the sim/`ReferencePerception` output. No change to `student-obs` schema (`VERSION` stays 3, `DIM` stays 65), no change to `build_student_obs`, no retrain of the run-2 student.
   - An integration test runs the live assembler path (`harness/student.py`) with a reader-produced estimate and asserts the `("pointer", 4)` obs tail block is populated (non-zero when the pointer is present) and that an identical frame with no pointer yields the degraded zeros/bit-0 block.

7. **HUD-mask interaction handled explicitly — hybrid ROI.**
   - The pointer lives inside the HUD/OSD region that the gate detector **masks out** (`FrameMasks`, `masks.py`; gate detections centred in a mask are dropped — `gate_cv.detect_frame`). The pointer reader reads the **unmasked** frame for a dedicated pointer ROI while the gate detector continues to mask that region.
   - The pointer ROI is resolved by a **hybrid policy**: by **default it is derived from the existing HUD mask geometry** (`camera.masks`, scaled per frame like `masks.py:68-80`), and an **optional explicit per-resolution config override** (a pointer-ROI rect, mirroring the `camera.masks` shape) takes precedence when present.
   - A test/doc shows the two consumers do not fight: the pointer ROI feeds the pointer reader, and is still excluded from gate detection. ROI geometry scales with capture resolution via `CameraModel.scaled_to` (`geometry.py:200`), the same way masks do.

8. **Live validation in Liftoff.** *(Windows follow-up — out of the in-sandbox develop run)*
   - The reader is exercised live on at least one track, and a short report shows the pointer bearing is populated and plausible across a lap (e.g. overlaid on the UC65 live debug overlay), with the availability bit dropping to 0 at gate passes as expected.

9. **Calibration output for a future noise re-tune.** *(empirical — real frames on the user's machine)*
   - The measured bearing-error statistics from AC3 are written to a small report (bias, per-tick jitter std, availability/false-positive rates), framed so they can **replace the provisional** `bias_sigma_rad` / `jitter_sigma_rad` / `pointer_bearing_tol_deg` defaults (`student-liftoff-run2.yaml:25-26`, `.dev-team/plans/uc-70-run-2.md:61`). Re-running run-2 training with the real values is explicitly **out of scope** here (a downstream experiment), but the numbers are produced.

## Potential Pitfalls & Open Questions

*(Resolved during the clarification round: ML dependency → classic OpenCV only (AC1); no student retrain (AC6); exact 4-float output contract (AC6); AC2/AC3 thresholds fixed; pointer-ROI → hybrid derive-with-override (AC7); scope split code+tests-now / live-and-real-frame-eval on the user's machine. The following remain genuinely open and must be characterized from captures.)*

- **Icon variants / scale / colour** *(open — needs capture-set validation).* The pointer icon may differ across Liftoff versions, map themes, colour schemes, or HUD scale settings. Template matching is brittle to scale/colour; colour-threshold + shape may generalize better but risks false matches. Open: multi-scale template bank vs shape/contour descriptor vs hybrid. Must be validated across the maps/themes in the recording corpus (mirrors UC71's multi-map generalization concern).
- **Pointer absent / repositioned near or at a gate** *(open — characterize from captures).* Liftoff typically hides or snaps the pointer when you are at/through the current gate; this must map cleanly to availability bit 0 (AC4) rather than a spurious detection. The exact Liftoff behaviour at gate passes needs to be characterized from the recordings.
- **False matches vs other HUD elements** *(open).* Lap timer, speed/altitude readouts, stick widgets, ghost/lap lists, battery and other OSD glyphs share the HUD region and may trigger template/colour false positives. Needs an explicit reject strategy (ROI restriction, shape constraints, uniqueness of best match).
- **Screen-position/angle → bearing model** *(open — bounds AC3).* The HUD pointer encodes a *direction*, but is it a simple 2-D screen-space arrow (angle on screen) or a 3-D-projected marker? If it is a screen-edge/clamped indicator when the gate is off-frame, the pixel→camera-ray model (principal point + FOV) may not hold at the clamp. Whether the icon's position is a faithful projection or a clamped/eased indicator bounds achievable bearing accuracy — characterize from captures before trusting the tighter end of AC3.
- **`fp_suppress_pointer` live guard** *(open).* Enabling the pointer FP-suppression sub-gate live (it consumes the same `ptr_body`) may need a guard when the live bearing is noisier than the sim noise model assumed. This reader turns both the pointer OBS gain and the pointer FP-suppression sub-gate on live (today both are dead — `.dev-team/plans/uc-70-run-2.md:60`).
- **Sim ↔ live calibration gap** *(known, downstream).* The run-2 sim noise (`bias_sigma_rad=0.05`, `jitter_sigma_rad=0.03`, `bearing_tol_deg=20`) is provisional (`student-liftoff-run2.yaml:25-26`). Until replaced by this reader's measured characteristics (AC9), there may be a sim-to-live mismatch in how the student weighs the pointer. Replacing them is a downstream run-2 re-tune, not this use case.
- **Capture/dataset availability + recording type** *(open — needs the right footage).* The empirical ACs need **live-pilot screen captures with the HUD visible**, stored raw by `recording.py` (pre-mask). Liftoff `.xml` race replays (the `liftoff-episodes` output) store trajectory only and re-render without the pointer HUD — unusable here. If the user's existing corpus is mostly `.xml` replays, a fresh screen-capture pass (HUD on) is needed. Internet FPV footage can harden detection (AC2) but not bearing calibration (AC3/AC9), which needs telemetry-synced captures. None of this is present in the Linux sandbox, so in-sandbox work proceeds on synthetic fixtures + hand-computed cases.
- **Windows-only live path** *(known).* The live harness / screen capture is Windows-oriented (`frames.py`, the `liftoff-episodes` skill). Capturing frames and the AC8 live run happen on Windows; the pure-OpenCV conversion logic is platform-neutral and unit-testable anywhere.
- **Stale "UC72" references in code** *(cleanup).* On completion, update the "UC72 adds the live HUD reader" comments (`harness/student.py:129`, `student_obs.py:171`, `obs_ref.py:88`, `student-liftoff-run2.yaml:8,19`) to reference UC74.

## Original Description
> Liftoff (the drone sim) renders an on-screen "point guide" / next-gate pointer — a small circle/arrow HUD icon pointing toward the next gate. We want to DETECT that pointer from the live game frame and convert it into a pointer-to-target bearing for the model — the SAME signal the UC70 run-2 student already consumes (currently None/unavailable in live flight because no live reader exists yet). Crucially this should NOT need an AI/ML model — just classic OpenCV image processing (template/shape/colour detection of the fixed HUD icon) + coordinate conversion (screen position/angle → body-frame unit bearing), mirroring how GATES are turned into model inputs today.

## Clarifications
- Q: Should the reader use any ML/learned model?
  A: No. Classic OpenCV only (template match / colour threshold / contour shape) + coordinate conversion. A learned HUD reader is explicitly out of scope.
- Q: Does the student need retraining to use the live pointer?
  A: No. The run-2 student already consumes the `("pointer", 4)` obs block; this reader only fills the live `info["pointer"]` the assembler already reads. Schema `VERSION`/`DIM` are unchanged.
- Q: What exactly must the reader output?
  A: A body-frame unit bearing (3) + availability bit (1) as `float32[4]` on `est.info["pointer"]`, byte-compatible with the sim/`ReferencePerception` contract (`perception.py:632-650`, `perception_ref.py:242-256`, `student_obs.py:63`).
- Q: Is re-tuning the run-2 noise sigmas part of this?
  A: No — this use case *measures* the real HUD-reader error (AC9) so a later run-2 re-tune can replace the provisional sigmas/tolerance, but running that experiment is downstream.
- Q: What detection precision/recall/localization should AC2 gate on?
  A: Suggested starting targets — precision ≥ 0.98, recall ≥ 0.95, localized ≤ 5 px at the capture reference resolution.
- Q: What bearing-accuracy bound should AC3 require?
  A: Suggested — median ≤ 3°, p95 ≤ 8° combined angular error (azimuth/elevation also reported separately).
- Q: How should the pointer reader get its region, given the pointer sits inside the gate detector's masked HUD region?
  A: Hybrid — default-derive the pointer ROI from the existing HUD mask geometry, with an optional explicit per-resolution config override that takes precedence when present.
- Q: AC8/AC9 live validation + real-measurement calibration and AC5 live latency need Liftoff on Windows, which the Linux dev sandbox can't run. How should the develop run treat them?
  A: Code + tests now (reader, conversion, parity, availability, latency guardrail — AC1/AC3 hand-computed/AC4/AC6/AC7/AC5-guardrail on synthetic fixtures); AC2/AC3 real-frame evaluation, AC8 live validation, and AC9 calibration are follow-ups run on the user's machine against existing race recordings (record more if needed).
- Q: Is there footage to evaluate against, and does it contain the pointer?
  A: The user has race recordings/screenshots on their machine (not in the repo or the Linux sandbox). Important caveat: the empirical ACs require **live-pilot screen captures with the HUD visible** (stored raw, pre-mask, by `recording.py`). Liftoff `.xml` race replays store trajectory only and re-render without the pointer HUD — unusable. If the existing corpus is mostly replays, a fresh HUD-on capture pass is needed (the user can record more). Internet FPV footage is a detection-only fallback (no bearing ground truth).
