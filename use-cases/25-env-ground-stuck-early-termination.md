# Use Case 25: Ground/no-progress episode early termination

## Summary
Training episodes currently waste almost their entire step budget with the drone lying motionless on the floor, starving PPO of useful experience. Evidence from a real user recording (2000-step episode, pybullet, full connectome, randomized 9-gate course): the drone spawned at z=1.068, dropped to z≤0.01 within 9 frames (0.5 s), then rested at z∈[0.008, 0.014] for the remaining **1991 of 2000 frames (~99.5%)** — x never moved (−0.109→−0.098, finish at x=16.1), `target_gate` stayed 0, outcome `completed=False, steps=2000, total_reward=−82.8` (truncated at the full budget). Root cause: the numpy adapter's floor collision is `position[2] <= floor_z` (`src/drone_fly/adapter/simple.py:290`, floor_z=0.0), but a resting drone asymptotes to ~8 mm **above** the floor and never crosses it, so `collided` — and therefore `crash`/`terminated` (`src/drone_fly/env/racing_env.py`, `crash = collided and not docked`; `terminated = completed or crash`) — never fire; the episode ends only via truncation at the inflated `_max_steps` (base + `steps_per_gate`·gates + recharge/repair allowances, racing_env.py ~252–267). There is no grounded/no-progress early-termination anywhere. This UC adds an env-level early-termination rule combining **(a) a floor-epsilon crash** — resting within a documented epsilon band above `floor_z` is treated as a floor crash — **and (b) a no-progress/stuck detector** that ends an episode after a sustained window with no course progress, where **progress = the distance to the current target gate decreasing**. A grounded/stuck cutoff counts as a **crash** (`terminated=True` + the existing collision penalty). The legitimate UC-16 **docked/servicing** state (a drone actively recharging/repairing on a pad) is **exempt** while service is productive. It is an env termination-rule change only — no observation-schema/width change, no connectome change, **no checkpoint invalidation**; a normally-flying episode's outcome stays byte-identical, and smoke-train (simple adapter, fixture connectome) stays green.

## Acceptance Criteria
1. **Grounded episode terminates early (floor-epsilon crash):** an episode where the drone comes to rest within a documented epsilon band above `floor_z` and stays there is treated as a floor **crash** and ends within a bounded number of steps rather than running to `_max_steps`. A regression test reproduces the "lands and rests ~8 mm above the floor" trajectory and asserts the episode ends promptly (well under the full budget) with the crash terminal.
2. **No-progress/stuck cutoff:** an episode whose distance to the current target gate fails to decrease (beyond a documented epsilon) for a sustained, documented window ends early as a **crash**. A test with a hovering/circling drone that never reduces gate distance asserts early termination; a drone that keeps closing the gap is not cut.
3. **Crash semantics:** both cutoffs set `terminated=True`, apply the existing collision penalty, and are reported consistently in `info`/outcome (`collided=True`), so downstream logging/rollout accounting treats them as crashes.
4. **Docked/servicing exemption (non-loophole):** a drone in the UC-16 docked state actively recharging/repairing on a pad is NOT cut by the stuck rule while service is productive (charge/integrity improving). A test with a valid dock-and-recharge dwell asserts the episode is not prematurely ended; a drone that docks once then sits idle with no further improvement is still eventually cut.
5. **Warm-up guard / no spurious firing:** neither rule can fire during normal early flight before enough history exists; a normally-flying episode that reaches a gate is unaffected and its per-step outcomes are byte-identical to today.
6. **No obs/checkpoint impact:** no change to the observation schema, width, or connectome; existing checkpoints remain loadable/valid. Only tests whose asserted outcome the new rule legitimately changes are updated; all others stay green, including the full Linux CI suite (`ruff check .`, `ruff format --check .`, `uv run pytest`).
7. **Tunable constants:** the floor epsilon band, the stuck window length, and the gate-distance progress epsilon are named, documented constants/config with sensible defaults.

## Potential Pitfalls & Open Questions
- **Edge case (docked loophole)** — the docked exemption must not let a drone dock once and idle forever; tie the exemption to *productive* service (charge/integrity actively improving), not mere presence on a pad.
- **Risk (over-aggressive thresholds)** — too-tight thresholds could cut legitimate slow maneuvers (a cautious hover/approach before a gate); the warm-up guard + gate-distance epsilon must be calibrated against a real flying trajectory so normal flight is never cut.
- **Edge case (last leg / finish)** — after the final gate, "distance to next target gate" must be defined sensibly (e.g. distance to the finish plane) so the stuck detector behaves on the run-out to the finish.
- **Assumption** — this is separate from the policy's inability to fly (the capacity/health story in UC-23); this UC only stops wasting timesteps once the drone is grounded/stuck, it does not make the drone fly.
- **Assumption** — the floor-epsilon crash applies to both adapters' floor semantics; the numpy adapter is the tested path (pybullet floor contact is a documented untested boundary), and the rule is expressed on the env's observed z vs `floor_z`, not adapter internals.

## Clarifications
- Q: Which early-termination mechanism should this add?
  A: **Both** — a floor-epsilon crash (resting within epsilon above `floor_z` is a floor crash) AND a no-progress/stuck detector (end after a window with no course progress).
- Q: When the drone is cut for being grounded/stuck, how should it count?
  A: **As a crash** — `terminated=True` plus the existing collision penalty (strongest "you failed" learning signal).
- Q: What counts as "progress" for the stuck detector?
  A: **Distance to the next target gate decreasing** (direct, task-aligned; works in free 3D). On the final leg, use distance to the finish.
- Q: Does this change the observation schema or checkpoints?
  A: No — env termination-rule change only; no obs/width/connectome change, no checkpoint invalidation; normally-flying episodes stay byte-identical.
