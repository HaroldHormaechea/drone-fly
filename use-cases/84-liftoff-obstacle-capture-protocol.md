# Use Case 84: Liftoff obstacle-capture protocol — richer hit-ray data for the vision eyes

## Summary
UC-83 proved the vision "eyes" estimator cannot be fixed by training tricks: with a classification head + focal loss + hit-weighted mining, near-obstacle miss stayed ~0.99 and the hit head itself collapsed (in-view recall 0.027) — **both detection and ranging fail at the current data scale** (only 5 train maps on disk, monocular, ~5% in-view hit-ray fraction, very few frames flown close to obstacles). UC-84 attacks that data ceiling directly: define and tool a **teacher/model-driven capture protocol** that flies obstacle-dense courses across more maps in Liftoff, recording camera frames + telemetry, to raise the in-view hit-ray fraction to **≥15%** (~3× today); then rebuild the dense dataset and re-run UC-83's existing, tested v2 recipe (`eyes dataset` / `eyes train` / `eyes eval` + `eyes compare`) to see whether richer data clears the AC4 bar (≥30% relative nearest-quarter in-view miss reduction, false-alarm-on-clear ≤0.10). **Capture execution requires Liftoff**, so the flights run on the user's Liftoff machine (not this CUDA sandbox); the dev-team's deliverable is the capture protocol + tooling, the data-ingestion/validation step, and a resumable retrain/compare driver, so the user just flies the courses, drops the captures in, and runs the (sim-only) retrain. A pretrained depth-model backbone (UC-78 lever 3) is explicitly **out of scope** — it is the named follow-up (UC-85) if richer data still does not clear the bar.

## Acceptance Criteria
1. **Capture protocol doc.** A documented protocol specifying: the map list and how obstacle-dense courses are selected/configured; the teacher/model-driven flight method (which checkpoint drives the flights — e.g. the 70-input `training/11-count-curriculum` model or the teacher); captures and approximate frame count per map; and the **≥15% in-view hit-ray fraction** target with its rationale (vs the ~5% baseline that UC-83's rebalancing could not overcome).
2. **Capture tooling.** Reuses the existing Liftoff capture harness (UC-62 / UC-71 lineage) to record frames + telemetry in the existing capture format, runnable on the Liftoff machine with a documented command. No new Liftoff-side format is invented; captures land where `eyes dataset` already expects them.
3. **Ingestion + validation.** A command (sim-only, runnable in-sandbox) that validates dropped-in captures — format, telemetry/pose alignment, and the per-map and overall **in-view hit-ray fraction** (computed via the existing label raycast against track geometry) — and reports the achieved fraction vs the ~5% baseline, flagging when it is below the 15% target so the user knows to fly more.
4. **Resumable retrain/compare driver.** Rebuilds the dense dataset over the enlarged capture set and re-runs the UC-83 v2 recipe (`eyes dataset` → `eyes train` v1-baseline + v2 → `eyes eval` on the intact held-out split → `eyes compare`) producing the AC4 verdict. Reboot-safe / per-step markers like the UC-82/83 drivers; the sim-only part runs in-sandbox once captures exist.
5. **Result doc** `docs/experiments/uc84-liftoff-obstacle-capture.md`: the achieved in-view hit-ray fraction; a ray-accuracy table comparing v2-on-new-data against the UC-83 v1/v2-on-old-data numbers (nearest-quarter + aggregate in-view miss, FA-on-clear, hit-head recall); and the AC4 verdict. If AC4 clears, document the gated path to re-run the UC-82 obstacle-avoidance rays-vs-blank comparison with the new eyes; if it does not, record the negative result and name UC-85 (depth backbone).
6. **CI-hermetic tests** (CPU-only, no Liftoff, no real captures): the ingestion/validation logic (format + pose-alignment checks + the in-view hit-ray-fraction computation + the <15% flag) and the driver's step/skip/resume logic, on tiny synthetic captures.

## Potential Pitfalls & Open Questions
- **Risk** — a model-driven pilot that avoids obstacles well yields few genuine near-misses, undercutting the point. Mitigated by obstacle-dense course selection + the ≥15% in-view-hit gate (hit rays are counted from geometry in the forward cone, so frames with obstacles *ahead* count even when the drone later avoids them). If the driving checkpoint flies too clean to reach 15%, the protocol must offer a fallback — degraded/perturbed flying, slower speeds, tighter courses, or sampling from runs that do collide — which the dev-team analyst should specify.
- **Assumption** — the UC-62 / UC-71 Liftoff capture harness is reusable as-is for an obstacle-focused capture protocol (map/course selection, frame+telemetry logging) without a new capture-side format.
- **Assumption** — obstacle-dense courses exist or are configurable in the Liftoff maps available to the user; the protocol names which maps/courses qualify.
- **Risk** — even a ≥15% hit-ray dataset may not clear the AC4 near-miss bar; monocular ranging may genuinely require depth features. That outcome is acceptable and routes to UC-85 (depth-model backbone), which is out of scope here.
- **Edge case** — disk: new captures add to the ~23 GB already on disk (~18 GB free); the ingestion/protocol must be disk-aware (downscaled frame cache, prunable intermediates, margin guard) as in UC-83.
- **Dependency** — the capture *execution* cannot run or be verified in this sandbox (no Liftoff); only the tooling, ingestion, driver, and tests are built + CI-tested here, and the sim-only retrain/compare runs here once the user supplies captures.

## Clarifications
- Q: How should the obstacle-focused flights be flown? A: Teacher/model-driven (reproducible, scriptable) through obstacle-dense courses — the protocol adds a degraded/perturbed-flying fallback if the clean pilot can't reach the hit-ray target.
- Q: What capture target defines "enough" data? A: In-view hit-ray fraction **≥15%** (~3× the current ~5%), measured at ingestion; map/course selection sized to hit it.
- Q: Scope the depth-model backbone (UC-78 lever 3) here or separately? A: Separately — UC-84 is strictly better-data + retrain/compare; the depth backbone is the named UC-85 follow-up if richer data still doesn't clear the bar.
