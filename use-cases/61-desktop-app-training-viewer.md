# Use Case 61: Desktop app to manage slices, trainings, and recordings (replace TUI + HTML viewer)

> **STATUS: BUILD-APPROVED (owner directive 2026-09-24).** The design/architecture analysis (`docs/desktop-app-analysis.md`, merged PR #67) was reviewed and the owner approved a build, resolving the analysis's five open questions with the four decisions below. The dev-team now **implements** this use case (it does not re-analyze). The analysis doc remains the grounding reference for the CLI surface, run registry, progress/pause mechanics, and viewer-embed approach.
>
> **Owner-approved build decisions (these override any conflicting phrasing below):**
> 1. **Framework — FastAPI + Uvicorn backend wrapped in a pywebview native desktop window from day one.** A real app window (not just a browser tab), pointing at the local server. Front-end is vanilla HTML/CSS/JS (no SPA framework); `viz/viewer.js` is reused unchanged. Electron/Tauri are rejected. Recording gzip is decompressed **server-side** so the choice does not depend on the system webview's `DecompressionStream`.
> 2. **Scope — Phases 0–2 of the analysis.** Configure + launch + monitor trainings; full run management (multiple named runs, concurrent, stop, pause/resume); the **slice-definition** surface; and the **Settings** pane — i.e. the complete left-nav (Generate slices / Train / Settings). Phase 3 packaging (PyInstaller) and remote-GPU topology are out of scope for this build.
> 3. **Backend glue — allowed in `src/drone_fly/train`.** Add a **JSONL status-emitter** callback (TUI-parity progress: timesteps, metrics, health verdict, dynamics summary) as the progress source, and a **checkpoint-on-signal handler** so pause flushes a checkpoint before terminating (**lossless pause**). This is pure observability/coordination glue — no training/env/reward logic changes.
> 4. **Topology — local-only.** App and training run on the same machine. Keep the client/server split clean so remote-GPU is a later config change, but do not build remote control now.

## Summary
Build a **lightweight desktop application** that replaces the current developer workflow of a training TUI plus a standalone HTML recording viewer, so the user manages the entire loop from one UI and never has to touch the TUI or hand-edit YAML. The app is a thin front-end over the existing Python CLIs (slice/prune, `train`, evaluate, the recorder) — it shells out to them under the hood — and reuses the existing dependency-free brain/inputs/course recording viewer (`viz/viewer.{html,js}`, UC-59/60) for playback. Framework must be **as lightweight as possible** (Electron is acceptable only if nothing lighter fits; Tauri, pywebview, or a local FastAPI/Flask server opened in the browser are lighter candidates given the Python + JS stack). The UI supports: (1) **defining/generating a new slice** via forms; (2) **configuring and launching multiple named trainings** via toggles/sliders/inputs (mirroring today's per-training-config-name runs) rather than editing files; (3) **monitoring a running training** — live progress, pause, resume, and access to its recordings; (4) **viewing recordings** with the existing brain + actions + 3D-course viewer. The layout is a **left-side navigation menu** (top level: Generate slices / Train / Settings, with sub-options) driving a **right-side main view**; clicking a terminal menu item swaps the main view. Configuration changes are committed only via an **explicit Save button** (no auto-save on blur/focus change), and **no configuration version history** is required.

## Acceptance Criteria
> These are the **build** contract (status is now BUILD-APPROVED). Each AC is something the shipped app must satisfy and QA must be able to verify. Where an AC's original wording referenced "the analysis," read it as "the implementation." The four owner decisions in the status banner override any conflicting phrasing.
1. **Framework as decided:** the app is a FastAPI + Uvicorn backend served inside a **pywebview** native window; front-end is vanilla HTML/CSS/JS (no SPA build chain); `viz/viewer.js` is reused unchanged; recording gzip is decompressed server-side. Launching the app opens the native window pointed at the local server.
2. **Left-nav → main-view shell:** a left menu with top-level Generate slices / Train / Settings (sub-options allowed); clicking a terminal item changes the right-side main view; hash routing (`#/train/<name>`, `#/train/new`, `#/slices/new`, `#/settings`) with working back/forward.
3. **Slice definition via UI:** a form-driven flow defines/generates a new slice by serializing to a `PruneRunConfig` YAML and invoking `drone-fly prune --config` (no manual file editing); the four fields (`connectome`, `out`, `prune_k`, `prune_rule`) are exposed.
4. **Training configuration via UI:** train configs are edited via toggles/sliders/inputs that serialize to the existing `TrainRunConfig` YAML schema; **every** key in the schema maps to a control; **omit-vs-default** is respected (a key is emitted only when the user sets it, tri-state placement toggles included); multiple **named** trainings are supported.
5. **Launch + manage trainings:** the app starts a run by spawning `drone-fly train --config <path> --no-tui` as a subprocess (CWD = project root); concurrent named runs are tracked via an in-backend `name → {pid,state}` map backed by the `training/<name>/` filesystem registry; stop terminates the subprocess cleanly.
6. **Live progress (JSONL emitter):** a new JSONL status-emitter callback in `src/drone_fly/train` writes one line per rollout (timesteps, metrics, health verdict, dynamics summary) to `training/<name>/status.jsonl`; the backend streams it to the UI (SSE/WebSocket or poll) to drive a progress bar and curves. CSV-tail is an acceptable fallback source, but the JSONL emitter is the primary path.
7. **Pause / resume (lossless):** pause flushes a checkpoint via a checkpoint-on-signal handler in `src/drone_fly/train`, then terminates the subprocess; resume relaunches `train` with `resume: auto` on the same YAML and continues from the just-flushed checkpoint (checkpoint `.zip` + matching `vecnormalize` `.pkl` + same config co-located). No progress is lost across a pause/resume cycle.
8. **Recording access + playback:** from a run, the user opens `training/<name>/recordings/episode_<n>.json[.gz]` in the embedded brain/actions/course viewer; the app serves `viewer.{html,js,css}` on a static route, gunzips server-side, and calls `window.loadDocument(parsed, name)`.
9. **Explicit save, no auto-save, no version history:** every form holds pending edits in local UI state; nothing persists on blur/focus-change/navigation; a single explicit **Save** button overwrites the target YAML in place; no snapshots/history; Launch is a separate action from Save; an unsaved-changes guard on navigation is acceptable.
10. **CLI-only under the hood:** every operation reduces to invoking an existing `drone-fly` subcommand or reusing an existing asset; the **only** new code in `src/drone_fly` is the JSONL status emitter (AC6) and the checkpoint-on-signal handler (AC7); the app itself lives **outside** `src/drone_fly` (e.g. `app/` or `tools/desktop/`).
11. **Tests + docs:** backend logic (YAML serialization incl. omit-vs-default, run enumeration, subprocess/pause-resume state machine, server-side gunzip, the JSONL emitter, the checkpoint-on-signal handler) is covered by hermetic tests that run in CI without a GPU/display; front-end/native-window rendering that cannot run headless in the sandbox is documented for owner eyeball (as with UC-59/60). README/docs describe how to launch and use the app.

## Potential Pitfalls & Open Questions
- **Ambiguity** — exact framework: "Electron or whatever, as lightweight as possible." The analysis must resolve this with a concrete recommendation, not leave it open.
- **Missing input** — the real pause/resume contract: whether the training loop can be paused live or only checkpointed-and-restarted; drives AC7.
- **Missing input** — progress source: does the TUI read a structured status the app can also read, or is progress only rendered to the terminal? May need a small structured-status emitter (thin glue in `src/drone_fly` — flag if so).
- **Edge case** — training host vs UI host: trainings run on a GPU box (possibly remote/Windows); the app may run elsewhere. The analysis must state the assumed topology (local-only first?) and whether remote control is in scope.
- **Edge case** — reusing the dependency-free `viz/viewer.js` (which loads a recording file via `file://`/DecompressionStream) inside the chosen framework: how files are handed to it.
- **Risk** — scope: this is a large, multi-surface app; the phased MVP must be small and genuinely useful (e.g. configure+launch+monitor one training, open its recordings) before the full slice-definition + settings surfaces.
- **Assumption** — no multi-user/hosted requirements (consistent with the project's stated non-goals); the app is a single-user local developer tool.
