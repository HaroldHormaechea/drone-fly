# Use Case 61: Desktop app to manage slices, trainings, and recordings (replace TUI + HTML viewer)

> **STATUS: ANALYSIS-ONLY (owner directive).** The owner wants the dev-team to produce a **design/architecture analysis** for this use case and push it to `main` for review — **not** to implement it yet. The analysis lives at `docs/desktop-app-analysis.md`. Do not begin implementation until the owner reviews the analysis and explicitly approves a build.

## Summary
Build a **lightweight desktop application** that replaces the current developer workflow of a training TUI plus a standalone HTML recording viewer, so the user manages the entire loop from one UI and never has to touch the TUI or hand-edit YAML. The app is a thin front-end over the existing Python CLIs (slice/prune, `train`, evaluate, the recorder) — it shells out to them under the hood — and reuses the existing dependency-free brain/inputs/course recording viewer (`viz/viewer.{html,js}`, UC-59/60) for playback. Framework must be **as lightweight as possible** (Electron is acceptable only if nothing lighter fits; Tauri, pywebview, or a local FastAPI/Flask server opened in the browser are lighter candidates given the Python + JS stack). The UI supports: (1) **defining/generating a new slice** via forms; (2) **configuring and launching multiple named trainings** via toggles/sliders/inputs (mirroring today's per-training-config-name runs) rather than editing files; (3) **monitoring a running training** — live progress, pause, resume, and access to its recordings; (4) **viewing recordings** with the existing brain + actions + 3D-course viewer. The layout is a **left-side navigation menu** (top level: Generate slices / Train / Settings, with sub-options) driving a **right-side main view**; clicking a terminal menu item swaps the main view. Configuration changes are committed only via an **explicit Save button** (no auto-save on blur/focus change), and **no configuration version history** is required.

## Acceptance Criteria
> These frame the eventual implementation. For the **analysis deliverable**, each AC is something the analysis must show is feasible and specify *how* it will be met (framework, data flow, CLI mapping), not something to build now.
1. **Lightweight framework, justified:** the analysis selects a UI framework/runtime with an explicit "as lightweight as possible" tradeoff table (bundle size, runtime deps, packaging per-OS, fit with the Python+JS stack) and a recommendation.
2. **Left-nav → main-view shell:** a left menu with top-level Generate slices / Train / Settings (sub-options allowed); clicking a terminal item changes the right-side main view; the navigation model is specified.
3. **Slice definition via UI:** a form-driven flow to define/generate a new slice maps to the existing slice/prune CLI (no manual file editing); the analysis lists the exact CLI + parameters it wraps.
4. **Training configuration via UI:** train configs are edited via toggles/sliders/inputs that serialize to the existing train YAML schema; multiple **named** trainings are supported (as today); the analysis maps every UI control to a YAML key.
5. **Launch + manage trainings:** the app starts a training by invoking the Python `train` CLI as a subprocess; the analysis specifies process management, working dir, and how concurrent/named runs are tracked.
6. **Live progress:** the app shows a running training's progress (the data the TUI shows today) sourced without the TUI — the analysis identifies the progress source (structured status/log file, IPC, or a small status endpoint) and how it updates the UI.
7. **Pause / resume:** the analysis states the **real feasibility** of pause/resume given the training stack (SB3 today supports checkpoint→stop→resume, not necessarily a live pause) and specifies the mechanism it will use (true pause vs checkpoint-and-resume), including how a resumed run continues cleanly.
8. **Recording access + playback:** from a run, the user opens its recordings in the existing brain/actions/course viewer (`viz/viewer.js`); the analysis specifies how the viewer is embedded/served and how recording files are located.
9. **Explicit save, no auto-save, no version history:** the config-editing model uses a Save button; edits are not persisted on focus change; no config history is kept.
10. **CLI-only under the hood:** every operation reduces to invoking existing Python CLIs / reusing existing assets — the analysis confirms no new training/env/runtime logic is required in `src/drone_fly` beyond thin glue (or names precisely what glue is needed).
11. **Phasing + risks + effort:** the analysis proposes a phased delivery (an MVP slice) and enumerates risks (packaging, cross-platform, subprocess lifecycle, progress plumbing, pause/resume, GPU/training-host coupling) with mitigations and a rough effort estimate.

## Potential Pitfalls & Open Questions
- **Ambiguity** — exact framework: "Electron or whatever, as lightweight as possible." The analysis must resolve this with a concrete recommendation, not leave it open.
- **Missing input** — the real pause/resume contract: whether the training loop can be paused live or only checkpointed-and-restarted; drives AC7.
- **Missing input** — progress source: does the TUI read a structured status the app can also read, or is progress only rendered to the terminal? May need a small structured-status emitter (thin glue in `src/drone_fly` — flag if so).
- **Edge case** — training host vs UI host: trainings run on a GPU box (possibly remote/Windows); the app may run elsewhere. The analysis must state the assumed topology (local-only first?) and whether remote control is in scope.
- **Edge case** — reusing the dependency-free `viz/viewer.js` (which loads a recording file via `file://`/DecompressionStream) inside the chosen framework: how files are handed to it.
- **Risk** — scope: this is a large, multi-surface app; the phased MVP must be small and genuinely useful (e.g. configure+launch+monitor one training, open its recordings) before the full slice-definition + settings surfaces.
- **Assumption** — no multi-user/hosted requirements (consistent with the project's stated non-goals); the app is a single-user local developer tool.
