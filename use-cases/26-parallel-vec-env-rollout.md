# Use Case 26: Parallel vec-env rollout backend (real multi-core speedup)

## Summary
PPO rollout collection currently runs single-core. `build_vec_env` (`src/drone_fly/env/racing_env.py:581`) builds `DummyVecEnv([_factory for _ in range(max(1, n_envs))])`, which steps every sub-env sequentially in the main process, so raising `n_envs` (config default 1, `train/config.py:45`; user runs 4) only enlarges the rollout batch (`n_steps * n_envs` per PPO update) and the per-iteration wall time proportionally — net samples/sec stays flat, no real parallel speedup. This UC adds a `SubprocVecEnv` backend (one worker process per env → true cross-core parallelism), wired `TrainRunConfig → build_vec_env`, keeping the `VecMonitor`-inside-`VecNormalize` wrapping order (`racing_env.py:585-600`) identical for both backends. Backend selection is **automatic**: `SubprocVecEnv` is used when `n_envs > 1` **and** the adapter is `pybullet`, otherwise `DummyVecEnv` — so the hermetic `simple`/CI smoke-train stays on `DummyVecEnv` (green, fast, deterministic) with no flags. Workers use the **`spawn`** start method (safe on macOS/Python 3.11 with native libs like pybullet) and each independently reconstructs the seeded env from cheap config (a live connectome can't be inherited under spawn). When the parallel backend is active and `n_envs` isn't set explicitly, it **defaults to 8** (matches the M4 Pro's performance-core count), overridable via config/CLI. Checkpoint/VecNormalize load compatibility is preserved across backends. No observation-schema, connectome, reward, or checkpoint change — rollout-infrastructure only; a normal run's learning outcome is equivalent (subject to inherent multiprocess RNG/ordering differences) while wall-clock drops materially with the pybullet adapter at `n_envs ≈ P-cores`.

## Acceptance Criteria
1. **Automatic backend selection, wired end-to-end:** `build_vec_env` produces a `SubprocVecEnv`-backed stack when `n_envs > 1` **and** the resolved adapter is `pybullet`, and a `DummyVecEnv`-backed stack otherwise (`n_envs == 1`, or the `simple` adapter). The rule is threaded from `TrainRunConfig` through to `build_vec_env` and is independently unit-testable for each branch (pybullet+n>1 → subproc; simple → dummy; n_envs==1 → dummy).
2. **Identical wrapper stack for both backends:** the wrapping remains `VecMonitor` (inside, `info_keywords=("is_success",)`) → `VecNormalize` (outside), in that order, regardless of backend — asserted by test.
3. **Real cross-core parallelism:** with the subproc backend and `n_envs > 1`, sub-envs run in separate worker processes concurrently (verifiable: worker PIDs differ from the main process and from each other).
4. **`spawn` correctness / picklable factory:** `SubprocVecEnv` is created with an explicit `start_method="spawn"`; the env factory is picklable and each worker independently reconstructs the seeded env from config (no reliance on inheriting a live connectome/adapter object). A test exercises the spawn path and asserts a worker builds a functioning env and completes a step.
5. **`n_envs` default of 8 for parallel runs:** when the parallel backend would be selected and `n_envs` is not explicitly provided, `n_envs` resolves to 8; an explicit config/CLI value overrides it. The non-parallel/default path (unset, `simple`, or explicit 1) is unchanged. Verified by a config-resolution test.
6. **Hermetic CI unchanged and green:** the `simple`-adapter fixture smoke-train stays on `DummyVecEnv`, completes a finite update deterministically, and the whole Linux suite (`ruff check .`, `ruff format --check .`, `uv run pytest`) stays green. No new heavy dependency (SB3 already ships `SubprocVecEnv`).
7. **Checkpoint/resume compatibility:** `PPO.load(ckpt, env=venv)` + `VecNormalize.load(stats, venv)` work under the subproc backend; VecNormalize stats saved under one backend load under either (backend-independent). The `n_steps`/`batch_size`/scheduled-iters math (`loop.py:437-447`, `559`) stays correct when `n_envs` is larger (e.g. 8).
8. **Policy stays on CPU:** no silent move of the policy to MPS/GPU as part of this change; CPU remains the default device. Any device change is out of scope / a separate explicit opt-in.
9. **No obs/connectome/checkpoint change:** rollout-infrastructure only — observation schema, width, connectome graph, reward, and existing checkpoints are all unaffected; base-path (non-parallel) per-step outcomes stay byte-identical.
10. **Documented, named config:** the backend-selection rule, the `start_method`, and the default-`n_envs` value are named/documented constants or config with sensible defaults; `configs/train/example.yaml` (and any relevant docs) note the parallel behavior, the P-core-vs-E-core sweet-spot guidance, and that the `simple` adapter stays serial.
11. **Parallelism surfaced in the UC-22 TUI:** the live training dashboard (UC-22) displays the effective parallelization for the run — at minimum the resolved `n_envs` (parallel worker count) and the active backend (`subproc` vs `dummy`) — in the metrics panel (e.g. the train/config area), so the operator can see at a glance how many cores the rollout is using. When the TUI is off, the same fact is emitted once as a startup log line. The value shown must be the *resolved* one (after the auto-selection + default-8 logic), not the raw config input. Verified by a render/format unit test against the TUI's pure metrics layer (not by driving a live `Live` display).

## Potential Pitfalls & Open Questions
- **Risk (spawn re-import cost)** — every worker re-imports the package and rebuilds the connectome-seeded env; if seeding is expensive (download/prune), spawn startup could dominate short runs. The factory must rebuild from cheap resolved config, not re-download/re-prune per worker; the analyst pins how the seeded connectome is made available cheaply to each worker (e.g. a cached/pruned artifact path in config).
- **Edge case (`simple` adapter + subproc)** — IPC/serialization overhead can erase gains for the cheap numpy adapter; the automatic rule keeps `simple` on `DummyVecEnv`, and an explicit request for subproc on `simple` (if allowed at all) must at least warn.
- **Risk (deterministic tests vs multiprocess RNG)** — multiprocess rollout ordering is not byte-reproducible; determinism-sensitive tests must stay on `DummyVecEnv`, and equivalence is asserted at the "learns/updates" level, not byte-identity of the parallel path.
- **Edge case (worker crash / cleanup)** — a subproc worker dying (e.g. pybullet init failure in a worker) must surface cleanly and not hang the run; `SubprocVecEnv` teardown must close workers on abort/error.
- **Edge case (oversubscription)** — 8 workers + 1 learner on a 12-core (8P+4E) M4 Pro slightly oversubscribes the P-cores; acceptable per the user's fixed-8 choice since rollout and optimize phases don't peak simultaneously, but documented.
- **Assumption** — SB3's stock `SubprocVecEnv` is used as-is; no custom shared-memory transport. Sufficient for this policy/observation size.

## Clarifications
- Q: How should the vec-env backend be chosen at runtime?
  A: **Auto** — pick `SubprocVecEnv` when `n_envs > 1` AND the adapter is `pybullet`, else `DummyVecEnv`. Keeps `simple`/CI on Dummy automatically and uses cores for real training with no extra flags.
- Q: What should `n_envs` default to for a parallel/pybullet run?
  A: **Fixed default of 8** (matches the M4 Pro's 8 performance cores), overridable via config/CLI. The non-parallel path keeps its current default.
- Q: Which multiprocessing `start_method` for `SubprocVecEnv`?
  A: **`spawn`** — safest cross-platform including macOS + native libs (pybullet); workers re-import cleanly.
- Q: (added after drafting) Should the parallelization be visible while training?
  A: Yes — the resolved `n_envs` (worker count) and active backend must be shown in the UC-22 live TUI dashboard's metrics panel, and logged once at startup when the TUI is off. Captured as AC-11.
