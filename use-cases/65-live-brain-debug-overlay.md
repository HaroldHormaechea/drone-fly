# Use Case 65: Live brain + debug overlay on top of Liftoff (Windows, click-through, capture-excluded)

## Summary
Add a **Windows desktop overlay** that floats over Liftoff (and anything else on screen) while the UC62/UC64 live harness flies, showing **the brain's activity as in the visualizer** (the UC-12/UC-60 MRI/fMRI-style heatmap of the K1 reservoir over the brain outline) plus a compact **"what is the AI doing" debug HUD**: the obs/extra vectors fed to the policy, the raw action → collective/body-rate command → stick values actually sent, detected gate keypoints/boxes and range drawn in game-screen space, the 40-ray raycast fan, estimate ages, per-stage latency and missed deadlines, focus/fail-safe state and stop reason, and telemetry (speed, altitude, battery). The overlay is a **separate process** (`drone-fly harness overlay`) fed by a **non-blocking localhost UDP stream** that the runner publishes once per tick (brain frames decimated); it drops data rather than ever blocking the 50 Hz loop. Because the UC64 runner **fails safe the moment Liftoff loses foreground focus**, the overlay window must never take focus or input: borderless, transparent, topmost, click-through, non-activating, not in the taskbar/Alt-Tab (Win32 `WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOPMOST | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`, shown without activation). Because the harness **screen-captures the game** (dxcam/mss) for the gate detector and depth model, the overlay must also be **excluded from capture** (`SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`), with a verified fallback of confining overlay panels to the UC64 HUD-mask regions. It renders on the CPU at ≤ 20 Hz so it does not compete with Liftoff and the detector/depth/policy on the shared RTX 3050. **Depends on UC-64** (focus fail-safe, learned gate estimator, depth → raycast, per-stage latency, HUD masks) being merged to `main` first. Prototype maturity; training code, `gpu_prototype/` and the inference contract stay read-only.

## Acceptance Criteria
1. **Brain state without touching the contract:** `ContractPolicyRunner` gains an opt-in path (`act_with_brain(obs, extra)` or equivalent) that returns the raw action **and** the full propagated reservoir state (all K1 neurons, as produced by `actor.propagated_full`) by calling the loaded contract policy's own `actor.propagated_full` → `actor.tap` → `actor.act` sequence — the same ops `inference.Policy.act` runs — so nothing is computed twice. A parity test pins the returned action **bit-identical** to `Policy.act` on a fake/stub actor with the same interface. `gpu_prototype/inference.py` is not modified; when the overlay is disabled the runner keeps calling the existing `act` path unchanged.
2. **Non-blocking publisher:** a runner-side publisher (enabled by `overlay.enabled` in the harness config and/or `drone-fly harness run --overlay`) sends, per tick, a small JSON (or msgpack) "tick" datagram to `127.0.0.1:<overlay.port>` (default chosen in config) carrying: tick, wall/sim time, run state, harness name, checkpoint name + short sha, `extra_dim`, obs (12), extra (12/30/70, with block boundaries per the contract), raw action (4), collective, body rates, sink output (stick values), gate estimate (status, index, lap, target/rel, range, class, detected keypoints in **frame pixel coordinates** and the frame stamp), free-space estimate (obstacle_vision 8, raycast 40, in-FOV mask, coverage), `latency_s`, `perception_s`, `ages_s` and their configured limits, missed-deadline count, focus state, events, and — on stop — the stop reason and fail-safe outcome. Telemetry extras not in `TickRecord.state` (speed, altitude, battery, stick inputs if present) come from the tick's `TelemetrySample`. A separate "brain" datagram carries the full reservoir state **quantised to uint8** with the recorder's existing scheme (`quantize_activation`, ~25.6 KB for K1, one datagram) every `overlay.brain_every_n` ticks (default 3 → ~16 Hz). The socket is non-blocking; any send error or `EWOULDBLOCK` drops the datagram, increments a counter, and never raises into the loop. Unit tests use a fake socket to show: payload schema, decimation, drop-on-error, and that a publisher failure cannot stop a run.
3. **Loop-budget guard:** the publisher's per-tick cost (serialise + GPU→CPU copy of the brain state on brain ticks + send) is measured into `latency_s["overlay"]`; a test with a fake clock shows it is recorded and excluded from `inference`. Live (AC13) p99 publish cost ≤ 1 ms and no increase in missed-deadline rate beyond +1 percentage point versus the same run without the overlay.
4. **Overlay process:** `drone-fly harness overlay [--port N] [--monitor M] [--layout <name>] [--replay <run-folder>]` starts the overlay window. It listens on the UDP port, keeps only the latest tick and latest brain frame (older packets discarded), and shows a "waiting for harness" / "no data for N s" state when the stream is absent or stale (> 1 s), and keeps the **last stop reason** visible after a run ends until the next run starts.
5. **Window behaviour (Win32):** the window is borderless, per-pixel transparent, always-on-top, click-through and non-activating: extended styles `WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOPMOST | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW` are applied to its native handle, it is shown without activation (`SW_SHOWNOACTIVATE` / toolkit equivalent), it does not appear in the taskbar or Alt-Tab, it covers the monitor configured as the harness capture monitor (`camera.monitor`), and the process is per-monitor-DPI-aware so overlay coordinates match game pixels. A unit test asserts, through an injectable Win32 shim, that exactly these styles and the display affinity (AC6) are requested on creation; the module imports and the test runs on non-Windows CI with the shim.
6. **Capture exclusion:** the overlay calls `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)`; if the call fails (pre-2004 Windows, driver refusal) the overlay logs a loud warning and automatically switches to **mask-confined layout**: every panel is placed inside the configured UC64 HUD-mask regions (which the gate detector, auto-labeller and depth sampling already ignore), and in-game drawings (gate boxes, ray fan) are disabled. A unit test covers the fallback decision through the shim.
7. **Brain panel "as in the visualizer":** a panel renders the full K1 reservoir state as the visualizer does — per-neuron additive Gaussian splats weighted by **deviation from rest** (resting neuron = dark), a hot colormap, over the static registered brain outline, using the same neuron positions/projection the recordings use (`drone_fly.record.coordinates` / the K1 slice's provisioned positions) and the UC-60 rule that out-of-boundary afferents render in the tagged side boxes. Because the visualizer's per-neuron gain is computed over a **whole recorded episode** (unavailable live), the overlay uses a **running per-neuron gain** (decaying min/max window, default ~5 s) plus a global visibility gain, documented in-source; tap (readout-visible) neurons can be optionally outlined. Positions and the splat kernel are precomputed once; per-frame work is a vectorised numpy splat at reduced resolution then upscaled. A test renders a synthetic state into an offscreen image and checks a hot spot appears at a known neuron's position and a resting state renders dark.
8. **Debug panels:** (a) **Action** — raw action bars, collective (with hover marker), body rates vs `MAX_BODY_RATE`, and the stick values from the sink; (b) **Inputs** — obs 12 grouped as rel / g_body / vel / omega, and the extra vector grouped by contract block (curr_gate, next_lookahead, obstacle_vision, raycast) as signed bars; (c) **Raycast fan** — the 40 rays as a polar/cone plot with out-of-FOV rays greyed; (d) **Perception** — gate status, index/lap, class, range, rel, and the detected keypoints/outline drawn **in game-screen space** over the gate (frame pixel → screen mapping from `camera.region`/resolution), tagged with the frame's age; (e) **Health** — tick rate, stacked per-stage latency (state, gate, free-space, inference, actuation, overlay), missed deadlines, estimate ages vs limits (amber near the limit, red past it), focus state, fail-safe/stop reason, publisher drop count; (f) **Telemetry** — speed, altitude, attitude, battery. Each panel can be toggled in the layout config; a default layout keeps panels at the screen edges away from the game centre.
9. **Replay mode:** `--replay <run-folder>` drives the overlay from a UC62/UC64 run folder's `ticks.jsonl` at recorded speed (brain panel shows "no brain data" unless the folder carries brain frames), so the overlay can be developed and inspected without Liftoff. A test feeds a tiny committed synthetic `ticks.jsonl` through the replay reader into the panel models (no window).
10. **Pure-model separation:** all layout/state logic (packet decoding, latest-wins buffering, staleness, gain, splat, panel data models, fallback decision) lives in toolkit-free modules that are unit-tested without a display; only a thin window/painter layer imports the GUI toolkit.
11. **Hermetic CI:** the GUI toolkit (decided: PySide6) goes in a new `overlay` optional extra (Windows-only markers where relevant), never in `dev`; every overlay dependency is lazily imported (`lazy_import` / `HarnessDependencyError` style used by the harness); `import drone_fly.overlay` and the publisher import and run their tests on CI with only `--extra dev`; `drone-fly harness overlay` without the extra fails with a clear "install `--extra overlay`" message.
12. **Focus safety test:** with a fake focus probe and a fake overlay launcher, a test shows starting/stopping the overlay never changes the runner's focus result, and that the runner still waits for focus (UC64 `wait_for_focus_s`) after the overlay is launched.
13. **Live check (performed by the user/orchestrator on the Windows machine):** with Liftoff in **borderless fullscreen** on the capture monitor, start `drone-fly harness overlay`, then run the UC64 stage (b) configuration (`drone-fly harness run --harness liftoff --overlay`, 70-dim model, depth free-space). Pass when: (i) the overlay is visible over Liftoff for the whole run and updates live (brain panel animates; action/inputs/health change every tick); (ii) the run is **not** stopped with `focus_lost` because of the overlay, and clicking/moving the mouse over overlay panels reaches Liftoff/desktop underneath; (iii) a frame grabbed by the harness's own frame source during the run (saved via the run folder's frame recording) contains **no overlay pixels** — or, if affinity failed, the overlay ran in mask-confined layout and all its pixels lie inside the HUD masks; (iv) AC3's publish-cost and missed-deadline limits hold, read from the run folder; (v) the overlay shows the final stop reason after F12. The result (pass/fail per item, screenshots taken with a phone/external capture since the overlay excludes itself from capture) is recorded in the ADR.
14. **Docs:** an ADR records the window-style/affinity approach, the toolkit choice, the UDP schema and decimation, the live-gain deviation from the visualizer, the borderless-fullscreen requirement, the capture-exclusion verification result and the live-check outcome; the harness README gains an "overlay" section.
15. Existing tests stay green; ruff passes; new deps only in the `overlay` extra; nothing under `training/`, `gpu_prototype/`, `docs/INFERENCE_CONTRACT.md`, training configs or `artifacts/` (beyond run folders produced by the live check) changes.

## Potential Pitfalls & Open Questions
- **Risk** — Focus theft: a topmost window that is ever activated (on creation, on a toolkit repaint, on a stray click if click-through fails) makes `GetForegroundWindow` return the overlay and the runner stops with `focus_lost`. Mitigated by `WS_EX_NOACTIVATE` + show-without-activate + `WS_EX_TRANSPARENT`; AC12/AC13(ii) verify it. Launching the overlay from a console may briefly focus that console — the runner already waits for focus, so start the overlay before focusing Liftoff.
- **Risk** — Capture pollution: if `WDA_EXCLUDEFROMCAPTURE` is not honoured by the capture path actually in use (dxcam Desktop Duplication vs mss GDI BitBlt), overlay pixels would enter the gate detector and depth model and silently corrupt perception. Must be verified live per backend (AC13(iii)); fallback is the mask-confined layout (AC6).
- **Edge case** — Exclusive fullscreen: DirectX exclusive-fullscreen games are not composited by DWM, so no overlay can be drawn over them. Liftoff must run borderless fullscreen or windowed (UC64's capture setup already assumes a composited desktop).
- **Edge case** — Multi-monitor / DPI: overlay coordinates must match game pixels (2560×1080 at the configured monitor); Windows display scaling ≠ 100 % breaks the frame-pixel → screen mapping unless the overlay is per-monitor-DPI-aware.
- **Assumption** — The K1 reservoir is **feed-forward per tick** (`propagated_full` starts from a zero state every step — there is no recurrent brain state), so the per-tick brain activity is a pure function of the 12-dim obs; the overlay shows exactly what the readout's tap sees, not a hidden temporal state.
- **Assumption** — Live gain differs from the visualizer: recordings normalise per episode after the fact (`record_aug.py` peak gain, `viewer.js` per-neuron episode gain); live we can only use a running window, so the picture will look similar but not identical to an offline recording of the same flight.
- **Risk** — GPU→CPU copy: pulling ~25.6k floats off the GPU forces a CUDA sync on brain ticks; small, but it lands inside the tick. Decimation (`brain_every_n`) and AC3 measurement bound it; if it hurts, copy asynchronously into pinned memory.
- **Risk** — Shared machine load: the overlay's CPU rendering competes with Liftoff and the harness threads on the same box; cap overlay FPS (≤ 20) and resolution of the splat buffer.
- **Missing input** — Detected gate keypoints are not currently part of `GateEstimate`'s public payload in pixel space; the learned estimator must expose them (e.g. in `info`) for AC8(d). This is a small harness change, in scope.
- **Missing input** — Exact panel layout / sizes / colours are left to the analyst within AC8 (edges of the screen, game centre kept clear).
- **Edge case** — UDP port collision with Liftoff's telemetry UDP port or another tool: the overlay port must be configurable and must differ from the telemetry listener port (validate in config).
- **Risk** — Concurrent work: another agent changes training on `main`; implementation happens on a separate branch/worktree, cut **after UC-64 merges**, and must not touch training paths.

## Clarifications
- Q: Separate process or a thread inside the harness runner?
  A: Decided by the drafting agent (user unavailable): separate process fed by localhost UDP, latest-wins, drop-on-error — a GUI event loop and rendering must never block or jitter the 50 Hz loop. Revisit if wrong.
- Q: Which transport between runner and overlay?
  A: Decided by the drafting agent (user unavailable): non-blocking localhost UDP (JSON/msgpack tick datagram every tick, uint8-quantised brain datagram every 3rd tick) — trivially non-blocking, loss-tolerant, and the 25.6 KB brain frame fits one datagram; shared memory was judged more complex for no prototype benefit. Revisit if wrong.
- Q: Which GUI toolkit for the overlay window?
  A: Decided by the drafting agent (user unavailable): PySide6 (Qt) with Win32 extended styles applied via ctypes to the native handle, CPU rendering with QPainter + numpy splats — gives reliable per-pixel transparency and handle access; pywebview/WebView2 (the desktop app's stack) was rejected because transparent, click-through, non-activating WebView2 windows are unreliable. Revisit if wrong.
- Q: Reuse `viz/viewer.js` for the brain panel, or reimplement?
  A: Decided by the drafting agent (user unavailable): reimplement the same heatmap method (deviation-from-rest Gaussian splats, hot colormap, brain outline, UC-60 out-of-boundary boxes) in numpy, using the same neuron positions — "as in the visualizer" means the same look, not the same code; embedding a browser engine in the overlay costs GPU/CPU and complicates transparency. Revisit if wrong.
- Q: Which brain activity to show — full reservoir, only the readout's tap, or readout hidden units?
  A: Decided by the drafting agent (user unavailable): the full propagated K1 state (same as the visualizer's recordings), optionally outlining tap neurons; the readout's influence is shown via the action panel. Revisit if wrong.
- Q: How to get the brain state without editing the inference contract?
  A: Decided by the drafting agent (user unavailable): a harness-side `act_with_brain` that calls the loaded contract policy's own actor methods in the same order as `Policy.act`, parity-tested bit-identical; `gpu_prototype/inference.py` stays untouched. Revisit if wrong.
- Q: How to keep the overlay out of the harness's own screen capture?
  A: Decided by the drafting agent (user unavailable): `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`, verified live per capture backend; automatic fallback to panels confined to the UC64 HUD-mask regions with in-game drawings disabled. Revisit if wrong.
- Q: Should the overlay accept any input (hotkeys, dragging panels)?
  A: Decided by the drafting agent (user unavailable): no — it is fully click-through and focusless; layout, opacity and panel toggles come from config/CLI, and F12 stays the harness abort. Revisit if wrong.
- Q: Is a live run part of acceptance?
  A: Decided by the drafting agent (user unavailable): yes — AC13, a UC64 stage (b) run with the overlay, judged on visibility, no focus loss, no capture pollution and loop budget; flight success not required. Revisit if wrong.
- Q: Does this depend on UC-64?
  A: Decided by the drafting agent (user unavailable): yes — it taps UC64's focus fail-safe, learned gate keypoints, depth → raycast, HUD masks and per-stage latency; implementation starts after UC-64 is merged to `main`. Revisit if wrong.
