# Use Case 49: Drone-dynamics observability — TUI segment, recording provenance, and T/W regression guard

## Summary
UC-47 diagnosed and UC-48 fixed the mass/thrust-scale bug that made the pybullet drone free-fall at any throttle (a randomized ~1 kg mass applied to the CF2X body while its native motor thrust — sized for 0.027 kg — was left alone, collapsing thrust-to-weight to ≈0.24). That fix now lives behind `EnvConfig.pybullet_tw_preserving` (default `True`), reinterpreting the sampled point mass as a CF2X-relative multiplier and scaling the mixer RPM band with `sqrt(mass_ratio)` so peak T/W stays invariant — see `resolve_tw_preserving_dynamics(...) -> ResolvedPybulletDynamics` and `thrust_to_weight(applied_mass, rpm)` in `src/drone_fly/adapter/pybullet_adapter.py` (both pure numpy, no pybullet import). This use case makes that physics **observable and regression-guarded** so the bug (which lived silently in the wiring/sampler layer for many training UCs) can never come back unseen. It introduces **one** shared runtime **drone-dynamics summary** — applied mass, weight (`mass·g`), thrust-to-weight, hover throttle, max body-rate, and the active training-curriculum knobs (UC-46 attitude-authority factor, UC-44 spawn-z) — computed **once** by reusing UC-48's `thrust_to_weight` and resolved dynamics, then surfaced in three places: (1) a new **top segment of the training TUI**, rendered per iteration above the existing TIME/TRAIN/ROLLOUT panel; (2) an **additive `meta` block in every recording** (beside the UC-45 `git_sha`/`checkpoint`/`dynamics` provenance); and (3) an **end-to-end hermetic CI-gating T/W regression guard** that takes the real `EnvConfig()` default plus the real `sample_dynamics` mass range and asserts the resulting configured pybullet drone stays flyable/in-band. This is strictly **observability + a guardrail**: it must not change training behavior, the UC-48 fix, the simple backend, the reward, or the UC-44/UC-46 curricula. The single shared computation is the anti-drift keystone — the TUI, the recording, the guard, and the tests all read the same number, so a display, a recording, and CI can never disagree about what the drone's T/W is.

## Acceptance Criteria
1. **One shared runtime drone-dynamics-summary computation.** A single pure function — proposed `drone_dynamics_summary(...)` in a new `src/drone_fly/adapter/dynamics_summary.py` (a `@dataclass(frozen=True) DroneDynamicsSummary` result) — computes the summary from the resolved dynamics for a given backend, **reusing UC-48's helpers** (`resolve_tw_preserving_dynamics` for the pybullet applied-mass/RPM band, `thrust_to_weight` for T/W) rather than re-deriving them. Fields at minimum: `applied_mass` (kg), `weight` (N, `applied_mass·g`), `thrust_to_weight` (peak T/W at full throttle), `hover_throttle` (the throttle that gives T/W≈1.0), `max_body_rate` (rad/s), plus the active curriculum knobs `attitude_authority` and `spawn_z`. It is **hermetically unit-testable without importing pybullet** (it is pure numpy/arithmetic over the same constants UC-48 exposes: `CF2X_NATIVE_MASS`, `CF2X_HOVER_RPM`, `CF2X_MAX_RPM`, `CF2X_KF`, `CF2X_GRAVITY`, `BASE_MASS`). A unit test asserts the field values for a known `(sampled_mass, tw_preserving)` pair, including the T/W-invariance under `tw_preserving=True` and the degenerate collapse under `tw_preserving=False`.
2. **New TUI top segment.** A new `build_drone_panel(model)` in `src/drone_fly/train/tui/render.py` renders a full-width segment **above** the existing values panel (added to `build_layout`'s `left` column split, or as a new top row of the layout), showing at least: **Weight** (N), **T/W**, **hover throttle**, **max body-rate**, and the **active curriculum knobs** (attitude-authority factor, spawn-z). The `DashboardModel` in `src/drone_fly/train/tui/metrics.py` gains a slot to carry the latest `DroneDynamicsSummary` (fed additively via `update(...)`/a new setter, `None`-tolerant → placeholder, mirroring the existing `self.raw` None-handling), and the `TrainingDashboard`/callback wiring in `src/drone_fly/train/tui/dashboard.py` + the callback populate it per iteration. A **hermetic render test** builds the panel/layout from a known summary and asserts the formatted Weight/T/W/hover-throttle/max-body-rate/curriculum values appear (constructible headlessly, exactly like the existing `render.py` tests). A summary of `None` (no dynamics available yet) renders placeholders and never raises — the TUI degrades gracefully like every other panel.
3. **Summary preserved in the recording `meta`.** The summary is stamped into every recording as an **additive** `meta` block (proposed key `meta.drone_dynamics`), alongside the UC-45 provenance (`git_sha`, `checkpoint`, `dynamics`) in `src/drone_fly/record/recorder.py`'s `finish_episode` meta assembly. It is **presence-guarded** (omitted entirely when no summary is set, exactly like the existing `meta.course` / `meta.dynamics` blocks) so pre-UC-49 recordings and no-randomization runs stay byte-for-byte back-compatible. `SCHEMA_VERSION` stays **1** — verify the repo treats `meta` additively (it does: UC-06 `course`, UC-09 `target_gate`, and UC-45 `dynamics` were all added at `SCHEMA_VERSION = 1`); only bump if a reader actually breaks, and justify it in the PR. A `set_drone_dynamics(summary)` setter mirrors `set_course`/`set_dynamics`, wired from the recorder construction / `RecordingCallback` path in `src/drone_fly/train/loop.py`. A hermetic test writes a recording with a summary and asserts the `meta.drone_dynamics` fields are present and correct (and absent when no summary is set).
4. **End-to-end hermetic CI-gating T/W regression guard.** A hermetic test constructs the **real `EnvConfig()` default** and reads the **real `sample_dynamics` mass range** (`RandomizationConfig.mass_factor_range` × `DynamicsParams.mass`, i.e. base 1.0 kg × [0.8, 1.2]), resolves each end of that range through the summary computation on the pybullet path (`tw_preserving=True`), and asserts the configured pybullet drone stays **flyable and in-band: peak T/W ∈ [1.5, 2.5] across the entire sampled mass range**, with **T/W invariance** (T/W is unchanged by mass under the fix) as the hard property. This deliberately guards the **wiring/sampler layer** — the `EnvConfig` → `sample_dynamics` → resolve seam where the UC-47 bug actually lived — making it a strictly stronger gate than UC-48's helper-only unit test (AC2/AC3 of UC-48 asserted the pure helper; this asserts the whole default-config path end to end). It imports **no pybullet** (pure computation over the real config objects), so it gates CI.
5. **Optional build-time unflyable warning.** If a drone is ever *configured* with a T/W below a documented floor (proposed `T/W < 1.0`, i.e. cannot even hover), the summary computation (or its adapter-construction caller) emits a **`logging.warning`** naming the offending mass/T/W — a cheap tripwire so a future sampler/config regression that reintroduces the UC-47 collapse is loud at build/adapter-construction time, not silently absorbed into a wasted GPU run. Warning-only: it never raises and never alters dynamics. A hermetic test asserts the warning fires for a deliberately-unflyable configuration (e.g. `tw_preserving=False` with a heavy mass) and does **not** fire for the healthy default.
6. **Full CI gate green:** `uv run ruff check .`, `uv run ruff format --check .`, and `uv run --extra dev pytest` all pass. (mypy is **not** a CI step for this project.)
7. **Observability/guard-only invariant.** No change to the UC-48 fix (`resolve_tw_preserving_dynamics`, `thrust_to_weight`, `EnvConfig.pybullet_tw_preserving`, the `ctbr_to_rpm` mixer, the RPM-band scaling), the simple backend, the reward function, or the UC-44 airborne-start / UC-46 attitude-authority curricula. The diff is confined to: the new `dynamics_summary` module + its test, the TUI render/metrics/dashboard additions + their test, the recorder `meta` addition + its test, the T/W-regression guard test, the callback/loop wiring that feeds the summary, and docs (README) where a new displayed/recorded contract is introduced. Existing reward-math, curriculum, recording-fidelity/provenance, and TUI render/autosize tests stay green.

## Potential Pitfalls & Open Questions
- **Ambiguity** — Simple vs pybullet T/W derivation differ: the simple backend's T/W is preserved by construction (`BASE_MAX_THRUST = 2·m·g` ⇒ peak T/W ≈ 2, independent of mass), whereas the pybullet path derives applied mass + RPM band via `resolve_tw_preserving_dynamics` and T/W via `thrust_to_weight`. The shared summary must be **backend-aware** (branch on backend / on whether it is the CF2X path) and the regression guard (AC4) is specifically the **pybullet** path, where the bug lived.
- **Missing input** — Where do `hover_throttle` and `max_body_rate` come from per backend? `max_body_rate` is on `DynamicsParams` (default 4.0 rad/s) for both; `hover_throttle` is the throttle giving T/W≈1.0 — for pybullet derive it from the resolved `hover_rpm`/`max_rpm` band (`ctbr_to_rpm` maps throttle 0.5 → `hover_rpm`, so hover throttle ≈ 0.5 under the fix), for simple it is 0.5 by construction (`throttle · max_thrust / mass` with `max_thrust = 2·m·g`). The analyst should confirm these mappings against the actual adapters rather than hardcoding 0.5.
- **Assumption** — The recording-`meta` addition does **not** need a schema bump: the repo has consistently added `meta` blocks (`course`, `dynamics`) additively at `SCHEMA_VERSION = 1`, and readers treat unknown keys as optional. Verify no recording reader (viewer, evaluator, tests) asserts an exact `meta` key set before relying on this; bump only if one actually breaks, and say why in the PR.
- **Edge case** — TUI layout/width: UC-33 made the bottom status region autosize and the values panel is a fixed `size=8` in `build_layout`. A new top segment consumes vertical rows from the `left` column — pick a small fixed height (e.g. `size=3–4`, one content row + panel chrome) and confirm it does not clip the values/trends panels on a normal terminal; keep it width-tolerant (the UC-33 autosize discipline) so a narrow terminal wraps rather than crashes.
- **Assumption / Edge case** — The summary must reflect the **actual applied (post-UC-48-resolve) values**, not the raw sampled `DynamicsParams.mass`. On pybullet the displayed/recorded mass is `native_mass · mass_ratio` (≈0.027 kg scaled), the weight and T/W are the resolved ones — showing the raw ~1 kg sampled mass would be exactly the misleading number that hid the UC-47 bug. Compute the summary **from `ResolvedPybulletDynamics`**, not from the sampler output.
- **Assumption** — The curriculum knobs (`attitude_authority`, `spawn_z`) are **training-curriculum-time** values from `attitude_authority_at(num_timesteps, cfg)` (`src/drone_fly/train/attitude_curriculum.py`) and `spawn_z_at(num_timesteps, cfg, ...)` (`src/drone_fly/train/airborne_curriculum.py`). At **eval/record** time both run at their annealed endpoint (authority 1.0, spawn-z = floor per UC-44/46), so the summary should reflect the endpoint there and the live scheduled value during training — document which is shown in each of the three surfaces so an operator is not confused by a "1.0" at record time.
- **Risk** — Over-coupling: the temptation is to compute the summary three times (once for the TUI, once for the recorder, once for the guard). The whole point of AC1 is a **single** computation reused everywhere; three copies would let them drift and defeat the guardrail. Keep one function, one dataclass, and have all three consumers call it.
- **Edge case** — `hover_throttle`/T/W are undefined if `applied_mass` is 0 or the RPM band is degenerate; the summary must guard divide-by-zero and the unflyable-warning (AC5) should fire rather than emit `inf`/`nan` into the TUI or the recording.
